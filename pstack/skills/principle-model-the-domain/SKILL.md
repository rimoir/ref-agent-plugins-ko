# 도메인 모델링(Model the Domain)

실제 도메인을 조건문 곳곳에 흩뜨리지 말고 데이터 구조에 담는다. 도메인에 맞는 구조는 잘못된 상태를 표현할 수 없게 만들고 분기를 지운다. 쓰는 시점에 그것을 고르는 비용은 싸다. 나중에 되찾으면 리팩터링으로 읽혀 미뤄진다.

이런 것을 꺼낸다.

- 흩어진 불리언, 단계, 생명주기 검사 대신 상태 기계.
- 느슨한 매개변수나 반복되는 형태 가정 대신 타입이 있는 모델.
- 여러 파일에 퍼진 분기 대신 map, 레지스트리, 조회 테이블, 판별 유니언.
- 즉흥적인 상태 변경 대신 reducer나 command/event 모델.
- load, validate, transform, save 같은 순서가 아니라 도메인 지식 한 덩어리를 중심으로 짠 모듈. 실행 순서는 소유가 아니다.
- 반복되는 동작, 소유, 불변식을 모으는 작은 모듈 경계.
- 접근 패턴이 요구하는 곳의 큐, 캐시, 인덱스, 그래프, 트리, 정규화된 컬렉션.
- 그 밖에 맞는 구조라면 무엇이든. 맞는 것이 없으면 코드가 절대 허용하면 안 되는 것과 데이터를 읽는 방식을 따져 보고, 정확히 그것을 담는 구조를 찾는다.

추상화를 억지로 만들지 않는다. 현재 형태가 이미 명확하고, 국소적이고, 커질 것 같지 않다면 지루한 코드를 택한다. 분기, 중복 규칙, 잘못된 상태, 생명주기 위험을 없애지 않고 간접 계층만 더하는 추상화는 의심한다.

이것을 건너뛰었다는 신호는 새 기능이 기존 if/else 체인에 분기를 하나 더 붙이는 것, 또는 첫 번째와 계속 동기화해야 하는 두 번째 불리언이다. 시간 순서에 따른 분해도 신호다. 단계 이름을 단 모듈은 같은 도메인 규칙을 단계마다 되풀이한다.
