# 티켓으로 나누기

계획, 스펙, 대화를 **티켓**들로 나눈다. 각 티켓은 종단 간 최소 구현(tracer bullet, 모든 계층을 끝까지 얇게 관통해 바로 확인할 수 있는 작은 구현) 방식의 수직 슬라이스(스키마, API, UI, 테스트 모든 계층을 좁게 관통하는 작업 단위)이고, 자신을 **막는** 티켓을 적어 둔다.

이슈 트래커와 분류(triage) 라벨 이름은 이미 제공되었어야 한다. 제공되지 않았다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 알린다.

## 진행 절차

### 1. 맥락 수집

대화 컨텍스트에 이미 있는 내용을 바탕으로 작업한다. 사용자가 인자로 참조(스펙 경로, 이슈 번호나 URL)를 넘기면 그것을 가져와 본문과 댓글 전체를 읽는다.

### 2. 코드베이스 살펴보기(선택)

아직 코드베이스를 살펴보지 않았다면 살펴보고 현재 코드 상태를 파악한다. 티켓 제목과 설명에는 프로젝트 도메인 용어집의 용어를 쓰고, 작업하는 영역의 ADR(아키텍처 결정 기록)을 따른다.

구현을 쉽게 만들 사전 리팩터링 기회를 찾는다. "먼저 변경하기 쉽게 만들고, 그다음에 쉬운 변경을 한다."

### 3. 수직 슬라이스 초안 만들기

작업을 **종단 간 최소 구현** 티켓들로 나눈다.

<vertical-slice-rules>

- 각 슬라이스는 모든 계층(스키마, API, UI, 테스트)을 좁지만 **완전하게** 관통한다. 한 계층만 떼어 낸 수평 슬라이스가 **아니라** 수직 슬라이스여야 한다.
- 완성된 슬라이스는 그것만으로 시연하거나 검증할 수 있다.
- 각 슬라이스는 새 컨텍스트 창 하나에 들어갈 크기로 정한다.
- 사전 리팩터링은 먼저 한다.

</vertical-slice-rules>

티켓마다 **차단 관계**를 적는다. 즉 그 티켓을 시작하기 전에 끝나야 하는 다른 티켓들이다. 선행 티켓이 없는 티켓은 바로 시작할 수 있다.

**광범위 리팩터링은 수직 슬라이스의 예외다.** **광범위 리팩터링**은 기계적인 변경 하나(열 이름 바꾸기, 공유 심볼의 타입 바꾸기)의 **영향 범위**가 코드베이스 전체에 걸쳐 있어서, 한 번 수정하면 수천 개의 호출 지점이 한꺼번에 깨지고 어떤 수직 슬라이스도 CI를 통과한 상태로 반영할 수 없는 경우다. 이것을 억지로 종단 간 최소 구현으로 만들지 말고 **확장-축소**(expand–contract) 순서로 진행한다. 먼저 확장한다. 기존 형태 옆에 새 형태를 추가해 아무것도 깨지지 않게 한다. 그다음 호출 지점을 영향 범위에 맞춘 묶음(패키지별, 디렉터리별)으로 나눠 새 형태로 옮긴다. 묶음마다 확장 티켓에 막힌 별도 티켓으로 만들고, 기존 형태가 아직 남아 있으므로 묶음마다 CI가 계속 통과한다. 마지막으로 축소한다. 남은 호출자가 없으면 기존 형태를 지우고, 이 티켓은 호출 지점을 옮기는 묶음 티켓 모두에 막힌다. 묶음 하나만으로는 CI 통과 상태를 유지할 수 없을 때도 순서는 그대로 두되, 묶음들이 통합 브랜치 하나를 함께 쓰게 하고 그 묶음들이 모두 마지막 통합·검증 티켓을 막게 한다. CI 통과는 그 마지막 티켓에서만 보장한다.

### 4. 사용자에게 확인받기

제안한 분할을 번호 목록으로 보여 준다. 티켓마다 다음을 보여 준다.

- **제목**: 내용을 알 수 있는 짧은 이름
- **선행 티켓**: 먼저 끝나야 하는 다른 티켓(있다면)
- **전달하는 것**: 이 티켓이 동작하게 만드는 종단 간 동작

사용자에게 묻는다.

- 티켓 크기가 적절한가요? (너무 큼 / 너무 잘게 나뉨)
- 차단 관계가 맞나요? 각 티켓이 정말로 먼저 끝나야 하는 티켓에만 의존하나요?
- 합치거나 더 나눠야 할 티켓이 있나요?

사용자가 분할을 승인할 때까지 반복한다.

### 5. 설정된 트래커에 티켓 게시하기

승인된 티켓을 게시한다. **어떻게** 게시할지는 `/setup-matt-pocock-skills`가 설정한 트래커에 따라 다르다. 어느 쪽이든 티켓 내용은 같고 차단 관계를 표현하는 형태만 달라진다.

- **로컬 파일** → 티켓마다 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`에 파일 하나를 쓴다. 의존 순서(선행 티켓 먼저)대로 `01`부터 번호를 붙인다. 각 파일의 "Blocked by"에는 의존하는 티켓의 번호나 제목을 적는다. 아래 티켓별 파일 템플릿을 쓰고, 파일 하나에 티켓 하나만 쓴다. 여러 티켓을 파일 하나에 합치지 않는다.
- **실제 이슈 트래커(GitHub, Linear 등)** → 각 티켓의 차단 관계가 실제 식별자를 참조할 수 있도록 의존 순서(선행 티켓 먼저)대로 티켓마다 이슈 하나를 게시한다. 플랫폼에 자체 차단 관계나 하위 이슈 관계가 있으면 그것을 쓰고, 없으면 각 티켓의 "Blocked by"에 선행 이슈를 적는다. 따로 지시가 없으면 `ready-for-agent` 분류 라벨을 붙인다. 이 티켓들은 처음부터 에이전트가 바로 가져가 작업할 수 있게 만든 것이기 때문이다.

**진행 가능 목록**(frontier)에 있는 티켓을 작업한다. 진행 가능한 티켓은 선행 티켓이 모두 끝난 티켓이다. 순서가 한 줄로만 이어진 경우라면 위에서 아래로 처리하는 것과 같다.

상위 이슈는 닫거나 수정하지 마라.

<local-ticket-template>

# <NN>: <티켓 제목>

**만들 것:** 이 티켓이 동작하게 만드는 종단 간 동작. 계층별 구현 목록이 아니라 사용자 관점에서 쓴다.

**Blocked by:** 이 티켓을 막는 티켓의 번호나 제목, 또는 "None (can start immediately)"(선행 티켓 없음, 바로 시작 가능).

**Status:** ready-for-agent

- [ ] 인수 기준 2

</local-ticket-template>

어느 형태든 구체적인 파일 경로나 코드 조각은 넣지 않는다. 금방 낡기 때문이다. 예외가 있다. 프로토타입에서 나온 코드 조각이 결정을 글보다 더 정확하게 담고 있다면(상태 기계, 리듀서, 스키마, 타입 형태) 본문에 넣고 프로토타입에서 나온 것이라고 짧게 적는다. 동작하는 데모가 아니라 결정이 담긴 중요한 부분만 남기고 줄인다.
