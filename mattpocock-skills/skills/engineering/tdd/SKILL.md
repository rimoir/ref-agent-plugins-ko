# 테스트 주도 개발

TDD는 실패 → 통과 루프다. 이 스킬은 그 루프가 남겨 둘 가치가 있는 테스트를 만들도록 참고하는 자료다. 좋은 테스트가 무엇인지, 테스트를 어디에 두는지, 피해야 할 패턴, 루프의 규칙을 다룬다. 모든 섹션이 매 사이클에 적용된다. 루프가 끝난 뒤가 아니라 루프 전과 도중에 참고한다.

코드베이스를 살펴볼 때는 `CONTEXT.md`가 있으면 읽어서 테스트 이름과 인터페이스 용어를 프로젝트의 공통 언어(ubiquitous language, 팀과 코드가 함께 쓰는 도메인 용어)에 맞춘다. 작업하는 영역의 ADR(아키텍처 결정 기록)도 따른다.

## 좋은 테스트란

테스트는 구현 세부가 아니라 공개 인터페이스를 거쳐 동작을 검증한다. 코드는 통째로 바뀔 수 있어도 테스트는 바뀌지 않아야 한다. 좋은 테스트는 명세처럼 읽힌다. "user can checkout with valid cart"(유효한 장바구니로 결제할 수 있다)라는 테스트는 어떤 기능이 있는지 정확히 알려 주고, 내부 구조에 신경 쓰지 않으므로 리팩터링을 해도 깨지지 않는다.

예시는 [tests.md](tests.md), 모킹 지침은 [mocking.md](mocking.md)를 본다.

## 교체 지점: 테스트를 두는 곳

**교체 지점(seam)**은 테스트하는 공개 경계다. 안쪽을 건드리지 않고 동작을 관찰할 수 있는 인터페이스를 말한다. 테스트는 교체 지점에 두고, 내부를 대상으로 쓰지 않는다.

**미리 합의한 교체 지점에서만 테스트한다.** 테스트를 쓰기 전에 테스트할 교체 지점을 적고 사용자에게 확인받는다. 확인받지 않은 교체 지점에는 테스트를 쓰지 않는다. 모든 것을 테스트할 수는 없다. 교체 지점을 먼저 합의해야 테스트 노력이 모든 엣지 케이스가 아니라 핵심 경로와 복잡한 로직에 쓰인다.

다음과 같이 묻는다. "공개 인터페이스가 무엇이고, 어느 교체 지점을 테스트해야 할까요?"

그 인터페이스의 형태 자체가 불확실하면(모듈이 얼마나 깊은지, 교체 지점이 어디에 있어야 하는지, 인터페이스가 무엇을 드러내야 하는지) Skill 도구로 "codebase-design"을 호출해 용어를 가져온다. 이 스킬은 모듈, 인터페이스, 깊이, 교체 지점, 어댑터, 활용도(leverage, 호출자가 배우는 인터페이스 단위당 얻는 기능), 지역성(locality, 변경과 버그와 지식이 한곳에 모이는 성질) 용어를 정의하는 공통 출처다. 진행할 세션이 아니라 참고할 자료다.

## 피해야 할 패턴

- **구현에 묶인 테스트**: 내부 협력 객체를 모킹하거나, private 메서드를 테스트하거나, 인터페이스 대신 우회 경로로 검증한다(인터페이스를 쓰지 않고 데이터베이스를 직접 조회하는 식). 알아보는 방법: 동작은 그대로인데 리팩터링하면 테스트가 깨진다.
- **동어반복 테스트**: 단언이 코드와 같은 방식으로 기대값을 다시 계산한다(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 손으로 만든 스냅샷, 자기 자신과 같다고 단언하는 상수). 그래서 구조상 항상 통과하고 코드와 결과가 달라질 수 없다. 기대값은 코드와 독립된 기준에서 가져와야 한다. 검증된 리터럴, 직접 풀어 본 예제, 스펙이 그런 기준이다.
- **수평 슬라이스**: 테스트를 모두 먼저 쓰고 나서 구현을 모두 쓰는 방식이다. 한꺼번에 쓴 테스트는 _상상한_ 동작을 검증한다. 사용자가 보는 동작이 아니라 _형태_를 테스트하게 되고, 테스트가 실제 변경에 반응하지 않게 되며, 구현을 이해하기 전에 테스트 구조를 정해 버린다. 대신 **수직 슬라이스**(스키마, API, UI, 테스트 모든 계층을 좁게 관통하는 작업 단위)로 작업한다. 테스트 하나 → 구현 하나 → 반복한다. 각 테스트는 **종단 간 최소 구현**(tracer bullet, 모든 계층을 끝까지 얇게 관통해 바로 확인할 수 있는 작은 구현)이고, 직전 사이클에서 알게 된 것을 반영한다.

## 루프의 규칙

- **통과보다 실패가 먼저다.** 실패하는 테스트를 먼저 쓰고, 그 테스트를 통과시킬 만큼만 코드를 쓴다. 앞으로 쓸 테스트를 미리 예상하거나 추측으로 기능을 추가하지 않는다.
- **한 번에 슬라이스 하나만 다룬다.** 사이클마다 교체 지점 하나, 테스트 하나, 최소 구현 하나만 다룬다.
- **리팩터링은 루프에 속하지 않는다.** 리팩터링은 실패 → 통과 구현 사이클이 아니라 리뷰 단계(`code-review` 스킬 참고)에서 한다.
