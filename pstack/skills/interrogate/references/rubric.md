# 리뷰 기준표

관련 있는 렌즈만 골라 리뷰한다. 모든 렌즈가 모든 변경에 해당하지는 않는다. 판단해서 쓴다.

## 정확성

코드가 의도한 대로 실제로 동작하는가?

- 경계 사례: 빈 입력, nil/undefined, 경곗값, 동시 접근
- 오류 처리: 오류를 잡는가, 전파하는가, 조용히 삼키는가?
- off-by-one, 타입 강제 변환, 정수 오버플로, 문자열 인코딩
- 상태 관리: 경쟁 상태, 낡은 클로저, 매달린 참조
- 정상 경로가 동작하는가? 실패 경로도 동작하는가?
- 멱등성: 이 작업이 두 번 돌거나, 이전 실행이 중간에 죽었다면 어떻게 되는가? 답이 "남은 상태에 따라 다르다"라면 정합 단계가 빠진 것이다.
- 동시성: 여러 주체가 같은 가변 상태(파일, 브랜치, 공유 데이터)를 건드릴 수 있다면, 접근이 구조로 직렬화되는가(잠금, 순차 단계, 배타적 소유), 아니면 지켜지지 않을 관례에 기대는가?

잠재 버그를 찾으면 실행 경로를 추적한다. "이게 nil일 수 있다"고만 표시하지 않는다. 그것을 nil로 만드는 호출 체인을 보여 준다.

## 근본 원인 대 증상

코드가 실제 문제를 고치는가, 증상을 덮는가?

여기에 답하려면 바뀐 파일 너머를 봐야 할 때가 많다. 주변 코드(호출자, 피호출자, 타입 정의, 형제 모듈)를 읽고 변경이 놓인 아키텍처를 이해한다. 쓸 수 있는 도구(Read, Grep, Glob)로 탐색한다. 호출 체인을 따라간다. 타입을 읽는다. 변경이 올바른 층을 다루는지 판단하기 전에 그 코드가 왜 존재하는지 이해한다.

- 더 깊은 불변식 위반을 가리는 가드 절
- 깨진 계약을 숨기는 재시도 로직
- 모델링 오류를 침묵시키는 타입 캐스트
- 우회책이 보이면 묻는다. 왜 우회책이 필요한가? 제대로 고치면 어떤 모습인가?
- 사실은 모듈 B의 계약을 고쳐야 할 것을 모듈 A에서 고친 수정
- 구조가 나을 자리에 둔 지시: 수정이 "X를 하지 마라"는 주석이나 누군가 기억해야 하는 관례라면, 잘못된 것을 불가능하게 만드는 타입 제약, lint 규칙, 런타임 검사로 바꿀 수 있는지 묻는다

## 구조적 온전성

코드가 속한 시스템에 잘 맞는가?

- 경계 규율: 검증이 시스템 경계에 있는가, 비즈니스 로직 곳곳에 흩어져 있는가? 데이터는 시스템에 들어오는 곳에서 한 번 검증하고, 안에서는 믿는다.
- 추상화 수준: 고수준 조율과 저수준 세부가 섞여 있는가?
- 결합: 이 변경이 앞으로의 변경을 어렵게 할 의존성을 들여오는가?
- 데이터 모델 적합성: 데이터 구조가 실제 접근 패턴과 맞는가? 올바른 구조는 하류 코드를 뻔하게 만든다. 잘못된 구조는 매번 발목을 잡는다.
- 덧댄 것 대 녹아든 것: 변경을 기존 설계에 덧댔는가, 아니면 설계가 처음부터 그것을 고려한 것처럼 읽히는가? 새 요구 사항을 처음부터 알았다면 코드가 이런 모양이었겠는가?
- 레거시 이중 경로: 변경이 새 API를 들여오면서 옛 API를 살려 두는가? 외부 소비자가 없다면 같은 묶음 안에서 호출자를 옮기고 옛 경로를 지운다. 영구화될 호환 층을 남기지 않는다.

단순한 코드를 추상화가 없다고 깎아내리지 않는다. 섣부른 추상화는 중복보다 나쁘다.

## 검증

읽기만 해서 이 코드가 동작한다고 말할 수 있는가?

- 테스트가 있는가? 동작을 테스트하는가, 구현 세부를 테스트하는가?
- 회귀를 잡을 단언이나 불변식이 있는가?
- 버그 수정이라면 그 버그에 대한 테스트가 있는가?
- 통합 경계를 건드린다면 전체 경로를 테스트하는가?
- 대리 지표가 아니라 실물을 확인한다. 코드가 실제 값을 읽지 않고 파일 mtime이나 캐시된 상태로 생존을 확인한다면 검증 공백이다.
- 위임하거나 비동기로 돌린 작업이라면, 코드가 실제 출력 산출물을 확인하는가, 아니면 자가 보고와 요약을 믿는가?

## 복잡도 예산

코드가 이루는 것에 비해 복잡도가 정당한가?

- 정확성이나 명료함을 잃지 않고 더 단순해질 수 있는 코드
- 호출 지점 하나만 섬기는 추상화
- 아직 존재하지 않는 경우를 위한 설정이나 매개변수화
- 죽은 코드, 쓰지 않는 import, 흔적만 남은 매개변수
- 과잉 설계: 지금 호출자가 없는 "혹시 몰라" 코드 경로
- 더는 필요 없는 과도기 안정성 때문에 살려 둔 낡은 호환 경로. 마이그레이션이 끝났다면 비계를 지운다
- 사용자 경험이 그 복잡도를 정당화하는가? 모든 기능, 컨트롤, 옵션은 자리값을 해야 한다. 반쯤 만든 기능은 없는 기능보다 나쁘다.

틀리지 않는 한 단순한 쪽이 낫다. 세 줄 중복이 섣부른 추상화를 이긴다.

## 보안

보안 발견마다 코드 속 입력 경로를 추적해 보여 준다.

- 정화 없이 위험한 싱크(SQL, shell, eval, innerHTML)로 흘러가는 사용자 입력
- 새 엔드포인트의 인증·인가 공백
- 코드, 로그, 오류 메시지 속 비밀 값
- 보안에 중요한 경로의 TOCTOU(time-of-check-time-of-use, 확인 시점과 사용 시점의 차이)
