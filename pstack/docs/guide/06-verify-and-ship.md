# 결과 검증과 PR 열기

"컴파일된다"는 증거가 아니다. [Prove It Works 원칙](../../skills/principle-prove-it-works/SKILL.md)은 에이전트가 성공을 보고하기 전에 실제 산출물을 확인하게 만들고, 여러분의 일은 그 "실제 산출물"을 확인 가능하게 만드는 것이다. 이 페이지는 완료 조건을 밝히는 법, 측정한 숫자를 검증하는 법, 앱용 검증 스킬을 생성하는 법, 테스트가 좀처럼 닿지 못하는 속성을 형식 검증하는 법, PR을 여는 법, 그리고 PR을 머지까지 끌고 가는 법을 다룬다.

대부분의 에이전트 작업에서 검증은 가장 느린 단계다. 보통 사람을 기다리는 단계이기 때문이다. 에이전트가 검증을 할 수 있게 만들면 여러분이 병목에서 빠진다. 건너뛰면 에이전트를 더 돌려 봤자 리뷰할 미검증 작업만 늘어난다.

![시제품 비행기가 실제 시험 코스를 비행하고 그녀가 스톱워치로 시간을 재는 동안 로봇들이 비행을 촬영하고 체크리스트에 기록한다. 터미널에는 verify: pass, evidence: captured가 찍혀 있다.](./images/verification.jpg)

## 완료 조건을 미리 밝히기

완료가 무엇을 뜻하는지 첫 프롬프트에 어떤 말로든 적는다.

```text
/poteto-mode 이 명령에 JSON 출력을 추가해 줘. 텍스트 출력은 바이트 단위로 그대로고, JSON은 파싱돼야 하고, 둘 다 샘플 프로젝트에서 돌려 봐. 증거를 보여 줘.
```

이제 에이전트에게는 맞춰야 할 기분이 아니라 실행할 수 있는 검사 세 개가 있다. 답이 돌아오면 정확한 명령과 출력이 담겨 있어야 한다. 검사를 실행하지 못했다면 좋은 답은 "결론 없음(inconclusive)"이라고 말한다. 증거 없이 자신만만한 답은 경고 신호다.

검사는 변경에 맞춘다.

- CLI 변경은 실제 명령을 실행한다.
- UI 변경은 실행 중인 앱에서 바뀐 흐름을 따라가 본다. 레퍼런스와 픽셀 단위로 맞아야 한다면 [Visual parity 플레이북](../../skills/poteto-mode/playbooks/visual-parity.md)이 눈대중 대신 고정된 기준선과 스크린숏을 diff한다.
- 파서나 마이그레이션은 저장해 둔 입력을 다시 돌린다.
- 성능 변경은 전후 프로파일을 비교한다.
- 저장소 변경은 쓴 값을 다시 읽어 본다.

증명은 직접 들여다볼 수 있는 산출물로 요구한다. 실패하는 테스트와 이어서 통과하는 테스트, 전후 비디오, 트레이스, 스크린숏 같은 것이다. 수정이 이미 머지됐다면 main에서 같은 검사를 다시 요구한다. 그럴듯한 설명보다 산출물이 낫다. 실행 전체를 다시 돌리지 않고도 따져 물을 수 있기 때문이다.

완전히 믿기 어려운 작은 diff라면 [`/blast-radius`](../../skills/blast-radius/SKILL.md)가 그것이 다른 곳에서 무엇을 깨뜨릴 수 있는지 찾는다. 변경을 안전하게 만드는 사실 하나를 찾아, 그 사실을 말로 옹호하지 않고 코드를 실행해 증명한다.

## `/benchmark-checklist`로 측정한 숫자 검증하기

전후 숫자는 실수로 틀리기 가장 쉬운 증거다. 데워진 캐시, 한쪽만 디버그 빌드, 측정 구간 안에서 실제로 돌지 않은 작업 하나만으로도 그럴듯한 속도 향상이 나온다. 숫자를 보고하거나 그에 따라 움직이기 전에 다음을 입력한다.

```text
/benchmark-checklist 내보내기 속도 개선을 PR에 넣기 전에 검증해 줘
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md)는 질문 일곱 개를 던지고, 각각에 대해 실행에서 나온 증거를 요구한다.

1. 무엇이 이 숫자를 제한하며, 왜 두 배가 아닌가?
2. 모든 쪽이 프로덕션과 같은 튜닝으로 돌았는가?
3. 결과가 디스크 대역폭이나 코어 수 같은 물리적 한계를 넘는가?
4. 오류가 나거나 틀린 출력을 낸 것이 있는가?
5. 번갈아 돌린 실행에서 중앙값과 범위와 함께 재현되는가?
6. 사용자가 기다리는 경로에서 처음부터 끝까지 의미가 있는가?
7. 작업이 정말 측정 구간 안에서 일어났는가?

판정은 빨라짐, 느려짐, 측정 가능한 차이 없음, 결론 없음 중 하나로 돌아오며, 실행 횟수와 범위와 제한 요인이 함께 붙는다. 제한 요인을 대지 못하거나 한쪽이 튜닝 없이 돌았으면 결론 없음이라고 말한다. `/poteto-mode`는 Perf issue와 Hillclimb 플레이북 안에서 이미 이 체크리스트를 돌린다. 그러니 그 밖에서 무언가를 측정했거나 남의 숫자가 너무 좋아 보일 때 직접 입력한다. [Explain the Number 원칙](../../skills/principle-explain-the-number/SKILL.md)을 실제로 돌아가게 만든 형태다.

## 프로젝트 검증 스킬 만들기

위의 UI 항목에는 실제 요구 사항이 숨어 있다. 에이전트에게는 앱을 스크립트로 조작할 방법이 필요하다. 프로젝트에 이미 있다면 좋다. 없다면 다음을 실행한다.

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md)은 여러분이 아니라 저장소를 인터뷰한다. 사용자가 무엇을 만지는지, 앱이 로컬에서 어떻게 실행되는지, 무엇으로 앱을 조작할 수 있는지(기존 하네스가 우선이고, 없으면 브라우저와 CDP, PTY, 평범한 HTTP), 어떤 증거가 동작을 증명하는지, 두 인스턴스를 나란히 돌릴 수 있는지 알아낸다. 코드가 답할 수 없는 것만 여러분에게 묻는다.

결과로 `.cursor/skills/verify-<app>/`를 쓴다. 에이전트용 지시로, 정확한 Launch, Doctor, Drive, Evidence, Cleanup 섹션과 함께 넣는 스크립트를 설명하는 Helpers 섹션을 담고, `features/` 아래에 기능 맵(feature map)을 둔다. 기능 맵은 앱이 하는 일과 각 기능이 동작함을 증명하는 결과를 색인한다. 이 스킬에는 README 색인과, 필수 H2 네 개를 쓴 기능별 파일로 이루어진 [기능 맵 작성 예시](../../skills/create-verification-skill/references/feature-map-example/)가 함께 들어 있다. 생성기는 넘겨주기 전에 스킬을 처음부터 끝까지 한 번 증명한다. 실행, doctor 검사, 기능 하나 조작, 증거 수집, 정리, 그리고 정리 뒤에도 증거가 남았는지 확인. 이 증명이 실패하면 출력을 쓰지 않는다.

그때부터 "앱에서 검증해"는 이 저장소에서 어떤 에이전트든 설정 대화 없이 실행할 수 있는 단계가 된다. 증명을 특정한 형태로 받고 싶다면 프롬프트에서 이름을 부른다.

```text
/poteto-mode 일괄 보관 기능을 만들어 줘. /verify-<app> 으로 변경을 검증하고 증거로 영상과 스크린샷을 보여 줘.
```

```text
/poteto-mode /verify-<app> 으로 이거 재현해 줘. main에서도 재현되면 고치고 증거로 영상을 보여 줘.
```

검증 스킬이 동작하면 [`/swarm`](../../skills/swarm/SKILL.md)이 전체 검증을 기능 맵 항목별로 나누고 결과를 모을 수 있다. 검증자 swarm은 충분히 큰 표본으로 성능 개선을 확인하거나, PR이 나가기 전에 앱을 퍼징해 회귀를 찾기도 한다.

검증 스킬은 일회용이 아니라 인프라로 다룬다. 커밋해 두면 팀의 모든 사람과 모든 에이전트가 같은 방식으로 앱을 조작한다. 그다음 [지렛대를 만든다](../../skills/principle-build-the-lever/SKILL.md). 에이전트가 앱을 클릭해 보려고 일회용 스크립트를 자꾸 쓴다면, 스킬이 대신 호출할 작은 제어 CLI를 요청한다. 에이전트는 토큰을 덜 쓰고, 모든 실행이 반복 가능해진다. 에이전트가 잘 쓰는 CLI에는 이런 특징이 있다.

- 얇은 명령 여러 개보다, 각자 실제 일을 하는 조합 가능한 명령 몇 개.
- 파괴적인 작업마다 붙은 `--dry-run` 옵션.
- 기능을 한꺼번에가 아니라 차근차근 드러내는 하위 명령.
- 대신 무엇을 하라고 알려 주는 오류 메시지.
- 충실한 `--help` 텍스트.
- JSON 같은 기계가 읽을 수 있는 출력.

하는 김에 개발 환경 설정도 반복 가능하게 만든다. 시드 데이터, 테스트 사용자, 매번 같은 방식으로 환경을 띄우는 명령 하나.

## 검증 스킬을 정직하게 유지하기

앱은 바뀌고, 기능 맵은 앱과 어긋나게 된다. 적어도 하루에 한 번 다음을 실행한다. 아무도 기억할 필요가 없도록 예약된 자동화에서 돌리면 가장 좋다.

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)은 생성된 스킬을 감사한다. 기능마다 읽기 전용 소스 리더를 하나씩 병렬로 돌린 뒤, 매핑된 모든 기능을 조작하는 실제 검증을 한 번 돌린다. 결과는 세 가지 중 정확히 하나다. `clean`은 커버리지가 완전하고 내보낼 것이 없다는 뜻이다. `changed`는 검증 스킬 자체 디렉터리 안으로 한정된, 증명된 수정 PR 하나를 뜻한다. `blocked`는 막는 요인을 밝힌다. 제품 코드는 절대 고치지 않는다. 실제 검증에서 제품 회귀를 잡으면 문서를 고쳐 감추지 않고 회귀를 보고한다.

## 형식 검증 스킬로 속성 증명하기

검증 스킬은 조작하는 경로를 증명한다. 어떤 버그는 아무도 조작하지 않는 경로에 산다. 겹치는 재시도 두 번, 쓰는 도중에 만료되는 락, 순서가 어긋나 도착하는 상태 변경이 그렇다. 테스트는 그런 경우에 좀처럼 닿지 못한다. 그런 버그의 대가가 큰 코드라면 다음을 돌린다.

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md)은 코드에서 대상을 고른다. 코드가 하는 약속 가운데, 깨지면 사용자가 피해를 보고 그것을 깨뜨리는 경우에 테스트가 좀처럼 닿지 못하는 약속이다. 검증하기 가장 쉬운 대상이 아니라 가장 강한 대상을 고른다. 다른 곳에서 시작하려면 영역이나 버그를 지목한다.

```text
/create-formal-verification-skill 작업 lease와 재시도 로직. 작업 하나가 동시에 두 번 돌면 절대 안 돼.
```

질문이 도구를 고른다. 사건이 나쁜 순서로 일어날 수 있는지는 설계를 작게 모델링해 모델 검사기로 확인하는 편이 맞고, 언어와 상관없이 TLA+가 기본이다. 코드가 모든 입력에서 제대로 동작하는지는 코드 위에서 도는 검증기가 맞다. 내 언어에서 도는 검증기가 없으면 에이전트가 그렇다고 말하고, 함수를 손으로 모델링하는 대신 생성한 입력으로 실제 코드를 테스트한다. 모든 크기에서 성립해야 하는 속성에는 증명이 필요할 수 있다. 에이전트는 어떤 도구를 왜 골랐는지 알려 준다.

속성 하나를 검증하고, 코드를 망가뜨린 변형에서 그 속성이 실패하는 것을 보여 준다. 한 번도 실패하는 것을 보지 못한 검사는 아무것도 증명하지 않기 때문이다. 현재 코드가 이미 속성을 깨면 코드의 용어로 쓴 짧은 단계 순서로 반례를 받는다. 속성은 밝힌 그대로 두므로 발견은 발견으로 남는다. 요청하지 않으면 제품 코드는 바뀌지 않는다.

결과로 프로젝트 로컬 스킬을 쓴다. 다음 에이전트는 이 스킬로 변경이 검증한 코드를 건드리는지, 명령 하나로 검사를 어떻게 돌리는지, 진짜 버그와 모델링 오류를 어떻게 구분하는지 안다. 생성기는 넘겨주기 전에 속성을 깨뜨리는 임시 변경에서 그 스킬을 한 번 따라가고, 검사는 그 깨짐을 잡아야 한다. 넘길 때는 무엇을 어떤 도구와 한계로 검증했는지, 검사가 무엇을 찾았는지, 무엇을 다루지 않는지 말한다. 통과는 시스템 전체가 아니라 모델이나 한계 안을 보증한다.

스킬은 각 검사가 다루는 코드와, 검사가 그 코드와 마지막으로 맞았던 커밋도 기록한다. 스킬을 거치지 않은 머지와 리팩터링 뒤에는 이미 사라진 코드의 설명 위에서 검사가 계속 통과할 수 있다. 그런 변경 뒤에는 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)을 돌린다. 코드를 보고 검증을 고치고, 다시 돌리고, 고친 검사마다 여전히 실패할 수 있음을 보여 주고, 실패마다 검증이 어긋난 것인지 코드의 버그인지 알려 준다.

## PR 열기

```text
/poteto-mode PR 열어 줘. 커밋은 작게 순서대로, 증거는 설명에 넣어.
```

[PR 열기 플레이북](../../skills/poteto-mode/playbooks/opening-a-pr.md)은 worktree에서 작업하고, 작업을 작고 순서 있는 커밋으로 rebase하고, diff를 정리하고, 산문을 unslop하고, PR 링크를 돌려준다. 뚱뚱한 PR 하나보다 좁은 PR 다섯 개가 낫고, 자라나는 브랜치보다 쌓아 올린 후속 PR이 낫다.

## Babysit으로 PR을 머지 가능 상태까지 끌고 가기

열린 PR은 곧바로 걸림돌을 모으기 시작한다. 검사가 실패하고, 리뷰어가 코멘트를 달고, trunk가 움직인다. 이 잡일은 [Babysit 플레이북](../../skills/poteto-mode/playbooks/babysit.md)에 맡긴다.

```text
/poteto-mode 이 PR 지켜봐 줘. 초록불 될 때까지.
```

Babysit은 PR을 지켜보며(GitHub에서는 번들된 watcher로, 쓸 수 있으면 Origin CLI로) 걸림돌을 순서대로 처리한다. 충돌, 리뷰 스레드, CI 순이다. 알려진 수정은 모두 한 번의 push로 묶어, 수정할 때마다가 아니라 한 번만 검사가 다시 돈다. 코멘트 분류는 회의적이다. 사람과 봇이 진짜 지적과 잡음을 같은 목록에 올리기 때문이다. 진짜 지적에는 수정이 들어가고, 잡음은 반증을 스레드에 남기고 기각한다. 상태만 알고 싶다면 작게 물어본다. 그러면 Babysit은 루프를 시작하지 않고 답한다.

```text
/poteto-mode PR 123 상태 확인해 줘. 남은 거 있어?
```

Babysit은 머지 가능 상태에서 멈춘다. 모든 것이 초록이어도 머지하지 않는다. 머지는 다른 결정이기 때문이다.

## Shipping으로 스택 착지시키기

초록이 안전과 같지는 않다. 착지할 준비가 되면 그렇게 말한다.

```text
/poteto-mode 스택 랜딩해 줘.
```

[Shipping 플레이북](../../skills/poteto-mode/playbooks/shipping.md)은 무엇이든 무장하기 전에 각 PR을 독립적으로 검증한다. PR마다 새 에이전트 하나가 동작을 실제로 증명하며, 변경을 판정하는 에이전트는 결코 그 변경을 쓴 에이전트가 아니다. 그런 다음 Shipping은 맨 아래부터 연속으로 검증된 구간만 착지시킨다. 기본은 GitHub를 통해, CLI가 있으면 Origin을 통해 PR을 하나씩 처리하고, 연쇄를 끊는 첫 PR을 보고한다. 검증되지 않은 PR 위에 놓인 검증된 PR은 기다린다. 그것을 머지하면 빈틈이 그 아래로 딸려 들어가기 때문이다.
