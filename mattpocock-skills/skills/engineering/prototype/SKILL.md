# 프로토타입

프로토타입은 **질문 하나에 답하고 버리는 코드**다. 어떤 질문인지에 따라 형태가 정해진다.

## 갈래 고르기

어떤 질문에 답하려는지 파악한다. 사용자의 프롬프트와 주변 코드를 보고, 사용자가 자리에 있으면 직접 묻는다.

- **"이 로직이나 상태 모델이 맞는가?"** → [LOGIC.md](LOGIC.md). 공유할 수 있는 HTML 파일 하나(자유롭게 누르는 버튼과 탭으로 나뉜 단계별 시나리오)를 만든다. 이 파일은 종이 위에서 따져 보기 어려운 경우들로 상태 기계를 실제로 돌려 보게 하고, 개발자가 아닌 사람도 직접 조작할 수 있어야 한다.
- **"이게 어떤 모습이어야 하는가?"** → [UI.md](UI.md). 한 라우트 안에 서로 완전히 다른 UI 변형을 여러 개 만들고, URL 검색 파라미터와 화면 아래에 떠 있는 막대로 전환하게 한다.

갈래마다 만드는 산출물이 전혀 다르므로, 갈래를 잘못 고르면 프로토타입 전체가 헛수고가 된다. 질문이 정말로 모호하고 사용자에게 물을 수 없으면 주변 코드에 더 맞는 갈래를 기본으로 고른다(백엔드 모듈이면 로직, 페이지나 컴포넌트면 UI). 그리고 그렇게 가정했다는 사실을 프로토타입 맨 위에 적는다.

## 두 갈래에 모두 적용하는 규칙

- **처음부터 버릴 코드로 만들고, 그렇다는 것을 분명히 표시한다.** 프로토타입 코드는 실제로 쓰일 곳 가까이(프로토타입 대상인 모듈이나 페이지 옆)에 두어 맥락이 바로 보이게 한다. 다만 이름을 붙일 때는 대충 훑어보는 사람도 운영 코드가 아니라 프로토타입임을 알 수 있게 한다. 일회용 UI 라우트는 프로젝트가 이미 쓰는 라우팅 규칙을 따른다. 새 최상위 구조를 만들지 않는다.
- **실행하기 쉽게 만든다.** UI 프로토타입은 프로젝트 작업 실행 도구의 명령 하나로 시작한다. `pnpm <name>`, `python <path>`, `bun <path>` 같은 식이다. 로직 데모는 사용자가 더블클릭해서 여는 HTML 파일 하나다. 어느 쪽이든 시작할 때 고민할 것이 없어야 한다.
- **기본적으로 데이터를 저장하지 않는다.** 상태는 메모리에만 둔다. 저장은 프로토타입이 _확인하는_ 대상이지 프로토타입이 기대야 할 기능이 아니다. 질문이 명시적으로 데이터베이스를 다룬다면 임시 DB나 로컬 파일을 쓰고, "PROTOTYPE, wipe me"(프로토타입이니 지워도 된다)처럼 분명한 이름을 붙인다.
- **다듬지 않는다.** 테스트를 쓰지 않고, 프로토타입을 _실행할 수 있게_ 하는 데 필요한 것 이상의 오류 처리를 넣지 않고, 추상화를 만들지 않는다. 목적은 빨리 무언가를 알아내는 것이다.
- **상태를 보여 준다.** 동작을 실행할 때마다(로직) 또는 변형을 바꿀 때마다(UI) 관련 상태 전체를 출력하거나 화면에 그려서, 무엇이 바뀌었는지 사용자가 볼 수 있게 한다.
- **끝나면 기록으로 남긴다.** 검증된 결정은 실제 코드에 반영한다. 그다음 프로토타입 자체를 **1차 자료**(가공하지 않은 원본 자료)로 남긴다. main에 합치지 않는 보관용 브랜치에 커밋하고, 구현 이슈에 그 브랜치를 가리키는 컨텍스트 포인터(컨텍스트 밖 자료를 가리키고 언제 읽을지 조건을 담은 짧은 참조)를 남긴다. 답(결론과 그 결론이 해결한 질문)도 이슈나 커밋에 기록한다. main 브랜치에는 검증된 결정만 남긴다.
