# Emil에게 묻기

스킬이 하는 일을 설명하거나 추천하기 전에 그 스킬의 SKILL.md를 읽는다. 여기 적은 요약은 방향을 잡는 용도일 뿐이다. 그다음 사용자 상황에 맞는 스킬을 **하나**(또는 짧은 순서 하나) 추천하고, 이유를 한 문장으로 말하고, 그다음에 쓸 스킬을 알려 준다. 지도 전체를 다시 늘어놓지 않는다.

**흐름**은 스킬을 지나가는 경로다. 대부분의 UI 작업은 아이디어에서 출시까지 이어지는 **주 흐름** 하나를 따른다. 어떤 스킬은 이미 있는 코드베이스에 돌리는 **유지 관리**용이고, 어떤 스킬은 모든 것의 바탕이 되는 **참조**이고, 몇 개는 따로 쓴다.

## 주 흐름: 아이디어 → 출시

1. **어떤 모습이나 느낌이어야 할지 모르겠다면** **`/prototype`** 을 먼저 거쳐 간다. 확실히 다른 여러 버전을 실시간 선택기 뒤에 만들고, 고른 버전을 실제 코드로 옮긴다. 말로 정하기 어려운 디자인 질문이 있을 때마다 쓴다.

2. **만든다.** 무엇이 움직이는지에 따라 만드는 스킬을 고른다.
   - 작업에 의존성(드롭다운, 다이얼로그, 토스트, 드로어, 커맨드 메뉴, 드래그 앤 드롭, 차트)이 필요하면 먼저 **`/pick-ui-library`**. 에이전트가 토스트를 직접 짜게 두지 않는다.
   - 웹 애니메이션 하나에는 **`/animate`**. 애니메이션을 넣을지부터 정하고 도구, 속성, 곡선, 지속 시간, 중단, 퇴장을 정한다.
   - 여러 요소가 함께 움직이면 **`/choreograph`**. 스태거, 히어로 등장, 뷰 전환, 항목이 빠지면서 형제 요소가 틈을 메우는 경우다.
   - 사용자의 손가락이 움직임을 이끌면 **`/gestures`**. 드래그, 스와이프, 시트, 스냅 포인트, 스와이프해서 닫기다.
   - 위의 무엇이든 React Native나 Expo에서 하면 **`/animate-expo`**.
   - Sonner로 토스트를 다루면 **`/ask-sonner`**.

3. **깨뜨려 본다.** 끝났다고 하기 전에 한다.
   - **`/break-ui`** 는 최악의 데이터(긴 이름, 빈 목록, 아주 큰 개수, 이모지, 라틴 문자가 아닌 텍스트)를 토글 뒤에 넣고 무엇이 깨졌는지 보고한다.
   - **`/review-animations`** 는 diff의 모션을 엄격한 기준으로 리뷰한다. 기본은 지적하는 것이고 통과는 얻어 내야 한다.
   - 휴대폰에서 웹 앱으로 돈다면 **`/mobile-native`**. 남아 있는 hover, 100vh 버그, 확대되는 입력 필드, 안전 영역을 다룬다.
   - 프레임이 떨어지는 곳이 있으면 **`/animation-performance`**.

4. **세션에서 배운다.** **`/learn-taste`** 가 고리를 닫는다. 같은 세션 끝에, 대화를 지우기 전에 돌린다. 직접 고친 편집까지 포함해 세션에서 한 디자인 교정을 모두 모으고, 하나하나를 이유가 붙은 규칙으로 바꿔서 다음 에이전트가 같은 실수를 하지 않게 한다.

## 유지 관리: 이미 있는 코드베이스

기능 작업이 아니다. 시간이 날 때나 앱이 "어딘가 이상하게 느껴질" 때 돌린다.

- **앱 전반의 모션을 손봐야 한다** → **`/improve-animations`**. 읽기만 한다. 모든 애니메이션을 점검하고, 다른 에이전트(또는 더 저렴한 모델)가 실행할 수 있는 우선순위가 매겨진 그 자체로 완결된 계획을 쓴다.
- **정적으로 느껴진다** → **`/find-animation-opportunities`**. 읽기만 한다. 정확한 값과 함께 모션을 제안하고 움직이지 말아야 할 것은 모두 걸러 낸다. 받아들인 제안은 `/animate` 로 만든다.
- **느리거나 애니메이션이 과하게 느껴진다** → **`/remove-animations`**. 코드를 고치지만 빼기만 한다. 키보드 동작에 붙은 모션, 자주 쓰는 화면의 모션, 목적 없는 장식을 지운다.

셋은 서로 다른 질문을 다룬다. 사용자가 어느 쪽인지 모르겠다면 문제가 *나쁜* 모션인지, *없는* 모션인지, *너무 많은* 모션인지 묻는다.

## 바탕이 되는 참조

다른 스킬이 기대는, 모델이 호출하는 스킬이다. 빠진 것이 절차가 아니라 **지식**일 때 바로 쓴다.

- **`/emil-design-eng`**: UI 완성도, 컴포넌트 상호작용, 보이지 않는 디테일을 다루는 핵심 철학이다. 더 좁은 스킬이 맞지 않을 때 기대는 기본값이다.
- **`/apple-design`**: 인터페이스 디자인과 유려하고 물리적인 모션에 관한 Apple의 원칙을 웹에 맞게 옮긴 것이다.
- **`/animation-vocabulary`**: 문제가 **단어**일 때 쓴다. "…하는 걸 뭐라고 하지?" 같은 막연한 묘사를 프롬프트에 넣을 정확한 용어로 바꾼다.

## 따로 쓰는 스킬

- **`/write-swift`**: 모던 Swift, Swift 6 동시성, 네이티브 iOS 코드. 웹 흐름과는 아예 별개다.
