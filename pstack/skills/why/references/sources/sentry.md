# Sentry 에러 기록

## 검색 방법

Sentry MCP를 쓴다.

1. **지형을 파악한다.** 프로젝트 slug와 조직을 모른다면 다음을 쓴다.

   ```
   find_organizations
   find_projects
   ```

2. **대상과 관련된 이슈를 검색한다.**

   ```
   search_issues (자연어. 예를 들어 "PaymentService 타임아웃 오류", "uploadFile의 처리되지 않은 예외")
   ```

   쿼리는 대상이 처리하는 예외 클래스 이름, 대상의 함수나 클래스 이름, 대상이 검사하는 에러 메시지 문자열, 대상의 파일 경로로 만든다.

3. **릴리스와 시간 구간으로 좁힌다.**

   ```
   search_issue_events (릴리스, 시간, 환경, trace ID, 태그로 거른다)
   get_issue_tag_values (이슈 하나의 버전, 사용자, 환경별 분포를 본다)
   ```

   의심 가는 이슈가 있으면 **처음 관측**과 **마지막 관측**(멈춘 시점이 대상의 출시일과 맞아떨어지나?), **영향받은 릴리스**(어느 버전에서 나타났고 어느 버전이 고쳤나?), **빈도 궤적**(치솟았다가 해결됐나?)을 확인한다.

4. **맥락을 보려고 이벤트 전체를 가져온다.**

   ```
   get_sentry_resource (Sentry URL이나 type+ID를 넘긴다)
   ```

   스택 트레이스가 대상 코드를 지나가는가? 태그와 breadcrumb가 대상이 방어하는 조건과 맞는가?

5. **대상 근처에 반영된 릴리스를 확인한다.**

   ```
   find_releases (대상 커밋 날짜 전후)
   ```

   릴리스 버전을 PR 머지 날짜와 대조한다.

6. **Seer는 아껴 쓴다.**

   ```
   analyze_issue_with_seer
   ```

   Seer의 AI 근본 원인 분석은 가설 생성기다. 권위 있는 답이 아니라 추론으로 다룬다. 1차 증거는 실제 이벤트와 스택 트레이스다.

## 돌려줄 것

관련 이슈마다 다음을 적는다.
- 이슈 ID와 제목
- 프로젝트와 조직
- 처음·마지막 관측 타임스탬프
- 이벤트 건수(알면 샘플링 비율도)
- 영향받은 릴리스
- 대상과의 관련성을 보여 주는 대표 스택 트레이스 조각(요약이 아니라 원문 발췌)
- 처음·마지막 관측과 대상 출시일의 상관관계
- 이슈 링크
- 작성자 댓글이나 해결 메모
