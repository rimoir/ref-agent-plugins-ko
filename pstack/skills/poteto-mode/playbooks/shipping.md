### Shipping

**머지되는 것은 네 책임이다. PR마다 따로 검증하고, 루트에서부터 검증된 구간만 머지한 뒤 스택에서 손을 뗀다.**

1. **forge를 정한 뒤, 머지 전에 PR마다 따로 검증한다.** 기본은 GitHub CLI(`gh`)다. `command -v origin`이 성공하고 Origin이 레포를 찾을 수 있으면 모든 PR 작업에 `origin pr`을 쓴다. 그렇지 않으면 `gh`를 쓰고 대체했다는 사실을 기록한다. Graphite(`gt`)를 요구하지 않는다. PR마다 검증자 하나를 두며, 각각 Cursor 클라우드 에이전트다. 검증자는 맞는 control skill(`cursor-team-kit`의 `control-ui`나 `control-cli` 등)로 사용자가 하듯 변경을 parent와 head에서 돌려 보고, 그 PR에 `PASS`, `PASS+NOTES`, `FAIL`을 올린다. 코드를 쓰지 않은 에이전트의 판정만 인정한다. 작성자는 자기가 만들려던 것을 확인하기 때문이다. CI 통과와 승인한 봇 리뷰는 판정이 아니다. 둘 다 사용자가 하듯 변경을 돌려 보지 않기 때문이다.
2. **맨 아래에서 시작해 끊김 없이 검증된 구간만 머지한다.** 머지되지 않은 가장 아래 PR부터 위로 올라가다가 `PASS`나 `PASS+NOTES`가 없는 첫 PR에서 멈춘다. 그 아래 PR들이 구간이고, 맨 위가 상한선(ceiling)이다. 검증되지 않은 PR 위에 있는 검증된 PR은 기다린다. 아래 코드 없이는 머지할 수 없기 때문이다. 브랜치가 그 코드를 담고 있지도 필요로 하지도 않는 PR은 trunk 위로 옮겨 따로 머지할 수 있다. 다만 먼저 새 판정을 받아야 한다. 예전 판정은 그 코드를 밑에 두고 돌았는데 trunk에는 그 코드가 없기 때문이다.
3. **판정이 여전히 그 코드를 설명하는지 다시 확인한다.** 판정은 패치를 덮는다. 사슬을 rebase하면 그 위의 모든 PR이 검사 하나 실패하지 않은 채 새 SHA로 옮겨진다. 예전 판정을 믿기 전에 판정 SHA와 현재 head의 `git patch-id`를 비교한다. 두 패치가 테스트, 문서, lint 설정만 다르면, 레인이 돌린 것이 두 SHA에서 소음을 빼고 똑같이 빌드될 때 그 레인의 결과는 유지된다. 소음은 판정 SHA를 두 번 빌드했을 때도 나타나는 차이거나 내장된 커밋 SHA다. 읽는 사람이 판단을 확인할 수 있게 소음의 종류마다 해당 파일과 함께 보고한다. 변경 자체는 여전히 새 검사와 리뷰를 받는다. 예전 판정은 그 변경을 본 적이 없기 때문이다. dev 서버처럼 빌드 산출물이 없는 레인은 이것을 보일 수 없으니 다시 돌리고, 그 밖에 어긋난 것은 모두 다시 검증한다.
4. **아래에서 위로, 한 번에 PR 하나씩 머지한다.** 언제나 구간에서 머지되지 않은 가장 아래 PR을 `origin pr merge <pr>`나 `gh pr merge <pr> --squash`로 머지한다. Origin에서는 일반 명령이 지정한 PR 아래의 모든 PR도 함께 머지하고, GitHub에서는 base가 아직 부모 브랜치인 PR이 trunk가 아니라 그 브랜치로 머지된다. 결과는 PR을 다시 읽어 확인한다(`origin pr view <pr>`나 `gh pr view <pr> --json state,mergedAt,baseRefName`). 머지 큐가 PR을 큐에 넣기만 했는데도 머지 명령이 성공을 보고할 수 있고, 요청한 auto-merge는 머지가 아니기 때문이다. 머지된 PR은 merged 상태이고 base가 부모 브랜치가 아니라 trunk로 읽힌다. `--auto`(Origin merge-when-ready나 GitHub auto-merge)는 판정이 현재 head를 덮는 PR에만 건다. 준비된 head라면 무엇이든 머지하기 때문이다. 머지가 끝나면 머지된 브랜치를 base로 두던 PR의 대상을 trunk로 바꾸고(`origin pr edit <pr> --base <trunk>`나 `gh pr edit <pr> --base <trunk>`), 그 패치를 머지 결과 위로 옮긴 뒤 `--force-with-lease`로 push한다. 판정은 커밋이 아니라 패치를 덮으므로, 판정이 살아남는지는 3단계의 patch-id 규칙이 정한다. 검사가 통과하고 판정이 살아남으면 머지한다.
5. **머지되는 동안 스택을 건드리지 않는다.** 4단계에서 다음 PR을 옮기는 것만이 브랜치나 base를 바꾸는 유일한 변경이다. 머지는 판정이 있든 없든 그 순간 브랜치와 base에 담긴 것을 반영하기 때문이다. GitHub에서는 `scripts/watch-pr/watch-pr --queued-stack`을 `/loop` 아래에서 돌려, 상한선에서 `COMPLETE`를 보고할 때까지 구간을 지켜본다. 이번 구간의 PR 번호를 아래에서 위 순서로 `--stack-prs`에 넘기고, 감시자를 다시 시작할 때마다 같은 목록을 넘긴다. Origin에서는 `origin pr checks <pr> --watch`가 돌아올 때마다 `origin pr view <pr> --checks`로 현재 PR을 다시 읽어, 상한선이 merged로 읽힐 때까지 지켜본다. 부모가 머지될 때 base가 trunk로 옮겨지는 것은 예상된 일이지 고쳐야 할 손상이 아니다. 머지가 멈추면 무엇이든 바꾸기 전에 이유부터 알아낸다.
6. **상한선에서 멈춘다.** 구간을 늘리려면 새 판정이 필요하므로 1단계부터 새로 진행한다.

**답변:** 검증된 구간과 그 상한선, 각 PR의 판정과 판정한 주체, 무엇이 머지되었고 어떻게 확인했는지, 다음 빈틈에 무엇이 필요한지.
