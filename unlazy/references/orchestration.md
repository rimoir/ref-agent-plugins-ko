# 오케스트레이션 모드

컨텍스트 하나로 작업과 그 검증을 온전한 주의력으로 감당할 수 없을 때 오케스트레이션 모드를 쓴다. 오케스트레이션 모드는 총괄 에이전트가 리프(leaf, 트리 맨 아래의 작업 단위)를 여러 에이전트에 나눠 맡기고 검증과 통합을 하는 방식이다. 계획, 배정(dispatch), 독립 검증, 통합, 루트 보고는 계속 총괄 에이전트가 맡는다.

## 상태와 경로 선언하기

리프 상태는 아래 값만 쓴다.

- `WAITING`: `Needs`에 있는 id 가운데 하나 이상이 아직 `VERIFIED`가 아니다.
- `READY`: 의존성이 검증되었고 소유권을 잡을 수 있다.
- `IN-FLIGHT`: 배정했지만 아직 독립 검증을 거치지 않았다.
- `VERIFIED`: 부모 재검증을 통과했고 수동 게이트 검토를 마쳤다(게이트는 완료로 인정하려면 충족해야 하는 조건 한 항목이다).
- `ABANDONED`: 필수 게이트 가운데 적어도 하나에 인계가 기록되어 있다. 이 상태를 완전한 완료로 취급하지 않는다.

중간 노드(branch)에는 `OPEN`, `VERIFIED`, `ABANDONED`를 쓴다. 리프 게이트 파일은 `gates/leaf-<id>.md`로, 통합용 중간 노드 게이트 파일은 `gates/node-<id>.md`로 저장한다. 중간 노드 경로에 `leaf-*` 이름을 붙이지 않는다.

## 총괄 에이전트 절차

1. **분산 배정 전에 계획한다.** 원래 요청과 현재까지의 변경 사항을 다시 읽는다. 템플릿으로 `.unlazy/<scope>/PLAN.md`, `.unlazy/<scope>/GATES.md`, 그리고 리프와 중간 노드마다 게이트 파일을 하나씩 만든다. 따로 빠뜨릴 수 있는 결과와 완료 판정 기준을 바꾸는 제약을 빠짐없이 목록에 적고, 항목마다 고정된 id, 담당, 확인 게이트나 수동 검토, 처리 상태, 개정 번호를 붙인다. 배정 전에 인터페이스, 이름 규칙, 툴체인, 의존성, 정확한 소유권을 확정한다.
2. **검사를 살펴보고 승인한다.** 물려받은 게이트 파일마다 `gate-check --status`를 실행한다. `CHECK:`, `EXPECT:`, `CWD:`를 하나하나 검토하고, 호출되는 스크립트까지 본다. 셸과 물려받은 `PATH`를 확인한다. 정확히 일치하는 승인이 없는 새 판정 기준(oracle)은 일반 실행에서 실행되지 않고 해석된 값만 출력한다. `--approve`는 검토를 마친 뒤에만 쓰고, 승인이 생긴 뒤에는 일반 실행을 모의 실행으로 여기지 않는다.
3. **동시에 실행할 리프마다 점유(lease)를 신청한다.** 다음을 실행한다.

   ```text
   node <skill-dir>/scripts/gate-check.mjs --scope <scope> --leaf leaf-1.2.1 --claim
   ```

   점유 신청(`--claim`)이 거부되면 그 분할은 동시 배정에 안전하지 않다는 뜻이다. 계획을 바꾸거나 작업을 순차로 실행한다. 거부를 절대 우회하지 마라.
4. **준비된 실행 묶음마다 실행을 시작한다.** 각 리프에는 공유 계약, 그 리프의 정확한 소유권과 의존성, 그 리프의 게이트 파일, 회차별 완료 규칙만 넘긴다. 독립된 `READY` 리프들로 실행 묶음(wave)을 열고, 리프마다 호스트의 네이티브 비차단 실행 시작을 한 번씩 호출하고, 호스트 핸들을 모두 기록하고, 처음 기다리거나 결과를 읽기 전에 실행 묶음을 확정(`seal`)한다. [dispatch.md](dispatch.md)를 따른다. 관련 없는 리프의 이력을 다른 리프에 넘기지 않는다.
5. **반환된 리프마다 독립적으로 검증한다.** 네이티브 반환을 해당 실행 묶음에 기록한 뒤, 반환된 리프의 실행 게이트를 이미 체크된 게이트까지 포함해 다시 실행해 재검증(`--reverify`)한다.

   ```text
   node <skill-dir>/scripts/gate-check.mjs --root . --cwd . --reverify .unlazy/<scope>/gates/leaf-1.2.1.md
   ```

   `--status`만으로는 재검증이 아니다. 승인된 판정 기준이 바뀌었으면 계속하기 전에 그것을 검토하고 새 판정 기준을 승인한다. 수동 게이트는 직접 검토하고, 통과한 게이트 가운데 적어도 하나는 반박을 시도한다.
6. **상태를 덧붙이고 다음 리프로 넘어간다.** 기존 기록을 고쳐 쓰지 않고 결과를 기록한다.

   ```text
   node <skill-dir>/scripts/gate-check.mjs --scope <scope> --log "leaf-1.2.1 verified"
   ```

   리프를 `VERIFIED`로 표시하고, 바로 그 리프의 점유를 해제(`--release`)하고, 승격(WAITING에서 READY로 올림)하기 전에 해제를 기록한다.

   ```text
   node <skill-dir>/scripts/gate-check.mjs --scope <scope> --leaf leaf-1.2.1 --release
   node <skill-dir>/scripts/gate-check.mjs --scope <scope> --log "leaf-1.2.1 lease released"
   ```

   그다음에야 새로 대기가 풀린 리프를 `WAITING`에서 `READY`로 승격하고, 관련 없는 진행 중인 리프를 기다리지 않고 배정한다.
7. **아래에서 위로 통합한다.** 각 `node-*.md` 게이트 파일은 이름이 적힌 자식이 모두 반환된 뒤에만 작업한다. 자식들을 재검증한 뒤 인터페이스, 엔드투엔드, 회귀 검사를 실행한다.
8. **대조해 맞추고, 해제하고, 보고한다.** 현재 요청을 다시 읽고 현재 계약 행을 모두 검토한다. 소유권이나 확인 수단이 없거나 최신이 아닌 경우, 포기, 연기, 담당자 결정은 미완료다. 모든 리프가 최종 상태에 이르고, 모든 실행 묶음이 종료 상태가 되고, 중간 노드와 루트 게이트 파일을 재검증하고, 최종 전체 검증까지 실행한 뒤에만 스코프(scope) 전체를 해제한다. 그 전에 하는 스코프 전체 해제는 기록된 소유 프로세스가 사라졌음을 확인한 뒤의 명시적 복구에만 쓰고, 일반 승격에는 절대 쓰지 않는다. 계약 항목 목록과 루트 게이트 파일이 모두 충족되었을 때만 보고하고, 보고하는 모든 수치를 다시 측정한다.

## 검사 동시 실행

게이트 검사는 기본적으로 순차 실행한다(`--jobs 1`). 이 방식이 실행 기록을 디버그하기 가장 쉽고, 호환성을 위한 기본 동작이다.

`--jobs <N>`은 실행 게이트들이 서로 독립이고 병렬 실행으로 실제 경과 시간이 줄어들 때만 쓴다.

```text
node <skill-dir>/scripts/gate-check.mjs --root . --cwd . --reverify --jobs 4 .unlazy/<scope>/gates/leaf-1.1.1.md .unlazy/<scope>/gates/leaf-1.1.2.md
```

이 상한은 하나가 끝나면 다음을 시작하는 연속 상한이다. 고정된 묶음이 모두 끝나기를 기다리지 않고, 검사 하나가 끝나면 다른 검사를 시작한다. 출력과 파일 갱신은 게이트 파일 순서를 따르므로 결정적이다. `--jobs`는 명령 실행을 제어할 뿐, 서브에이전트 배정이나 의존성 준비 상태는 제어하지 않는다. 네이티브 에이전트 동시 실행에는 [실행 묶음](dispatch.md)을 쓴다.

## 연속 배정

배정을 다음 반복 절차로 다룬다.

```text
검증되지 않은 리프가 남아 있는 동안:
  호스트 동시 실행 상한까지 독립된 READY 리프를 모은다
  바로 그 리프 집합으로 실행 묶음을 연다
  네이티브 에이전트를 모두 실행 시작하고 돌려받은 호스트 핸들을 모두 기록한다
  처음 기다리기 전에 실행 묶음을 확정한다
  다음 리프가 반환되기를 기다린다
  그 반환을 해당 실행 묶음에 기록한다
  그 리프를 재검증하고 수동 증거를 검토한다
  상태를 덧붙이고 VERIFIED로 표시한다
  바로 그 리프의 점유를 해제하고 해제를 기록한다
  Needs가 모두 VERIFIED인 WAITING 리프를 각각 승격한다
```

배정 중에 계획에 없는 의존성을 즉석에서 만들지 않는다. 의존성은 `PLAN.md`에 추가하고, 영향을 받는 상태를 바로잡고, 변경을 기록한다. 사용자 변경 요청은 계약 개정 번호를 올리며, 완료를 더 인정하기 전에 대조해 맞춰야 한다. 독립된 리프를 우선하되, 인터페이스를 먼저 정해야 하는 곳에서는 억지로 독립시키지 않는다.

## 검증 계층

1. **리프 자체 점검:** 흔한 미완료를 잡아내지만 여전히 자기 인증이다.
2. **부모 `--reverify`:** 예전 증거나 손으로 적은 증거를 믿지 않고 실행 게이트의 판정 기준을 모두 다시 실행한다.
3. **중간 노드 통합:** 하나씩 보면 맞지만 합치면 서로 맞지 않는 자식들을 잡아낸다.
4. **선택 사항인 Stop 훅:** 훅이 총괄 에이전트의 것으로 결정한 파이프라인에 미충족 게이트 파일이나 끝나지 않은 실행 묶음이 있으면 총괄 에이전트가 끝내지 못하게 막는다. 검사를 실행하거나 검사의 의미를 검증하지는 않는다.

부모는 필요한 툴체인과 선언된 셸을 똑같이 써야 한다. 환경이 다르면 예전 증거를 받아들이지 말고 불일치를 기록하고 해결한다.

## 수동 게이트

자동화로는 사용자에게 보이는 결과나 판단이 많이 필요한 결과를 모두 증명할 수 없다. 수동 게이트마다 다음을 지킨다.

- 정확한 결과물, 위치, 측정값, 검토자 결정을 인용한다.
- 겉모습의 완성도만 보지 말고 결과가 미치는 영향을 검토한다.
- 위험이 큰 결과는 가능하면 독립 검토를 받는다.
- 증거가 모호하면 게이트를 미충족으로 둔다.

실행 게이트가 모두 통과했다는 이유만으로 리프를 `VERIFIED`로 부르지 않는다.

## 오케스트레이션하지 않을 때

집중된 컨텍스트 하나로 독립된 산출물이 묻히지 않게 하면서 작업을 구현하고 검증할 수 있으면 단독으로 작업한다. 오케스트레이션에는 계획과 통합 비용이 든다. 주의력을 분리하려고 쓰고, 형식을 갖추려고 쓰지 않는다.
