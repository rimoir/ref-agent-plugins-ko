# 네이티브 에이전트 배정

오케스트레이션 모드(총괄 에이전트가 리프를 여러 에이전트에 나눠 맡기고 검증과 통합을 하는 방식)에서 서로 독립된 `READY` 리프(leaf, 트리 맨 아래의 작업 단위)가 두 개 이상이면 언제나 이 계약을 따른다. unlazy는 네이티브 실행 시작을 기록하고, 에이전트 세션은 호스트가 만든다.

실행 묶음(wave) 하나에서는 네이티브 실행 시작 호출과 `start` 기록이 모두 끝나야 처음으로 결과를 기다리거나(wait, join), 결과를 읽거나, 반환을 기록할 수 있다.

## 실행 묶음 열고 확정하기

먼저 모든 리프를 점유 신청(`--claim`)한다. `READY` 리프가 호스트의 현재 동시 실행 상한보다 많으면 남는 리프는 다음 실행 묶음으로 나눈다. 그다음 정확한 id를 넣어 실행 묶음 하나를 연다.

```text
node <skill-dir>/scripts/dispatch-check.mjs open --scope <scope> --wave ready-1 --leaf leaf-1.1.1 --leaf leaf-1.1.2
```

리프마다 호스트의 네이티브 비차단 실행 시작 도구를 호출하고, 호스트가 돌려준 불투명하고 비밀이 아닌 핸들을 기록한다.

```text
node <skill-dir>/scripts/dispatch-check.mjs start --scope <scope> --wave ready-1 --leaf leaf-1.1.1 --handle <host-agent-id-1>
node <skill-dir>/scripts/dispatch-check.mjs start --scope <scope> --wave ready-1 --leaf leaf-1.1.2 --handle <host-agent-id-2>
```

어떤 결과든 기다리기 전에 실행 묶음을 확정(`seal`)한다.

```text
node <skill-dir>/scripts/dispatch-check.mjs seal --scope <scope> --wave ready-1
```

선언한 모든 리프에 서로 다른 시작 핸들이 기록되기 전에는 확정이 실패한다. 확정 전에는 `return`이 실패한다. 이렇게 거부하면 총괄 에이전트가 리프 하나를 실행 시작하고 그 결과를 기다린 뒤에야 다음 리프를 실행 시작하는 순차 패턴을 잡아낼 수 있다.

네이티브 에이전트가 끝나면 부모 재검증 전에 반환을 기록한다.

```text
node <skill-dir>/scripts/dispatch-check.mjs return --scope <scope> --wave ready-1 --leaf leaf-1.1.1
```

반환 기록은 스케줄러 기준으로 작업이 끝났다는 것을 기록하며, 작업 에이전트가 실패 결과를 낸 경우도 포함한다. 반환 기록이 리프를 `VERIFIED`로 표시하지는 않는다. 부모는 여전히 리프의 게이트(완료로 인정하려면 충족해야 하는 조건 한 항목)를 실행하고 수동 증거를 검토한다.

끝난 실행 묶음은 다음 명령으로 확인한다.

```text
node <skill-dir>/scripts/dispatch-check.mjs status --scope <scope> --wave ready-1
```

`status`는 선언한 모든 리프가 반환된 뒤에만 `0`으로 종료한다. 배정(dispatch) 상태와 타임스탬프는 `.unlazy/<scope>/dispatch.json`에 저장되고, 수명 주기 이벤트는 스코프(scope) 상태 로그에도 덧붙는다. 기준이 되는 것은 원자적 상태 전환이다. 그 뒤의 감사 로그 덧붙이기가 거부되어도 전환 명령은 성공하고, 상태가 커밋되었다는 길이가 제한된 경고를 출력한다. 다음에 할 일을 정하기 전에 상태를 확인한다. 전환 명령을 무작정 반복하지 않는다.

상태 로더는 id, 핸들, 포기 사유가 문자열이어야 하고 전환 이력이 가능한 순서여야 한다고 요구한다. 반환은 모든 리프가 시작 기록된 확정된 실행 묶음에서만 가능하고, 종료 상태의 타임스탬프는 반드시 있어야 하며 앞선 전환보다 뒤여야 하고, 모든 리프가 반환된 실행 묶음은 완료 상태여야 한다. 손으로 고쳐 불가능한 종료 상태를 만들면 실패로 처리한다(fail closed). 기본 명령 `gate-check.mjs --scope <scope>`의 집계에는 이 전체 상태가 포함되므로, 실행 묶음이 열려 있거나, 확정만 되었거나, 포기되었거나, 유효하지 않으면 `ALL MET`을 출력할 수 없다.

## Codex 어댑터

[현재 Codex 릴리스는 병렬 서브에이전트를 지원한다](https://developers.openai.com/codex/agent-configuration/subagents). 호스트에 있는 네이티브 서브에이전트 도구를 쓴다. 도구 이름이 `spawn_agent`와 `wait_agent`이면 정확히 다음 순서를 따른다.

1. 열린 실행 묶음의 리프마다 `spawn_agent`를 한 번씩 호출한다.
2. 돌려받은 에이전트 id를 각각 `dispatch-check start`로 기록한다.
3. 실행 묶음을 확정한다.
4. 확정한 뒤에만 `wait_agent`를 호출한다.
5. 끝난 에이전트마다 `dispatch-check return`으로 기록한 뒤 재검증한다.

`codex exec`로 대신하지 않는다. 이 명령은 현재 호스트가 소유하고 볼 수 있는 네이티브 서브에이전트가 아니라 별도의 CLI 프로세스를 만든다.

## Claude Code 어댑터

[Claude Code의 백그라운드 서브에이전트는 동시에 실행된다](https://code.claude.com/docs/en/sub-agents#run-subagents-in-foreground-or-background). 모든 리프를 백그라운드 `Agent` 작업으로 실행 시작하고, 돌려받은 작업 id나 에이전트 id를 모두 기록하고, 어떤 결과든 읽기 전에 확정한다. 포그라운드 Agent 호출을 하나씩 차례로 하지 않는다.

같은 형태의 작업을 대규모로 분산 배정할 때는 [Dynamic Workflow](https://code.claude.com/docs/en/workflows)를 우선 쓴다. 그 `pipeline()` 기본 요소는 런타임의 동시 실행 상한 안에서 목록 전체에 걸쳐 에이전트 작업을 실행한다. 워크플로도 같은 의미의 배리어(모든 실행 시작이 기록되기 전에는 결과를 기다리거나 읽지 못하게 하는 동기화 지점)를 지켜야 한다. 즉 첫 결과를 모으기 전에 분산 배정 전체를 예약해야 한다. 워크플로 인터페이스가 에이전트마다 서로 다른 네이티브 핸들을 보여 줄 때만 CLI 배정 실행 묶음을 연다. 그렇지 않으면 생성된 워크플로 스크립트와 런타임 진행 기록을 중간 노드(branch) 증거로 보관하고, CLI로 검증한 실행 묶음이라고 주장하지 않는다.

사용할 수 있는 네이티브 백그라운드 Agent나 워크플로가 있으면 `claude -p`로 대신하지 않는다. 셸 프로세스를 여러 개 띄우는 방식으로는 현재 세션의 네이티브 스케줄링과 관찰 기능을 쓸 수 없다.

## 실패와 대체 방식

네이티브 실행 시작이 핸들을 돌려주기 전에 실패하면 실행 묶음을 열린 채로 두고, 실행 시작 문제를 고친 뒤 그 리프를 다시 시도한다. 일부만 시작된 실행 묶음을 확정하지 않는다. 복구할 수 없으면 핸들을 지어내거나 상태를 지우지 말고 감사 기록을 보존한다.

```text
node <skill-dir>/scripts/dispatch-check.mjs abandon --scope <scope> --wave ready-1 --reason "<bounded nonblank reason>"
```

포기한 실행 묶음은 종료 상태이고 `status`는 `1`로 종료한다. Stop 훅은 이 실행 묶음 때문에 차단하지 않지만, 길이가 제한된 `HANDOFF REQUIRED` 메시지를 내보낸다. 이 메시지는 실행 묶음 이름을 밝히되 자유 형식 사유를 권한이 높은 호스트 메시지에 옮겨 적지 않는다. 최종 인계에서는 배정 상태에 있는 사유를 드러낸다. 호스트에 비차단 실행 시작 기능이 없으면 그 한계를 `PLAN.md`에 기록하고, 선언한 순차 실행 대체 방식으로 실행하며, 병렬 실행 묶음을 열거나 병렬 실행 묶음이라고 설명하지 않는다.

실행 묶음을 여는 것은 실제로 실행했다는 주장이다. 핸들을 지어내거나, 포그라운드 결과를 시작 기록으로 남기거나, 명령이 빨리 끝났다는 이유만으로 동시에 작업했다고 증명되었다고 말하지 않는다.

## 증거의 한계

실행 시작 배리어는 총괄 에이전트가 반환을 받아들이기 전에 호스트가 모든 네이티브 시작을 받아들였다는 것을 증명한다. 작업 에이전트가 정직했는지, CPU에서 정확히 겹쳐 실행되었는지, 파일 시스템이 분리되었는지, 통합이 성공했는지는 증명하지 않는다. 점유(lease), 부모 재검증, 중간 노드 게이트는 여전히 별도의 요구 사항이다.
