# Sentry 에러 기록

## 이 출처에 담긴 것

Sentry는 잘못된 일들의 보관소다. 방어 코드, 교정 코드, 에러 처리 코드라면 직접적인 동기가 여기에 있는 경우가 많다. 누군가에게 검사, catch, 재시도, 폴백을 추가하게 만든 구체적인 예외, 스택 트레이스, 빈도가 그것이다.

- **이슈.** 건수, 처음·마지막 관측 타임스탬프, 영향받은 릴리스, 댓글이 붙은 그룹화된 에러
- **이벤트.** 이슈 안의 개별 에러 사례(스택 트레이스, 태그, 사용자 맥락)
- **릴리스.** 관련 이슈가 연결된 배포 기록("어느 버전이 이걸 고쳤나?"에 쓸모 있다)
- **리플레이.** 사용자에게 보인 에러의 세션 녹화(켜져 있다면)
- **프로파일.** 성능 프로파일링 데이터("왜"보다는 "얼마나 느린가"에 더 쓸모 있다)
- **이슈 댓글과 담당 지정.** 근본 원인에 대한 엔지니어의 메모가 담겨 있기도 하다

Sentry가 주는 가장 값진 것은 **시간 상관관계**다. "이슈 X는 2024-01-02에 생겼고, 하루 500건으로 정점을 찍었고, 2024-01-15에 방어 검사를 출시한 릴리스 v2.14.0 이후로 나타나지 않았다."

## 검색 방법

Sentry MCP를 쓴다.

1. **지형을 파악한다.** 프로젝트 slug와 조직을 모른다면 다음을 쓴다.

   ```
   find_organizations
   find_projects
   ```

2. **대상과 관련된 이슈를 검색한다.**

   ```
   search_issues (자연어. 예를 들어 "PaymentService 타임아웃 오류", "uploadFile의 처리되지 않은 예외")
   ```

   좋은 쿼리 재료는 대상이 처리하는 예외 클래스 이름, 대상의 함수나 클래스 이름, 대상이 검사하는 에러 메시지 문자열, 대상의 파일 경로다.

3. **릴리스와 시간 구간으로 좁힌다.**

   ```
   search_issue_events (릴리스, 시간, 환경, trace ID, 태그로 거른다)
   get_issue_tag_values (이슈 하나의 버전, 사용자, 환경별 분포를 본다)
   ```

   의심 가는 이슈가 있으면 다음을 확인한다.
   - **처음 관측.** 에러가 언제 나타나기 시작했나?
   - **마지막 관측.** 언제 멈췄나? 대상의 출시일과 맞아떨어지나?
   - **영향받은 릴리스.** 어느 버전에서 나타났나? 어느 버전이 고쳤나?
   - **빈도 궤적.** 치솟았다가 해결됐나?

4. **맥락을 보려고 이벤트 전체를 가져온다.**

   ```
   get_sentry_resource (Sentry URL이나 type+ID를 넘긴다)
   ```

   스택 트레이스가 대상 코드를 지나가는가? 태그와 breadcrumb가 대상이 방어하는 조건과 맞는가?

5. **대상 근처에 반영된 릴리스를 확인한다.**

   ```
   find_releases (대상 커밋 날짜 전후)
   ```

   릴리스 버전을 PR 머지 날짜와 대조한다.

6. **Seer는 아껴 쓴다.**

   ```
   analyze_issue_with_seer
   ```

   Seer는 AI 근본 원인 분석을 만든다. 가설 생성기로는 쓸모 있지만 권위 있는 답이 아니라 추론으로 다룬다. 1차 증거는 실제 이벤트와 스택 트레이스다. Seer의 서사는 부차적이다.

## 여기서 좋은 증거의 모습

- **처음 관측**이 대상 PR 직전이고 **마지막 관측**이 직후인 이슈. 대상이 이 에러를 다뤘음을 시사한다
- 대상 함수를 지나가거나 거기서 끝나는 스택 트레이스. 방어하려던 실패 방식을 정확히 보여 준다
- PR 작성자가 이슈에 남긴, 수정을 설명하는 댓글
- Sentry 이슈 URL이나 ID를 언급하는 대상의 PR 설명이나 커밋 메시지
- 이벤트 건수가 많다가 대상이 포함된 릴리스 이후 멈춘 이슈

## 흔한 함정

- **그룹화 표류.** Sentry는 지문(fingerprint)으로 에러를 묶는다. 리팩터링이나 이름 변경 때문에 "같은" 에러가 새 이슈 ID로 추적될 수 있다. 이슈가 갑자기 끝났다면 에러가 다른 그룹으로 옮겨졌을 뿐일 수 있다. 바로 뒤에 생긴 새 이슈를 확인한다.
- **릴리스 상관관계는 잡음이 많다.** 릴리스 하나에는 커밋이 많다. 이슈가 v2.14.0에서 멈췄다고 대상이 고쳤다는 증명은 아니다. 같은 릴리스의 다른 변경이 고쳤을 수도 있다. 대상의 정확한 커밋과 대조한다.
- **조용한 수정.** 방어 코드 때문이 아니라 상류가 바뀌어서 에러가 멈추기도 한다. 상관관계는 수정을 시사할 뿐, 누가 고쳤는지 증명하지 않는다.
- **resolved != 고쳐짐.** 코드 변경 없이 수동으로 "resolved" 표시를 할 수 있다. `resolved`는 코드가 고쳤다는 증거가 아니라 사람이 단 표시로 다룬다.
- **Seer의 환각.** Seer는 확신에 차 보이지만 틀린 설명을 만들 수 있다. 주장할 때는 실제 이벤트, 스택 트레이스, 타임스탬프로 돌아간다.
- **샘플링.** 어떤 프로젝트는 이벤트를 공격적으로 샘플링한다. 이벤트 건수가 적은 것은 드문 에러여서가 아니라 샘플링이 심해서일 수 있다. 의심스러우면 빈틈으로 적는다.

## 돌려줄 것

관련 이슈마다 다음을 적는다.
- 이슈 ID와 제목
- 프로젝트와 조직
- 처음·마지막 관측 타임스탬프
- 이벤트 건수(알면 샘플링 비율도)
- 영향받은 릴리스
- 대상과의 관련성을 보여 주는 대표 스택 트레이스 조각(요약이 아니라 원문 발췌)
- 처음·마지막 관측과 대상 출시일의 상관관계
- 이슈 링크
- 작성자 댓글이나 해결 메모
