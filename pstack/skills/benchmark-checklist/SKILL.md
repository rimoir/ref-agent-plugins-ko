# 벤치마크 체크리스트

성능 숫자를 낼 때 쓴다. PR의 전후 비교, 회귀 주장, hillclimb 하네스, 라이브러리나 설정 선택이 여기에 든다. 질문마다 코드를 보고 한 추측이 아니라 실행에서 나온 증거로 답한다.

사용자가 대략적인 수치만 원했다면 한 번 돌려도 된다. 그래도 4번과 7번 질문은 확인하고, 한 번 돌린 결과라고 밝힌다. 그 실행이 이상해 보이지 않는 한 나머지는 건너뛴다. 선택지 사이의 선택은 결코 대략적인 수치로 끝나지 않는다.

## 무엇이든 돌리기 전에

- 내놓을 주장을 실제로 쓸 문장으로 적어 둔다("60k행 데이터셋에서 export가 p50 기준 30% 빠르다"). 질문들은 이 문장을 검증한다.
- 측정 스크립트를 읽는다. 무엇을 재고, 무엇을 세고, 무엇을 무시하는지 적어 둔다.
- `uptime`으로 load average를, `nproc`로 코어 수를 확인한다. 기계가 바쁘면 무엇이 돌고 있는지 찾는다. 멈출 수 없다면 양쪽을 번갈아 돌려 같은 잡음을 겪게 하고, 보고서에 그렇게 했다고 밝힌다.

## 질문

1. **왜 두 배가 아닌가?** 제한 요인을 짚는다. 프로파일러와 트레이서는 작업을 느리게 하므로 보고하지 않을 실행에서 프로파일링한다. 프로세스별 CPU(`top`, `pidstat`), 런타임용 프로파일러(`node --cpu-prof`, `py-spy`, `perf`), I/O 대기, 시스템 콜 횟수(Linux에서 `strace -c`)를 쓴다. 그다음 핫스팟을 소스와 연결한다. 부하 생성기도 지켜본다. 그쪽이 먼저 포화되면 부하 생성기를 잰 것이다. 변경이 숫자를 움직이지 못했다면 제한 요인이 그 이유를 말해 주므로, 변경이 쓸모없다고 말하기 전에 제한 요인부터 찾는다.
2. **튜닝했는가?** 모든 쪽을 프로덕션과 같은 방식으로 돌린다. 릴리스 빌드, 프로덕션 플래그와 환경 변수, 배칭과 트랜잭션 설정, 커넥션 풀, 프로덕션과 같은 정도로 데우거나 식힌 캐시, 같은 버전과 데이터다. 한쪽이 기본 설정으로 돌았다면 구현이 아니라 설정을 비교한 것이다. 행마다 커밋하기, 디버그 빌드, 빠진 인덱스처럼 제한 요인이 설정이라면 그쪽은 튜닝되지 않은 것이다. 튜닝하고 다시 잰 뒤에 승자를 고른다. 튜닝할 수 없다면 그 실행으로 승자를 고르지 않는다. 사용자가 무엇을 도입할지 고르는 중이라면 주장을 "지금 배포된 코드 기준"으로 좁혀도 해결되지 않는다. 사용자가 도입하는 것은 지금의 설정이 아니라 그 선택지이기 때문이다.
3. **한계를 넘었는가?** 계산해 본다. 초당 바이트를 디스크와 네트워크 대역폭과 비교하고, 초당 연산 횟수에 연산당 비용을 곱한 값을 가진 코어 수와 비교한다. 아낀 시간을 바꾼 조각이 원래 걸린 시간과 비교한다. 실행 시간의 10%를 차지하는 조각을 없애면 실행은 많아야 11%쯤 빨라진다. 한계를 넘는 결과는 캐시, 아무 일도 하지 않는 코드, 버그처럼 작업이 아닌 다른 것을 쟀다는 뜻이다.
4. **오류가 났는가?** 실패와 성공이 아닌 응답을 세고, 출력이 존재하는지만이 아니라 정확한지 확인한다. 거부는 보통 빠르고 타임아웃과 재시도는 느리다. 스크립트가 오류를 세지 않으면 세게 고친다.
5. **재현되는가?** 각 쪽을 적어도 5번씩 돌리고, 워밍업, 지연 초기화, 캐시, 드리프트가 한쪽에 유리하지 않도록 양쪽을 번갈아(A, B, A, B 식으로) 돌린다. 중앙값과 범위를 보고한다. 실행 간 변동보다 작은 차이는 측정 가능한 차이가 없는 것으로 본다. 판정이 아슬아슬하면 순위합 검정이나 하네스 자체의 통계를 쓴다.
6. **중요한가?** 미시 결과 옆에 사용자가 실제로 기다리는 종단 간 경로를 현실적인 데이터 크기와 동시성으로 잰다. 미시 결과는 전체에서 차지하는 비율로 보고한다. 요청의 1%를 차지하는 헬퍼는 아무리 빨라져도 요청을 많아야 1% 빠르게 한다.
7. **작업이 실제로 일어났는가?** 측정 구간 안에서 작업이 돌았는지 확인한다. 요청이 서버에 닿았고, 행이 쓰였고, 바이트를 읽었고, 코드가 결과를 썼는지 본다. 지연 코드(아무도 순회하지 않는 제너레이터, 아무도 await하지 않는 promise, JIT가 버릴 수 있는 결과)와 타임아웃은 일어나지 않은 작업에 대해 숫자를 낸다.

## 보고

- 판정을 맨 앞에 둔다. 빨라짐, 느려짐, 측정 가능한 차이 없음, 결론 없음 중 하나다.
- 숫자를 단위, 실행 횟수, 범위, 제한 요인과 함께 준다. 예를 들어 "p50 41 ms → 33 ms, 쪽마다 7번 실행한 중앙값, 이후 범위 32~35 ms, 코어 하나에서 JSON 파싱에 묶임."
- 차이를 주장하면서 제한 요인을 짚지 못할 때, 한쪽이 튜닝 없이 돌았을 때, 4번과 7번 질문을 확인하지 못했을 때는 결론 없음으로 판정한다. 빠진 부분을 밝힌다.
- **Opening a PR** 플레이북에 따라 PR 본문에는 대표 숫자 하나만 둔다. 실행 기록, 범위, 제한 요인 증거는 연결된 산출물이나 노트 파일에 둔다.

## 다른 성능 자료

- **Perf issue** 플레이북이 기준선으로 계획을 세우기 전에 그 기준선을 점검하고, 그 뒤에 나오는 모든 숫자도 점검한다.
- **Hillclimb** 플레이북의 하네스를 고정하기 전에 점검한다. 고정된 하네스는 오류 수와 작업 수를 출력하므로, 유지할지 되돌릴지 정할 때마다 4번과 7번 질문을 공짜로 확인한다.
