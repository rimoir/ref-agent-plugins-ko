사용자가 알려 준 기준점(fixed point, 비교 기준이 되는 커밋, 브랜치, 태그)과 `HEAD` 사이의 diff를 두 축으로 리뷰한다.

- **코딩 표준(Standards)**: 코드가 이 저장소에 문서화된 코딩 표준을 따르는가?
- **스펙(Spec)**: 코드가 원래 이슈나 스펙을 충실하게 구현하는가?

두 축은 서로의 컨텍스트가 섞이지 않도록 **병렬 서브에이전트**로 실행하고, 이 스킬이 결과를 모은다. 서브에이전트는 모두 새 컨텍스트 창으로 시작한다.

이슈 트래커 정보는 이미 제공되었어야 한다. 그렇지 않으면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 알린다.

## 절차

### 1. 기준점 정하기

사용자가 말한 것이 기준점이다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 사용자가 기준점을 정하지 않았으면 물어본다.

diff 명령은 한 번만 정해 둔다. `git diff <fixed-point>...HEAD`를 쓴다(점 세 개를 써서 merge-base와 비교한다). `git log <fixed-point>..HEAD --oneline`으로 커밋 목록도 적어 둔다.

더 진행하기 전에 기준점이 실제 커밋으로 해석되는지(`git rev-parse <fixed-point>`)와 diff가 비어 있지 않은지 확인한다. 잘못된 ref나 빈 diff는 병렬 서브에이전트 두 개 안에서가 아니라 여기서 실패해야 한다.

### 2. 스펙 출처 찾기

원래 스펙을 다음 순서로 찾는다.

1. 커밋 메시지 안의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등)를 찾고, 트래커 문서에 적힌 방식으로 관련 티켓을 가져온다.
2. 사용자가 인자로 넘긴 경로
3. `docs/`, `specs/`, `.scratch/` 아래에서 브랜치 이름이나 기능과 맞는 스펙 파일
4. 아무것도 찾지 못하면 사용자에게 스펙이 어디 있는지 묻는다. 스펙이 없다고 하면 **스펙** 서브에이전트는 건너뛰고 "no spec available"(사용 가능한 스펙 없음)이라고 보고한다.

### 3. 코딩 표준 출처 찾기

저장소에서 코드를 어떻게 써야 하는지 문서화한 파일을 모두 찾는다. `CODING_STANDARDS.md`나 `CONTRIBUTING.md`가 있으면 반드시 목록에 넣는다.

저장소가 문서화한 내용에 더해, 코딩 표준 축에는 항상 아래 **기본 코드 스멜 목록**이 따라간다. 코드 스멜은 리팩터링이 필요할 수 있다는 징후이고, 이 목록은 Fowler의 코드 스멜(_Refactoring_, 3장) 중 정해 둔 항목이다. 저장소가 아무것도 문서화하지 않았어도 적용한다. 이 목록에는 다음 규칙이 붙는다.

- **저장소 규칙이 우선한다.** 문서화된 저장소 표준이 항상 이긴다. 목록이 문제로 짚을 만한 것을 저장소 표준이 권장하면 그 스멜은 보고하지 않는다.
- **항상 판단이 필요한 항목이다.** 각 스멜은 이름을 붙인 경험 법칙("possible Feature Envy"처럼 "~일 수 있음"으로 표시)이고 명백한 위반으로 다루지 않는다. 여기의 다른 표준과 마찬가지로 도구가 이미 강제하는 것은 건너뛴다.

각 스멜은 *무엇인지* → *어떻게 고치는지* 순서로 적혀 있다. diff와 대조한다.

- **Mysterious Name**(뜻을 알 수 없는 이름): 이름만 보고 무엇을 하는지, 무엇을 담는지 알 수 없는 함수, 변수, 타입. → 이름을 바꾼다. 정확한 이름이 떠오르지 않으면 설계가 불분명하다는 뜻이다.
- **Duplicated Code**(중복 코드): 같은 형태의 로직이 변경 안의 여러 변경 블록(hunk)이나 파일에 나타난다. → 공통 형태를 추출하고 양쪽에서 호출한다.
- **Feature Envy**(다른 객체 데이터에 의존): 자기 데이터보다 다른 객체의 데이터를 더 많이 건드리는 메서드. → 그 메서드를 그 데이터가 있는 쪽으로 옮긴다.
- **Data Clumps**(늘 함께 다니는 데이터): 같은 필드나 매개변수 몇 개가 계속 함께 전달된다(하나의 타입으로 묶어야 한다는 신호). → 하나의 타입으로 묶어 그것을 넘긴다.
- **Primitive Obsession**(기본 타입 남용): 자기 타입이 있어야 할 도메인 개념을 기본 타입이나 문자열로 대신한다. → 그 개념에 작은 전용 타입을 준다.
- **Repeated Switches**(반복되는 분기): 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 곳곳에 되풀이된다. → 다형성으로 바꾸거나, 두 곳이 함께 쓰는 맵 하나로 바꾼다.
- **Shotgun Surgery**(흩어진 수정): 논리적 변경 하나 때문에 diff 안의 여러 파일을 흩어져 고쳐야 한다. → 함께 바뀌는 것을 한 모듈로 모은다.
- **Divergent Change**(여러 이유로 바뀌는 모듈): 한 파일이나 모듈이 서로 관계없는 여러 이유로 수정된다. → 모듈마다 바뀌는 이유가 하나가 되도록 나눈다.
- **Speculative Generality**(추측성 일반화): 스펙에 없는 필요를 위해 추가한 추상화, 매개변수, 훅. → 지운다. 실제 필요가 생길 때까지 인라인으로 되돌린다.
- **Message Chains**(메시지 체인): 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 탐색. → 첫 번째 객체의 메서드 하나 뒤로 이 탐색을 숨긴다.
- **Middle Man**(중개자): 대부분의 일을 다른 곳에 넘기기만 하는 클래스나 함수. → 없애고 실제 대상을 직접 호출한다.
- **Refused Bequest**(상속 거부): 물려받은 것 대부분을 무시하거나 재정의하는 하위 클래스나 구현체. → 상속을 없애고 조합을 쓴다.

### 4. 두 서브에이전트를 병렬로 실행하기

두 서브에이전트 호출을 포그라운드에서 함께 보내고, 돌아온 보고를 모은다.

**코딩 표준 서브에이전트 프롬프트**에는 다음을 넣는다.

- 전체 diff 명령과 커밋 목록
- 3단계에서 찾은 코딩 표준 출처 파일 목록, 그리고 **3단계의 기본 코드 스멜 목록 전문**(서브에이전트는 이 목록을 다른 방법으로 볼 수 없다)
- 지시 요약: "관련 있는 곳은 파일/변경 블록 단위로 다음을 보고한다. (a) diff가 문서화된 표준을 어기는 모든 곳. 해당 표준(파일과 규칙)을 인용한다. (b) 눈에 띄는 기본 목록의 스멜. 스멜 이름을 적고 해당 변경 블록을 인용한다. 명백한 위반과 판단이 필요한 항목을 구분한다. 문서화된 표준 위반은 명백한 위반일 수 있지만 기본 목록의 스멜은 항상 판단이 필요한 항목이고, 문서화된 저장소 표준이 기본 목록보다 우선한다. 도구가 강제하는 것은 건너뛴다. 400단어 이내로 쓴다."

**스펙 서브에이전트 프롬프트**에는 다음을 넣는다.

- diff 명령과 커밋 목록
- 스펙의 경로 또는 가져온 스펙 내용
- 지시 요약: "다음을 보고한다. (a) 스펙이 요구했지만 빠졌거나 일부만 구현된 요구사항. (b) 요구하지 않았는데 diff에 들어간 동작(범위 확장). (c) 구현된 것처럼 보이지만 구현이 잘못된 것 같은 요구사항. 발견한 항목마다 스펙의 해당 줄을 인용한다. 400단어 이내로 쓴다."

스펙이 없으면 스펙 서브에이전트를 건너뛰고 최종 보고에 그 사실을 적는다.

### 5. 결과 모으기

두 보고를 `## 코딩 표준`과 `## 스펙` 제목 아래에 그대로 또는 조금만 다듬어서 싣는다. 발견 항목을 합치거나 순위를 다시 매기지 **않는다**. 두 축은 일부러 분리해 두었기 때문이다(_두 축으로 나누는 이유_ 참고).

마지막에 한 줄 요약을 붙인다. 축별 발견 항목 수와 _각 축 안에서_ 가장 심각한 문제(있다면)를 적는다. 두 축을 통틀어 가장 심각한 것 하나를 고르지 않는다. 그것이 바로 축을 나눠서 막으려는 순위 재조정이다.

## 두 축으로 나누는 이유

변경은 한 축을 통과하고 다른 축에서 실패할 수 있다.

- 모든 표준을 따르지만 잘못된 것을 구현한 코드 → **코딩 표준 통과, 스펙 실패**
- 이슈가 요구한 대로 정확히 동작하지만 프로젝트 규칙을 어기는 코드 → **스펙 통과, 코딩 표준 실패**

두 축을 따로 보고하면 한 축의 결과가 다른 축의 문제를 가리지 않는다.
