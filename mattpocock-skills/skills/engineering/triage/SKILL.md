# 분류(Triage)

프로젝트 이슈 트래커의 이슈를 분류(triage) 역할로 이루어진 작은 상태 기계에 따라 옮긴다.

이 저장소가 외부 풀 리퀘스트를 요청 접수 경로로 쓴다면(이슈 트래커 설정 참고) 분류 대상에 PR도 들어간다. **PR은 코드가 붙은 이슈다.** 같은 역할, 같은 상태, 같은 상태 기계를 쓰고, 아래에 "PR이면"으로 표시한 몇 가지 차이만 있다. 번호만 있는 `#42`가 이슈인지 PR인지는 트래커 설정에 따라 판단한다.

분류 중에 이슈 트래커에 올리는 모든 댓글과 이슈는 **반드시** 다음 안내 문구로 시작한다.

```
> *이 글은 분류(triage) 과정에서 AI가 작성했습니다.*
```

## 참고 문서

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 오래 유효한 에이전트 작업 지시서(agent brief)를 쓰는 방법
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` 기록 저장소가 동작하는 방식

## 역할

**유형** 역할:

- `bug`: 무언가가 고장 났다
- `enhancement`: 새 기능이나 개선

**상태** 역할:

- `needs-triage`: 메인테이너가 검토해야 한다
- `needs-info`: 보고자의 추가 정보를 기다린다
- `ready-for-agent`: 스펙이 완전히 정해져 AFK 에이전트(사람 없이 에이전트 혼자 진행)가 바로 작업할 수 있다
- `ready-for-human`: 사람이 구현해야 한다
- `wontfix`: 처리하지 않는다

PR이면 같은 상태를 붙어 있는 코드 기준으로 읽는다. `ready-for-agent`는 작업 지시서가 붙어 있고 에이전트가 이 diff에 다음 작업을 해야 한다는 뜻이다. `ready-for-human`은 사람이 병합할 준비가 됐다는 뜻이다.

분류를 마친 이슈에는 유형 역할과 상태 역할이 정확히 하나씩 붙어 있어야 한다. 상태 역할이 서로 충돌하면 그 사실을 알리고, 다른 일을 하기 전에 메인테이너에게 묻는다.

위 이름은 표준 역할 이름이다. 이슈 트래커에서 실제로 쓰는 라벨 문자열은 다를 수 있다. 그 대응표는 이미 제공되었어야 한다. 제공되지 않았다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 알린다.

상태 전환: 라벨이 없는 이슈는 보통 먼저 `needs-triage`로 간다. 거기서 `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix` 중 하나로 옮긴다. `needs-info`는 보고자가 답하면 `needs-triage`로 돌아간다. 메인테이너는 언제든 이 흐름을 무시하고 직접 정할 수 있다. 평소와 다른 전환이면 그 사실을 알리고 진행하기 전에 묻는다.

## 호출 방식

메인테이너가 `/triage`를 호출하고 원하는 것을 자연어로 설명한다. 요청을 해석해서 실행한다. 예시:

- "내가 봐야 할 게 있으면 보여 줘"
- "#42 좀 보자" (이슈 또는 PR)
- "#42를 ready-for-agent로 옮겨 줘"
- "에이전트가 가져갈 수 있는 게 뭐가 있어?"

## 확인이 필요한 항목 보여 주기

이슈 트래커를 조회해 아래 그룹으로 나눠 보여 준다. 각 그룹 안에서는 오래된 것부터 보여 준다.

- **라벨 없음**: 한 번도 분류하지 않았다.
- **`needs-triage`**: 검토가 진행 중이다.
- **마지막 분류 메모 이후 보고자 활동이 있는 `needs-info`**: 다시 검토해야 한다.

PR이 분류 대상이면 외부 PR도 이 그룹에 넣고 각 줄에 `[PR]` 또는 `[issue]` 태그를 붙인다. 목록을 찾을 때는 *외부* PR만 보여 준다(누가 외부인인지는 트래커 설정이 정한다). 그래서 협업자가 진행 중인 PR은 분류 작업이 아니다. 이 필터는 목록을 찾을 때만 적용한다. 직접 지정해 요청한 PR은 작성자와 상관없이 항상 분류한다.

개수와 항목별 한 줄 요약을 보여 준다. 무엇을 다룰지는 메인테이너가 고르게 한다.

## 특정 이슈나 PR 분류하기

1. **맥락 수집.** 이슈나 PR 전체(본문, 댓글, 라벨, 작성자, 날짜, PR이면 diff까지)를 읽는다. 이전 분류 메모가 있으면 읽어서 이미 해결된 질문을 다시 묻지 않는다. 프로젝트의 도메인 용어집을 기준으로 코드베이스를 살피고, 해당 영역의 ADR(아키텍처 결정 기록)을 따른다. 코드베이스에서 다음을 확인한다. (a) **중복**: 요청한 동작이 이미 구현돼 있는지 요청 문구만이 아니라 도메인 개념으로 찾아보고, 어디를 찾아봤는지 보고한다. 찾으면 이미 구현된 경우의 `wontfix`다(5단계). (b) **이전 거절**: `.out-of-scope/*.md`를 읽고 이번 요청과 비슷한 것이 있으면 알린다.

2. **추천.** 메인테이너에게 추천하는 유형과 상태를 이유와 함께 알리고, 요청과 관련된 코드베이스 상황(이미 구현돼 있는지 포함)을 짧게 요약해 전한다. 그다음 지시를 기다린다.

3. **주장 검증.** 집요하게 질문하기 전에 주장이 사실인지 확인한다. 버그면 보고자가 적은 단계대로 재현한다. PR이면 diff가 설명대로 동작하는지 확인한다. 체크아웃하고 관련 테스트나 명령을 실행한다. 결과를 보고한다. 확인됨(코드 경로 포함), 실패, 정보 부족(`needs-info`로 가야 한다는 강한 신호) 중 하나다. 검증으로 확인된 내용이 있으면 에이전트 작업 지시서가 훨씬 탄탄해진다.

4. **집요한 질문(필요하면).** 요청을 더 구체화해야 하면 Skill 도구를 "grilling"으로 한 번, "domain-modeling"으로 한 번, 두 번 호출한다. 그리고 질문 라운드를 한 번에 하나씩 진행하며 집요하게 질문해 요청을 구체화한다. 이 과정에서 도메인 용어를 다듬고, 결정이 날 때마다 `GLOSSARY.md`와 ADR을 바로 갱신한다.

5. **결과 적용:**
   - `ready-for-agent`: 에이전트 작업 지시서 댓글을 올린다([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: 에이전트 작업 지시서와 같은 구조로 쓰되, 왜 에이전트에게 맡길 수 없는지(판단이 필요한 항목, 외부 접근 권한, 설계 결정, 수동 테스트) 적는다.
   - `needs-info`: 분류 메모를 올린다(아래 템플릿).
   - `wontfix`면 이슈를 닫는다. 댓글 내용은 *왜* 닫는지에 따라 다르다.
     - **이미 구현됨**: 요청한 변경이 코드베이스에 이미 있다. 어디에 있는지 알려 준다. `.out-of-scope/`에는 기록하지 **않는다**(그 기록 저장소는 *거절한* 요청용이지 이미 만든 기능용이 아니다).
     - **거절(bug)**: 정중하게 설명하고 닫는다.
     - **거절(enhancement)**: `.out-of-scope/`에 기록하고, 댓글에 그 파일 링크를 남긴 뒤 닫는다([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: 역할을 붙인다. 일부 진행된 내용이 있으면 댓글을 남겨도 된다.

## 빠른 상태 변경

메인테이너가 "#42를 ready-for-agent로 옮겨 줘"라고 하면 그 판단을 믿고 역할을 바로 붙인다. 무엇을 할지(역할 변경, 댓글, 닫기) 확인받은 뒤 실행한다. 집요한 질문은 건너뛴다. 집요한 질문 세션 없이 `ready-for-agent`로 옮기는 경우에는 에이전트 작업 지시서를 쓸지 묻는다.

## needs-info 템플릿

```markdown
## 분류 메모

**지금까지 확인한 내용:**

- 항목 1
- 항목 2

**추가로 알려 주셔야 할 내용 (@reporter):**

- 질문 1
- 질문 2
```

집요한 질문 과정에서 해결된 내용은 모두 "지금까지 확인한 내용" 아래에 적어서 그동안 한 작업이 사라지지 않게 한다. 질문은 구체적이고 바로 답할 수 있어야 한다. "추가 정보를 주세요" 같은 질문은 쓰지 않는다.

## 이전 세션 이어 가기

이슈나 PR에 이전 분류 메모가 있으면 읽고, 남아 있던 질문에 보고자가 답했는지 확인하고, 갱신된 상황을 먼저 보여 준 뒤 이어 간다. 이미 해결된 질문을 다시 묻지 않는다.
