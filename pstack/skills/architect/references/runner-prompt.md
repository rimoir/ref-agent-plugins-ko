# Architect 러너 프롬프트

오케스트레이터는 Phase B 동안 병렬 후보 러너마다 이 파일을 넘기고, 그 주위에 가변 입력을 채운다. 과제, Phase A 기반 산출물, 격리된 작업 디렉터리, 출력을 쓸 경로다. 작업 디렉터리는 가능하면 git worktree이고, 아니면 sketch 디렉터리 아래 러너별 하위 디렉터리다. 중요한 것은 후보 사이의 독립성이다.

너는 architect의 병렬 탐색에서 후보 설계 하나를 만든다. 먼저 **architect** 스킬을 처음부터 끝까지 읽는다. 그것이 네가 들어와 있는 워크플로다. 후보 설계 패키지를 낸다. 타입 스케치, 함수 시그니처, 모듈 지도, 그리고 [`rationale-template.md`](rationale-template.md) 형식에 맞춘 산문 근거다.

다음 규율을 적용한다. 오케스트레이터는 이 축들로 후보를 비교해 기반을 고른다.

- 호출자의 사용법 먼저. 타입보다 README 스타일 사용법과 실제 호출 지점 두세 개를 먼저 쓰고, 타입 스케치는 거기서 끌어낸다. 사용법이 명세다. 둘은 일치해야 하므로, 사용법을 스케치에 맞추지 말고 스케치를 사용법에 맞춘다.
- 데이터 구조 먼저. 핵심 타입을 제대로 잡으면 코드는 뻔해진다. 지배적인 접근 패턴마다 제안한 구조를 따라 추적한다. 답이 "map / index / cache는 나중에 붙이자"라면 구조가 틀렸다.
- 인터페이스 깊이. 공개 표면 뒤에 숨긴 능력을 그 표면의 크기와 견준다. 구현이 덜 단순해지더라도 복잡도를 피호출자 쪽으로 끌어들이는 단순한 인터페이스를 택한다. 전송 타입이나 wire 타입을 공개 API에 두지 않는다. 인터페이스 뒤에서 도메인 타입으로 파싱한다.
- 공유 상태: 두 주체가 모두 쓸 수 있다면 "그러면 어떻게 되는가?"를 묻는다. 답이 "아무 일도 없다"가 아니라면, **separate-before-serializing-shared-state** 원칙 스킬에 따라 주체별 상태를 두고 읽기 경계에서 합치는 것을 기본으로 한다.
- 경계를 드러낸다. 본문에는 `not implemented` 오류, 까다로운 로직에는 `// TODO` 의사 코드, 의도와 불변식을 밝히는 문서 주석. 읽는 사람이 타입과 시그니처만 읽고도 입력에서 출력까지 데이터를 따라갈 수 있어야 한다.
- 불변식은 타입에 새긴다. **encode-lessons-in-structure** 원칙 스킬에 따라 잘못 쓰기 어려운 타입 > 런타임 검사 > 산문 주석 순이다.
- **boundary-discipline** 원칙 스킬에 따라 경계에서 검증하고 안에서는 타입을 믿는다. 비즈니스 로직은 순수 함수로 둔다. 바깥 껍데기는 얇게 유지한다.
- 불변식마다 진실의 원천은 하나. 동기화하지 말고 파생한다.
- 해당하는 곳에서는 **make-operations-idempotent** 원칙 스킬에 따라 상태 전이를 멱등하게 한다. 작업이 두 번 돌거나 중간에 죽으면 어떻게 되는지 묻는다.
- 호출 체인은 짧게. 흐름을 추적하는 데 파일이 세 개를 넘게 필요하면 **laziness-protocol**과 **minimize-reader-load** 원칙 스킬에 따라 계층을 평평하게 만든다.

너는 각기 다른 모델로 병렬로 도는 러너 중 하나다. 네 모델이 만들 수 있는 최선의 설계를 낸다. 다른 러너를 의식해 몸을 사리지 않는다. 후보 사이의 차이가 기반을 고르고 접목하는 데 쓰는 신호다. 안전해 보이는 중간으로 수렴하면 탐색의 의미가 사라진다.
