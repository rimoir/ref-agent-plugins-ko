# 게이트 파일 형식

게이트(완료로 인정하려면 충족해야 하는 조건 한 항목)를 적은 게이트 파일은 기계가 검사하는 완료 계약이다. 검사기와 Stop 훅은 같은 엄격한 파서를 쓴다. 구조가 잘못되면 완료를 인정하는 결과를 내지 않고 실패로 처리한다(fail closed).

## 최소 형식

```markdown
# Gates: 계정 가져오기

OWNS: src/import/**, tests/import/**

Scope: 올바른 레코드는 가져오고 형식이 잘못된 레코드는 거부한다

- [ ] G1: 올바른 픽스처를 빠짐없이 가져온다
  CHECK: node scripts/check-import.mjs fixtures/valid.json
  EXPECT: import verification passed
  EVIDENCE: pending

- [ ] G2: 패키지 수준 통합이 성공한다
  CHECK: node ../../scripts/check-package.mjs
  EXPECT: package verification passed
  CWD: packages/importer
  EVIDENCE: pending

- [ ] G3: 마이그레이션 문구를 제품 결정과 대조해 검토했다
  EVIDENCE: pending

ABANDON: G3 결정 담당자와 연락할 수 없어 인계 내용을 이슈 123에 기록했다
```

위의 코드 펜스 예시는 설명용 문서다. 파서는 코드 펜스 안의 줄을 무시한다. 펜스의 경계는 [CommonMark의 코드 펜스 규칙](https://spec.commonmark.org/0.30/#fenced-code-blocks)을 따른다. 닫는 표시는 여는 표시와 같은 문자를 쓰고, 길이가 여는 표시 이상이며, 뒤에 다른 내용이 없고, 앞에 공백을 세 개까지 둘 수 있다.

## 엄격한 파싱 규칙

- 게이트는 `- [ ] ID: outcome` 또는 `- [x] ID: outcome`으로 시작한다. 파일 안에서 고유하고 비어 있지 않은 id를 명시한다. id가 없는 게이트는 잘못된 형식이다. 줄 위치로 만든 식별자는 줄이 옮겨지면 바뀌기 때문이다.
- `CHECK:`, `EXPECT:`, `CWD:`, `EVIDENCE:`는 해당 게이트 아래에 들여 쓴다. 들여 쓰지 않은 속성은 게이트를 조용히 수동 게이트로 바꾸지 않고 오류로 진단한다.
- 실행 게이트에는 `CHECK:`와 `EXPECT:`를 모두 준다. 수동 게이트에는 둘 다 주지 않는다. 하나만 있는 실행 게이트는 잘못된 형식이다.
- 게이트마다 `EVIDENCE:` 줄을 하나 둔다. 나머지가 올바른 게이트에서 이 줄이 빠지면 검사기가 파일의 원래 줄바꿈 방식(CRLF 또는 LF)을 바꾸지 않고 이 줄을 넣는다.
- 선택 사항인 `OWNS:` 헤더는 첫 게이트 앞에 둔다. 경로는 쉼표로 구분한다. 경로는 저장소 기준 상대 glob이다. 절대 경로와 `..` 같은 상위 디렉터리 이동 구간은 잘못된 값이다.
- `ABANDON: <id> <reason>`은 같은 파일에 있는 게이트에만 쓴다. 이유에는 공백이 아닌 글자가 있어야 한다. 알 수 없는 id는 파싱 오류다. 오타를 조용히 무시하면 나머지가 모두 통과한 자식이 부모를 완료로 승격시킬 수 있기 때문이다.
- `ABANDON:`은 1열에서 시작한다. 이 줄은 id로 게이트를 가리키므로 게이트 속성이 아니라 파일 수준 선언이고, 들여 쓰면 안 되는 줄은 이것 하나뿐이다. 들여 쓴 `ABANDON:`은 적용하지 않고 오류로 진단한다.
- 게이트가 하나도 없는 게이트 파일을 정의하지 않는다. 이름을 붙였지만 비어 있거나 형식이 잘못된 게이트 파일은 `ALL MET`이 아니라 파싱 오류다.
- JavaScript 정규 표현식으로 기대값을 적으려면 `/pattern/flags`를 쓰고, 부분 문자열로 적으려면 일반 텍스트를 쓴다. 잘못된 정규 표현식은 파싱 오류다.
- 양 끝의 슬래시가 항상 우선한다는 점을 기억한다. `EXPECT: /etc/app/conf/`는 그 경로 문자열이 아니라 패턴 `etc/app/conf`이므로 그 안의 점은 아무 문자에나 맞는다. 이스케이프하지 않은 안쪽 슬래시가 있으면 두 해석이 모두 그럴듯하므로 경고한다. 패턴으로 쓰려면 안쪽 슬래시를 이스케이프하고, 아니면 양 끝 슬래시를 빼고 `etc/app/conf` 같은 뚜렷한 부분 문자열로 맞춘다.

id는 한 파일 안에서 고유하다. 도구는 트리 전체 출력에서 id 앞에 파일 이름(확장자 제외)을 붙여 `leaf-1.2.1:G3`, `node-1.1:N2`처럼 전체 id(파일 이름을 앞에 붙인 id)로 나타낸다. 보고와 인계에는 이 전체 id를 쓴다.

## 성공 조건과 증거

실행 게이트는 다음 조건을 모두 만족할 때만 통과한다.

- 프로세스가 시작되고 종료 상태 `0`으로 끝난다.
- `EXPECT:`가 명령의 표준 출력과 표준 오류를 합친 내용과 맞는다.

0이 아닌 상태로 끝난 프로세스는 오류 메시지에 기대한 문자열이 들어 있다는 이유만으로 통과하지 않는다. 시간 초과, 셸 시작 오류, 명령 없음, 출력 한도 초과도 실패다. 기본 제한 시간은 120초이고, `--timeout`은 1부터 86400까지의 정수를 받는다. 정리 작업과 검사기가 최종 상태에 이르는 시간에는 상한이 있다. 그러나 unlazy는 프로세스 샌드박스가 아니므로, 일부러 분리해 띄운 프로세스는 시간 초과로 끝난 셸보다 오래 살아남을 수 있다. 검사는 일부러 분리해 띄운 백그라운드 서비스를 스스로 정리해야 한다. 검사마다 1 MiB 한도를 두 곳에 둔다. 먼저 캡처한 stdout/stderr 원본 전체에 적용하고, 그다음 정규 매칭 문자열의 UTF-8 바이트 길이에 적용한다. 정규 매칭 문자열은 캡처한 stdout 전체를 UTF-8로 디코딩한 것, 두 스트림이 모두 비어 있지 않을 때 넣는 합성 줄바꿈 하나, 캡처한 stderr 전체를 UTF-8로 디코딩한 것을 차례로 이은 것이다. `EXPECT:`와 증거의 SHA-256 및 바이트 수는 정확히 이 문자열을 쓴다. 잘못된 바이트를 대체 문자로 바꾸거나 스트림 구분자를 넣으면 두 번째 표현이 원본보다 커질 수 있다. 이때는 넘침으로 실패하고, 잘라서 매칭에 쓰는 일은 없다. 정규 표현식 매칭은 일회용 워커를 최대 네 개까지 쓴다. 워커마다 5초의 시작 제한 시간이 있고, 그 뒤에 별도의 250ms 매칭 시간이 시작된다.

자동 증거는 `automatic-evidence=v1`로 시작하고, 이어서 파싱한 `CHECK:`, `EXPECT:`, 원본 `CWD:` 정의의 전체 소문자 SHA-256 다이제스트가 온다. 이 다이제스트는 환경과 무관하며, 게이트 id와 제목, 서식, 게이트 파일 경로, 해석된 경로, 셸, 제한 시간, 플랫폼, `PATH`를 포함하지 않는다. 그 바로 뒤에 정규 형식의 `exit=0`, `EXPECT=matched`, 성공 출력 문자열의 다이제스트와 그 UTF-8 바이트 수가 오며, 길이 제한이 있는 기계별 실행 기록 필드보다 먼저 검증된다. 불투명한 부분은 그 뒤의 실행 기록뿐이다. 따라서 잘라 내더라도 판정을 결정하는 요약 해시는 어느 것도 지워지지 않는다. 성공한 출력 원본과 전체 `PATH`는 저장하지 않는다. 실패 진단 메시지는 길이가 제한되고, 터미널에만 출력되며, 제어 문자를 제거한다.

체크된 실행 게이트는 정확히 그 v1 정의 바인딩과 정규 형식의 성공/출력 헤더가 있을 때만 충족이다. 실행 게이트의 증거가 없거나, 비어 있거나, `pending`이거나, 일반 문장이거나, v1 이전 형식이거나, 형식이 잘못되었거나, 이후 버전이거나, 정의와 맞지 않으면 `stale-unmet`이다. 일반 실행은 이런 게이트를 평소처럼 승인 조회를 거쳐 실행 대상에 넣고, 실행에 성공하면 증거를 새 형식으로 옮긴다. 다이제스트는 키 없이 구조 변경을 감지하는 수단일 뿐, 진위나 위조 여부를 증명하지 않는다. 게이트 파일을 편집할 수 있는 사람은 문법상 정규 형식이고 정의와 맞는 헤더를 위조할 수 있다. 최신이 아닌 게이트를 다시 실행해 실패하면 체크를 지우고 `EVIDENCE: pending`으로 되돌린다. 수동 게이트는 사람이 적은 과거 증거를 그대로 유지한다. 다만 실행 게이트가 수동 게이트로 바뀌면 예약된 v1 증거와 레거시 `exit=0; shell=` 실행 기록은 계속 기계 증거로 취급한다. 반대로 사람이 증명한 수동 게이트에 실행 정의를 추가하면 그 이전 증거는 최신이 아닌 것이 된다.

`--status`는 명령을 실행하거나 파일을 바꾸지 않고 게이트 파일을 파싱해 상태를 보고한다. 셸을 해석하거나 승인 저장소를 읽지 않고, `PATH`, 제한 시간, 기타 실행 옵션에 의존하지 않고 순수한 정의 바인딩만 검증한다. Stop 훅도 명령을 실행하지 않는 같은 상태 모델을 쓴다. 둘 다 현재 결과물이나 간접 입력을 살펴보지 않는다. 부모 검증에는 재검증(`--reverify`)을 쓴다. 재검증은 이미 체크된 게이트를 포함해 모든 실행 게이트를 실행하고, 판정 기준(oracle)이 더 이상 통과하지 않으면 그 게이트를 미충족으로 되돌린다. 요약에는 다시 실행한 전체 명령과 그중 이전에 충족이었던 것을 함께 보고한다.

## 승인 경계

`CHECK:`는 검사기의 권한과 물려받은 환경으로 실행되는 셸 코드다. 물려받은 게이트 파일(다른 사람이나 이전 세션이 만든 것)은 `--status`로 파싱하고 그 소스를 읽는다. 기존 승인이 없는 일반 실행은 해석된 판정 기준을 하나씩 출력하고 실행하지 않는다. 모든 명령과 호출되는 스크립트를 검토한 뒤 명시적인 `--approve`로만 실행한다.

승인 기록은 기본적으로 `~/.unlazy/approved` 아래에 있다. `UNLAZY_APPROVAL_DIR`로 다른 디렉터리를 고를 수 있지만, 그 디렉터리가 실제 디렉터리이고 소유자 전용이며 정규 대상 경로가 정규 저장소 루트 밖에 있을 때만 가능하다. 심볼릭 링크로 된 저장소, 그리고 링크되었거나 교체되었거나 소유자 전용이 아닌 기록은 실패로 처리한다. 승인 식별 정보에는 게이트 파일의 절대 경로와 게이트, 정확한 `CHECK:`와 `EXPECT:`, 해석된 `CWD:`와 셸, 제한 시간, 출력 및 정규식 한도, 정규식 워커 한도, 플랫폼, 물려받은 `PATH` 전체가 들어간다. 이 식별 정보는 환경과 무관한 증거 다이제스트와 일부러 분리해 두었다. 승인은 이 실행 환경의 판정 기준을 실행해도 되는지 정하고, 정의 다이제스트는 기록된 자동 증거가 현재 파싱된 정의를 설명하는지 정한다. 승인 대상에 묶인 입력이 하나라도 바뀌면 승인은 무효가 된다. 승인은 호출되는 스크립트, 픽스처, 소스 파일, 의존성 같은 간접 입력을 일부러 해시하지 않는다. 그래서 이런 파일이 한 바이트라도 바뀌어도 기존 승인으로 실행될 수 있고, 구조상 최신인 증거는 명시적으로 재검증하기 전까지 계속 보일 수 있다. 바뀐 의존성은 다시 살펴보고 `--reverify`를 실행한다. 의존성 파일이 기대한 내용과 같은지 기계로 강제해야 하면 기대하는 다이제스트를 승인 대상인 `CHECK:` 텍스트에 넣고, 따로 신뢰하는 도구나 런타임으로 검증한다. 이것은 사용자가 설계한 확인 범위이지 unlazy가 간접 입력을 추적하는 것이 아니다. 승인은 명령을 실행해도 된다는 확인일 뿐, 그 명령이 자연어로 적은 결과를 실제로 측정한다는 증거가 아니다. 전체 위협 모델은 [../SECURITY.md](../SECURITY.md)를 본다.

## 셸, PATH, 작업 디렉터리

검사기는 다음 순서로 셸을 정한다.

1. `--shell <path-or-name>`
2. `UNLAZY_SHELL`
3. Unix에서는 `/bin/sh`, Windows에서는 `process.env.ComSpec`(없으면 대체 이름 `cmd.exe`)

자식 프로세스는 `PATH`를 포함해 검사기의 환경을 물려받는다. Node 문서에 따르면 셸 명령은 플랫폼 셸과 물려받은 환경을 쓴다. Microsoft 문서에 따르면 `cmd.exe`는 실행 파일 확장자가 붙은 파일을 현재 디렉터리에서 먼저 찾고 그다음 `PATH`에서 찾는다. 그래서 Git Bash에서 검사기를 실행하면, 같은 명령을 PowerShell에서 실행할 때는 보이지 않는 도구가 보일 수 있다. 셸을 지정해 바꾸면 인터프리터만 바뀌고, 설치된 프로그램이나 물려받은 `PATH`는 바뀌지 않는다.

여러 플랫폼에서 돌아가야 하는 게이트에는 저장소에 들어 있는 Node 스크립트를 쓰는 편이 낫다.

```markdown
  CHECK: node scripts/verify-output.mjs
  EXPECT: output verification passed
```

기본 설치된 Windows에 `grep`, `tail`, `tr`, `sed`, POSIX 파이프라인 동작이 있다고 가정하지 않는다. 게이트가 특정 셸이나 외부 도구를 일부러 필요로 하면 그 전제 조건을 밝히고, 부모 재검증 때도 같은 셸과 툴체인을 쓴다.

`CWD:`는 검사기의 기본 작업 디렉터리를 기준으로 해석한다. 기본값은 `--cwd`로 정한다. `--cwd`가 없으면, 명시적으로 지정한 게이트 파일은 그 파일이 있는 디렉터리를 기준으로 하고, 스코프 탐색과 레거시 탐색은 `--root`를 기준으로 한다. `CWD:`는 저장소 기준 상대 경로로 둔다. 해석된 디렉터리는 증거와 승인 양쪽에 들어간다.

주요 플랫폼 참고 문서는 다음과 같다.

## 실패할 수 있는 게이트 작성하기

검사기는 선언된 판정 기준을 검증한다. 제한 없는 자연어 문장과 제한 없는 셸 코드가 같은 뜻인지는 추론하지 못한다. `G1: invoices reconcile`과 `CHECK: node -e "console.log('ok')"`의 조합은 문법상 올바르지만 의미상 쓸모가 없다.

- **결과를 직접 확인한다.** 검사가 제목에 적은 결과물, 서비스, 측정값을 직접 읽게 한다.
- **성공 전용 표시 문자열을 출력한다.** 스크립트가 모든 확인을 수행하고, 하나라도 실패하면 0이 아닌 상태로 끝나며, 모든 확인이 통과한 뒤에만 기대한 표시 문자열을 출력하게 한다.
- **음성 대조를 시험한다.** 부재 검사를 믿기 전에 같은 로직을 알려진 양성 픽스처(검사가 반드시 걸러 내야 하는 입력)에 실행해 실패하는지 확인한다. 그렇지 않으면 파일 누락, 잘못된 경로, 잘못된 패턴이 정상적인 부재처럼 보일 수 있다.
- **주어진 숫자는 따로 측정한다.** 작업 지시에서 옮겨 온 숫자를 그대로 그 숫자의 기대값으로 삼지 않는다. 스크립트가 원본 데이터에서 값을 계산하고, 완료 판정 규칙을 적용하고, 별도의 성공 표시 문자열을 출력하게 한다.
- **영향이 큰 수동 게이트는 위험도에 따라 검토한다.** 한 기여자가 게이트 17개짜리 강의 점검을 한 번 했을 때, 그 안의 유일한 수동 게이트가 가장 영향이 큰 게이트이기도 했다. 이 관찰은 검토를 더 엄격히 하라는 신호로 삼고, 검사 가능성과 위험 사이에 일반적인 상관관계가 있다는 증거로 삼지 않는다. 정확한 증거를 인용하고, 영향이 그만큼 크면 두 번째 검토를 받는다.
- **판정을 확정하는 증거를 남긴다.** 자동으로 기록한 성공 증거는 원본 출력이 아니라 출력 요약 해시를 저장한다. 수동 게이트에는 결과를 증명하는 가장 작은 민감하지 않은 사실을 기록하고, 게이트 파일에 로그 전체를 붙여 넣지 않는다.

### 작업 전에 게이트 파일 린트하기

위 규칙은 문장으로 적은 것이고, 이 프로젝트는 문장으로 된 층을 이미 가장 약한 층으로 본다. `gate-lint.mjs`는 그 규칙 중 기계적으로 확인할 수 있는 부분을 검사할 수 있게 만든다. 이 린터는 `CHECK:`를 실행하지 않는다. 게이트 파일을 읽고 판정 기준을 평가한다.

```text
node scripts/gate-lint.mjs GATES.md
node scripts/gate-lint.mjs --strict --json .unlazy/<scope>/gates/leaf-1.1.1.md
```

경고는 일부러 권고 수준의 어휘 신호로 둔다. 명령 전체가 고정된 출력을 내는 명령처럼 보이는 경우, 실패 출력에도 쓰이는 어휘로 기대값을 정한 경우, 경로처럼 생긴 정규 표현식을 슬래시로 감싼 경우, 제목이 결과가 아니라 활동을 적은 경우, 아무것도 측정하지 않는 숫자가 있는 경우, 게이트 파일 대부분이 수동 게이트인 경우에 경고한다. 린터는 명령을 셸 문법으로 파싱하지 않는다. 명령 접두어도, argv에 나타난 EXPECT 텍스트도 판정 기준이 실패할 수 없음을 증명하지 않는다.

기본 모드에서는 경고가 있으면 세부 내용과 함께 `LINT OK (<N> warning(s))`를 출력하고 `0`으로 끝난다. 그래서 아래의 자체 게이트는 모든 권고를 치명적 오류로 만들지 않고도 쓸모가 있다. `--strict`는 `LINT FINDINGS`를 출력하고 `1`로 끝나며 `LINT OK` 표시를 내지 않는다. 종료 코드 `2`는 사용법 오류나 공유 파서 실패를 뜻한다. 린트 지적은 게이트를 더 정확하게 다듬으라는 신호이지, 결과가 틀렸다는 증거가 아니다.

린트를 게이트로 넣어 게이트 파일이 스스로의 품질을 요구하게 만든다.

```markdown
- [ ] G0: 이 게이트 파일은 실패할 수 있는 결과를 적는다
  CHECK: node scripts/gate-lint.mjs GATES.md
  EXPECT: LINT OK
  EVIDENCE: pending
```

## 포기

포기는 승인된 작업 범위 안에서 필수 결과를 정말로 이룰 수 없을 때만 쓴다. 원래 게이트는 그대로 두고, 비어 있지 않은 이유 하나를 추가하고, 최종 보고에서 포기한 사실을 밝힌다. 포기는 눈에 보이게 남는 종료 상태의 인계이지 통과한 검사가 아니다. 포기하지 않은 게이트가 모두 충족이어도 `gate-check`는 `HANDOFF REQUIRED`를 출력하고 `1`로 끝난다. Stop 훅은 세션 종료를 허용하지만, 자유 형식의 이유가 아니라 전체 id만 담은 길이가 제한된 인계 메시지를 낸다. 포기한 자식을 부모의 `ALL MET` 판정 기준으로 승격시키거나 작업이 완전히 끝났다고 말하지 마라.

## 리프 게이트와 중간 노드 게이트

게이트는 그 증거가 있는 곳에 둔다. 리프(leaf, 트리 맨 아래의 작업 단위) 게이트 파일은 리프 하나를 증명하므로, 그 리프의 결과물을 읽고 그 리프가 선언한 `OWNS:` 경로만으로 충족할 수 있는 게이트만 넣는다. 부모는 반환된 리프를 재검증할 때 그 리프의 게이트 파일을 정확히 지정한다. 그래서 프로젝트 전체를 확인하는 검사를 리프에 끼워 넣으면, 리프별 `--reverify`가 반환된 리프 하나가 아니라 트리 전체를 다시 실행하게 된다.

여러 리프에 걸친 결과는 중간 노드(branch) 게이트 파일에 둔다. 거기서는 지정한 자식이 모두 반환된 뒤 한 번만 실행된다. 인터페이스 호환성, 엔드투엔드 동작, 합친 작업 전체의 회귀가 여기에 해당한다. `templates/gates-node.md`는 바로 이런 게이트를 위해 `N1`부터 `N6`까지를 남겨 둔다. 회귀 게이트나 엔드투엔드 게이트를 리프마다 복제하면, 합친 결과를 확인하는 중간 노드 게이트 하나보다 느리고 증거로서도 약하다.

## 동시 실행

`OWNS:`는 [parallel.md](parallel.md)의 조정 규약의 일부로만 쓴다. `OWNS:`는 명령의 파일 시스템 접근을 제한하지 않는다. 동시에 실행하는 리프는 서로 겹치지 않는 경로를 선언하고, 배정(dispatch) 전에 점유 신청(`--claim`)으로 그 경로를 점유(lease)하고, 검증 뒤에 해제(`--release`)해야 한다.
