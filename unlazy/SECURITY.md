# 보안 모델

Unlazy는 저장소에 적힌 검사를 실행한다. 안전 경계는 명시적인 검토와 승인이며, 명령 샌드박스가 아니다.

## `CHECK:` 줄은 코드다

`gate-check.mjs`는 각 `CHECK:`를 셸로 실행한다. 이때 검사기를 실행한 사용자의 권한과 물려받은 환경을 그대로 쓴다. 명령은 그 프로세스가 쓸 수 있는 파일, 네트워크 연결, 자격 증명, 개발 도구에 모두 접근할 수 있다.

게이트는 완료로 인정하려면 충족해야 하는 조건 한 항목이고, 게이트 파일은 게이트를 적은 파일이다. 물려받은 게이트 파일(다른 사람이나 이전 세션이 만든 것)을 쓰기 전에 다음 순서를 따른다.

1. `node <skill-dir>/scripts/gate-check.mjs --status <gate-file>`를 실행해 검사를 실행하지 않고 파싱하고 상태만 표시한다.
2. 모든 `CHECK:`, `EXPECT:`, `CWD:`를 읽는다. 검사가 호출하는 스크립트는 생성된 파일이나 무시 대상 파일까지 모두 살펴본다.
3. 셸이 `--shell`, `UNLAZY_SHELL`, 플랫폼 기본값 중 무엇으로 정해지는지 확인하고, 물려받은 `PATH`를 살펴본다. 정확히 일치하는 승인이 없는 새 판정 기준(oracle, 게이트 통과를 결정하는 CHECK, EXPECT, CWD 묶음)이면 일반 실행은 명령을 실행하지 않고 결정된 값만 출력한다. 하지만 정확히 일치하는 승인이 이미 있으면 명령이 실행되므로, 일반 실행이 언제나 모의 실행인 것은 아니다.
4. 결정된 판정 기준 전체가 예상한 내용이고 그 내용을 이해했을 때만 `--approve`로 실행한다.

승인 기록은 기본적으로 `~/.unlazy/approved` 아래에 저장된다. `UNLAZY_APPROVAL_DIR`로 다른 디렉터리를 고를 수 있지만, 그 디렉터리가 실제 디렉터리이고 소유자 전용이며 그 정규 경로가 정규 저장소 루트 밖에 있을 때만 허용된다. 검사기는 심볼릭 링크로 된 승인 저장소를 거부한다. 승인 기록은 링크를 따라가지 않는 디스크립터로 읽고, 읽은 뒤에도 그 디스크립터가 같은 소유자 전용이면서 링크가 하나뿐인 일반 파일을 가리킬 때만 받아들인다. 승인은 게이트 파일의 절대 경로와 게이트, 정확한 명령과 기대값, 결정된 작업 디렉터리와 셸, 타임아웃, 출력 상한과 정규식 상한, 정규식 워커의 시작 상한과 동시 실행 상한, 플랫폼, 물려받은 `PATH` 전체에 묶인다. 묶인 입력 중 하나라도 바뀌면 다시 검토하고 승인해야 한다. 승인은 실행에 동의한다는 뜻일 뿐이며, 명령이 자연어로 적힌 게이트 제목과 맞는다는 증거가 아니다.

승인은 명령이 호출하는 파일의 스냅숏을 남기지 않는다. 참조하는 스크립트, 생성된 파일, 실행 파일, 픽스처, 의존성이 바뀌어도 승인된 명령 문자열이 그대로면, 예전 승인으로 바뀐 내용을 실행할 수 있다. 명령을 실행하기 전에 이 의존성들을 다시 살펴본다. 게이트 파일의 자동 증거에는 파싱한 `CHECK:`, `EXPECT:`와 가공하지 않은 `CWD:`로 계산한 다이제스트가 따로 들어가며, 이 다이제스트는 환경에 따라 달라지지 않는다. `--status`와 Stop 훅은 명령을 실행하지 않고도 최신이 아니거나 바인딩되지 않은 정의를 거부한다. 하지만 둘 다 결과물을 다시 검증하지는 않는다. 이 다이제스트는 키 없이 계산하므로 정의가 바뀐 것을 감지할 뿐이며, 게이트 파일을 편집할 수 있는 사람을 상대로 결과를 인증하지는 못한다. 의존성이나 입력이 바뀌면 `--reverify`로 재검증한다. 워크플로에서 의존성이 최신인지 기계로 강제해야 하면, 기대하는 의존성 다이제스트를 승인 대상에 묶인 `CHECK:` 문자열에 직접 넣고 따로 신뢰하는 도구나 런타임으로 검증한다. 이것도 사용자가 설계한 검사 범위이며, unlazy가 간접 입력을 추적하는 것이 아니다.

승인 잠금과 점유(lease) 잠금은 자동으로 빼앗지 않고 실패로 처리한다(fail closed). 잠금을 가진 프로세스가 예기치 않게 종료되었다면, 그 잠금에 기록된 PID가 더 이상 실행 중이 아니고 그 잠금을 가질 수 있는 작업이 남아 있지 않은지 확인한 뒤에 주인이 없어진 잠금을 직접 지운다. unlazy가 동작하는 동안 잠금 디렉터리를 한꺼번에 지우지 마라.

신뢰할 수 없는 검사가 무엇을 하는지 알아보려는 이유만으로 그 검사를 실행하지 마라. 먼저 소스로 검토한다. 소스를 신뢰할 수 있는지 확실하지 않으면 쓰고 버리는 환경이나 더 강한 샌드박스를 쓴다.

## 셸과 환경

셸은 `--shell`, `UNLAZY_SHELL`, Node의 플랫폼 기본값 순서로 결정한다. 자식 프로세스는 `PATH`를 포함한 현재 환경을 물려받는다. unlazy를 실행한 터미널이 바뀌면 어떤 외부 도구가 선택되는지도 바뀔 수 있으며, Windows에서 특히 그렇다.

저장소에 있는 Node 스크립트와 명시적인 `CWD:` 값을 쓰는 편이 낫다. 셸을 따로 지정해도 없는 유틸리티가 설치되거나, 환경이 정리되거나, 명령 접근이 제한되지는 않는다. 실행 기록은 결정된 `PATH`를 표시 길이 상한까지 보여 준다. 저장되는 증거에는 결정된 셸, 작업 디렉터리, 종료 상태, 짧은 `PATH` 요약 해시, 매칭 결과, 그리고 `EXPECT:`에 넘긴 정확한 정규 문자열의 SHA-256과 바이트 수로 된 요약 해시가 들어간다. 가공하지 않은 stdout/stderr 내용과 그 문자열의 UTF-8 표현은 둘 다 1 MiB 상한 안에 들어가야 한다. 잘못된 바이트를 바꿔 넣은 문자와 두 스트림 사이에 넣는 줄바꿈도 UTF-8 표현의 크기에 포함되며, 상한을 넘으면 잘라 내지 않고 매칭 전에 거부한다. 성공한 출력의 원문은 화면에 다시 출력하지 않고 게이트 파일에도 쓰지 않는다. 실패 진단은 콘솔에만 나오고 길이가 제한되며, 터미널 제어 문자, 유니코드 줄 구분 문자, 양방향 재정의 문자를 제거한다. gate-lint도 이스케이프한 뒤 표시하는 필드마다, 그리고 돌려주는 발견 사항 개수에 상한을 두며, 전체 개수와 종료 코드의 의미는 그대로 유지한다.

정규식 기대값은 최대 네 개의 일회용 워커에서 실행한다. 250ms 매칭 시간 예산이 시작되기 전에 5초의 워커 시작 상한이 따로 적용되므로, `--jobs` 동시 실행 수가 커서 워커 시작이 늦어져도 역추적 시간 예산이 줄어들지 않는다. 시간이 초과된 워커는 종료되며 게이트를 통과로 인정할 수 없다.

셸과 성공 조건 계약 전체는 [references/gates.md](references/gates.md)를 본다.

## 스코프와 점유는 샌드박스가 아니다

스코프(scope)는 unlazy의 게이트 파일 탐색, 로그 대상, 훅 연결, 배정(dispatch) 실행 묶음(wave), 점유 이름표의 범위를 제한한다. 소유권 점유와 배정의 실행 시작 배리어(모든 실행 시작이 기록되기 전에는 결과를 기다리거나 읽지 못하게 하는 동기화 지점)는 이 규약을 스스로 따르는 도구끼리만 조정한다. 어느 쪽도 프로세스가 다른 경로를 읽거나 쓰는 것을 막지 못한다.

워크트리를 따로 두면 일반적인 경로 충돌은 줄일 수 있지만, 외부 캐시와 서비스는 여전히 함께 쓸 수 있다. 신뢰할 수 없는 코드에는 운영 체제, 컨테이너, 가상 머신 수준의 분리를 쓴다. [references/parallel.md](references/parallel.md)를 본다.

## Stop 훅과 로컬 상태

선택 사항인 Claude Code Stop 훅은 게이트 파일과 배정 상태를 훑은 뒤 진행 상태를 쓴다. 이 훅은 `CHECK:` 명령을 실행하지 않고, 실행 시점의 승인 판정 기준을 결정하지 않고, 승인 저장소를 살펴보지 않고, 간접 입력 결과물을 다시 검증하지 않고, 에이전트 세션을 만들지 않는다. 다만 `--status`가 검증하는 것과 같은 자동 증거 정의 다이제스트, 곧 파싱한 게이트 파일 내용만으로 계산하는 다이제스트는 검증한다. 결정된 세션 파이프라인에 미충족 게이트나 끝나지 않은 배정 실행 묶음이 있는 동안에는 Claude Code 문서에 나온 최상위 차단 결정을 내보내고, unlazy 자체 기준으로 진행 없는 차단이 여섯 번 쌓이면 차단을 해제한다. 게이트나 배정의 포기는 성공이 아닌 인계 상태다. Stop 훅은 인계만 있는 결과, 차단이 섞인 결과, 차단 해제 결과 모두에서 길이가 제한된 `HANDOFF REQUIRED` 시스템 메시지를 유지한다. 저장소에서 가져온 진단 문자열은 제어 문자를 제거하고 길이를 제한하며, 자유 형식의 포기 사유는 권한이 있는 메시지에 절대 복사하지 않는다.

스코프 모드에서는 런타임, 바인딩, 배정 파일과 덧붙이기만 하는 감사 파일이 `.unlazy/` 아래에 있다. 레거시 모드는 `.unlazy-hook-state.json`을 쓸 수 있다. 게이트 파일, 바인딩, 점유, 배정, 훅 상태를 읽을 때는 읽는 크기에 상한을 두고, 읽는 동안 바뀌지 않은 링크가 하나뿐인 일반 파일이어야 한다. 저장소에서 찾은 입력은 여기에 더해 정규 저장소 루트 안에 있어야 한다. 이름으로 지정한 잘못된 입력은 빈 파이프라인으로 취급해 조용히 넘어가지 않고 실패로 처리한다. 고정한 스코프의 지정 항목이 존재하지만 링크이거나, 특수 파일이거나, 읽을 수 없거나, 루트 밖에 있는 경우도 마찬가지다. 물리적으로 존재하지 않는 최신이 아닌 스코프만 훅의 비차단 대체 방식을 쓸 수 있다. 파일을 비차단 방식으로 열기 때문에 FIFO가 검사기나 훅을 멈춰 세우지 못한다. 상태를 쓸 때는 심볼릭 링크 디렉터리와 심볼릭 링크 대상을 거부한다. 상태 로그 덧붙이기는 링크가 여러 개인 파일도 거부하고, 쓰기 전에 연 디스크립터가 여전히 같은 링크가 하나뿐인 일반 파일을 가리키는지 확인한다.

Windows에서는 이름으로 가리킨 항목의 `lstat`이 계속 파일 종류, 심볼릭 링크 여부, 링크 수를 확인한다. 같은 파일인지 판단할 때는 원래 디스크립터와, 현재 이름으로 새로 연(파일을 만들지 않는) 두 번째 디스크립터의 BigInt `dev`와 `ino`를 엄격하게 비교한다. 두 번째 디스크립터를 열기 앞뒤로 이름 항목 스냅숏을 찍고, 이름 항목과 디스크립터의 inode가 정확히 같은지 확인하고, 디스크립터 스냅숏을 반복해서, 영향받는 경로 stat의 `dev`를 디스크립터 stat의 `dev`와 비교하지 않고도 일반적인 링크 경쟁 상태와 교체 경쟁 상태를 실패로 처리한다. 이것은 스냅숏 검사이며 원자적인 경로 분리가 아니다. 검사하는 동안 Windows 경로의 이름을 바꾸거나 다른 곳으로 돌릴 수 있는 공격자는, 두 `lstat` 호출이 원래 파일을 보는 동안 다른 볼륨에 있으면서 inode가 같은 대상을 두 번의 열기에 모두 보여 주거나, 마지막 스냅숏 뒤에 이름을 교체할 수 있다. Node 16은 Windows에서 링크를 따라가지 않는 열기도, 핸들에서 이름이나 볼륨을 얻는 네이티브 기능도 제공하지 않으므로, 네이티브 의존성 없이는 이 경쟁 상태를 막을 수 없다. Unix에서는 `O_NOFOLLOW`와 기존의 디스크립터-경로 검사를 그대로 쓴다. Node/libuv가 제공하는 `st_dev`/`st_ino` 추상화는 네이티브 볼륨 GUID와 128비트 파일 ID를 합친 것보다 약할 수도 있다. BigInt는 제공된 비트를 모두 보존하지만 런타임이 제공하지 않는 식별자를 되살릴 수는 없다. 두 경로를 모두 프로젝트의 무시 규칙에 넣는다. 바인딩의 세션 id와 배정 실행 묶음의 네이티브 에이전트 id는 전달 대상을 정하는 값일 뿐이며, 비밀 값이나 인증 토큰이 아니다.

각 검사는 분리된(detached) Node 감독 프로세스 아래에서 실행된다. 이 감독 프로세스는 셸과 물려받은 stdout/stderr 디스크립터가 모두 닫힐 때까지 프로세스 그룹 리더로 남는다. POSIX 그룹 정리는 바로 그 감독 프로세스가 아직 살아 있는 것이 확인될 때만 시도한다. 감독 프로세스가 끝난 뒤에는 그 PID/PGID 숫자가 재사용되었을 수 있으므로 절대 시그널을 보내지 않는다. Windows에서 타임아웃 정리를 할 때 unlazy는 호스트가 준 `SystemRoot`, `WINDIR`, `SystemDrive` 값이 서로 일치할 때만 드라이브 루트의 `<drive>:\Windows\System32\taskkill.exe`를 받아들인다. 임의의 루트, 없는 루트, 서로 맞지 않는 루트는 거부하며, 검사의 현재 디렉터리나 `PATH`에서는 절대 찾지 않는다. 이 실행기 환경 값들은 서로 일치하는지 보는 경계일 뿐이며, 어떤 OS인지 보증하는 암호학적 증명이 아니다. 위치를 확정할 수 없으면 이미 가지고 있는 자식 프로세스 핸들로 정리하고, 검사기는 그래도 자체의 상한이 있는 타이머로 최종 상태에 이른다. 시그널 요청이 성공했다고 해서 프로세스가 종료되었다고 보지 않는다.

## 설치 대상과 개인 정보

설치 스크립트는 명시적으로 실행했을 때만 Claude Code 설정을 바꾼다.

- 기본값: 현재 프로젝트의 `.claude/settings.local.json`
- `--global`: 현재 사용자의 Claude Code 설정
- `--shared`: 프로젝트의 `.claude/settings.json`

설치된 훅 명령에는 Node 실행 파일의 절대 경로와 이 사본의 `stop-hook.mjs` 절대 경로가 들어간다. 이 경로로 로컬 디렉터리 이름이 드러날 수 있다. 또 모든 협업자의 경로가 같지 않으면 `--shared` 설정은 다른 환경에서 쓸 수 없다. 기본 로컬 대상을 쓰고 `.claude/settings.local.json`을 프로젝트의 무시 규칙에 넣는 편이 낫다. Claude 설정 파일을 커밋하기 전에는 diff를 검토한다.

설치와 제거는 관련 없는 훅을 그대로 둔다. 새 핸들러에는 정확한 관리 표시가 붙는다. 레거시 핸들러는 예전 표시와 경로 형태가 정확히 일치할 때만 알아보며, 관련 없는 명령 안에 부분 문자열로 들어 있는 경우는 알아보지 않는다. 설치 스크립트는 기존 설정 파일을 링크를 따라가지 않고 열고, 디스크립터가 여전히 같은 링크가 하나뿐인 일반 파일을 가리키는지 확인하며, 형식이 잘못되었거나 지원하지 않는 설정 구조는 덮어쓰지 않고 거부한다. 쓰기는 원자적으로 하며, 기존 설정 파일을 교체하기 전에 그 옆에 `<settings-file>.unlazy.bak`을 만든다.

## 증거와 로그

명령 출력에는 개인 경로나 다른 민감한 문자열이 들어 있을 수 있다. 성공한 출력은 매칭에만 쓰고 다이제스트와 바이트 수로만 남긴다. 터미널의 성공 줄이나 게이트 증거에는 복사하지 않는다. 실패 진단은 여전히 로컬 터미널에 보이므로, 검사는 성공하든 실패하든 비밀 값을 출력하면 안 된다. 배정 상태에는 타임스탬프와 불투명한 호스트 핸들이 들어간다. 핸들에 프롬프트, 자격 증명, 결과 본문을 절대 넣지 마라. 검사는 간결한 성공 표시 문자열을 출력하고 비밀 값을 출력하지 않도록 설계한다. 게이트 파일, 배정 상태, 상태 로그는 커밋하거나 공유하기 전에 검토한다.

확정(`seal`)된 실행 묶음이 증명하는 것은, Unlazy가 반환을 받아들이기 전에 선언된 모든 리프(leaf, 트리 맨 아래의 작업 단위)마다 호스트가 서로 다른 네이티브 시작 핸들을 돌려주었다는 사실뿐이다. 정확한 CPU 동시 실행, 작업 에이전트의 정직성, 파일 시스템 분리, 게이트 성공, 올바른 통합은 증명하지 않는다. `dispatch.json`이 상태 전환의 기준이고, `status.log`는 그 뒤에 덧붙이는 감사 기록이다. 전환을 확정해 기록한 뒤에 이 덧붙이기가 거부되면, 명령은 성공하면서 길이가 제한된 경고를 낸다. 호출하는 쪽이 전환을 무작정 다시 실행하지 않고 상태를 살펴보게 하기 위해서다.

Unlazy는 원격 측정 데이터를 수집하거나 승인, 게이트, 훅 상태 기록을 서비스로 보내도록 만들어지지 않았다. `CHECK:` 명령은 임의의 코드이므로 스스로 네트워크 통신이나 로깅을 할 수 있다.

## 취약점 신고

일반적인 결함은 최소 재현 절차를 담아 GitHub 이슈를 연다. 재현 과정에서 비밀 값이 드러나거나 악용이 가능해지는 취약점이면, 이 저장소에서 GitHub 비공개 취약점 신고 기능을 쓸 수 있을 때 그 기능을 쓴다. 쓸 수 없으면 관리자에게 비공개 연락 방법을 묻는 최소한의 이슈를 열고, 비공개 채널이 생길 때까지 민감한 세부 내용은 적지 않는다.
