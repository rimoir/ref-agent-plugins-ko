# 검증 스킬 유지보수

기능 지도(feature map)는 앱이 바뀌는 순간 썩기 시작한다. 이 스킬은 `/create-verification-skill`로 만든 스킬(또는 기능 지도를 가진 프로젝트 로컬 검증 스킬)을 관리하는 유지보수 루프다. 엄밀함의 단위는 문장 하나하나가 아니라 기능이다. 모든 기능 파일을 소스로 다루고 모든 기능을 라이브로 실행하되, 글머리표 하나하나를 터미널에서 확인하지는 않는다.

## 결과

하나를 고르고 무엇인지 밝힌다.

- **clean**: 모든 기능이 소스와 라이브 커버리지를 받았고, 내보낼 만한 것이 없다. 브랜치도 PR도 없다.
- **changed**: 증명된 문서, 하네스, 지도 수정을 PR 하나로 낸다.
- **blocked**: 커버리지를 끝내지 못했거나 증명된 수정을 안전하게 내보내지 못했다. 무엇이 막았는지 정확히 밝힌다.

## 수정 범위

검증 스킬 자신의 디렉터리(그 SKILL.md, features/, 그 스킬이 소유한 하네스 스크립트)만 고친다. 실행 중에 제품 코드는 절대 고치지 않는다. 지도가 설명하는데 앱이 더는 하지 않는 동작은 문서 표류(지도를 고친다)이거나 제품 회귀(보고하고, 문서로 덮지 않는다) 둘 중 하나다.

## 점검 단계

0. **대상 찾기.** 유지보수할 검증 스킬을 찾는다. 본문에 실행·구동 절과 기능 지도가 있는 프로젝트 로컬 스킬이다(보통 `.cursor/skills/verify-*/`). 후보가 여럿이면 어느 것인지 묻는다. 하나도 없으면 대상을 지어내지 말고 멈춘 뒤 `/create-verification-skill`을 안내한다.

1. **색인 정리.** 기능 지도 README를 읽고 형제 파일을 glob으로 모은다. 빠진 항목, 남는 항목, 중복 항목, 죽은 항목을 고친다. 가볍게 하며, 목록을 생성하지 않는다.

2. **소스 wave.** 기능 파일마다 읽기 전용 subagent 하나를 동시에 띄운다. 각자 소스를 보고 "이 사용자 기능은 어떻게 동작하는가?"를 설명하고, 문서 표류로 보이는 것을 인용과 함께 표시하고, 간결한 라이브 검증 레시피 하나를 돌려준다. 자식은 앱을 구동하지도 파일을 고치지도 않는다. 반환 형태는 기능 요약 / 소스 진입점 / 표류 의심 또는 없음 / 레시피 하나다.

3. **맞추기.** 모든 기능 파일에 돌아온 요약이 있는지 확인한다. 겹치는 레시피를 실용적인 한 가장 적은 앱 상태로 합친다. 인용된 표류는 표본 점검한다. 깨끗하다는 주장은 다시 증명하지 않는다. 최근 변경을 훑어 지도에 빠진 사용자 화면을 찾는다. 빠졌다고 부르기 전에 구체적인 소스 경로를 요구한다.

4. **라이브 점검.** 소스가 깨끗해 보여도 반드시 한다. 구동은 전부 코디네이터가 맡는다. 검증 스킬 자체의 실행 모델을 따른다. 서버와 UI라면 오래 사는 인스턴스 하나를 직렬로 구동하고, 수명이 짧은 CLI라면 구동마다 새로 격리된 세션을 쓴다(정하는 것은 이 스킬이 아니라 그 스킬의 Launch 절이다). 모든 기능을 최소 한 번 실행하고, 어떤 실패가 나든 점검 내내 세 불변식을 지킨다. (1) 마지막으로 예상 밖의 일을 한 뒤 상태 점검을 하지 않은 인스턴스는 구동하지 않는다. 첫 구동 전에 doctor를 돌리고, 세션이 단위라면 새 세션마다 doctor를 돌리고, 구동이 실패하면 다시 doctor를 돌린다. doctor가 실패를 보지 못하는 경우(건강한 프로세스 위에서 UI 상태가 끼어 버린 경우)라면 바라기만 하지 말고 알려진 상태로 리셋하거나 다시 실행한다. (2) 지금까지 모은 증거는 어떤 정리 작업에서도 살아남아야 하며, 짐작하지 말고 정해진 위치에서 확인한다. (3) 구동이 시작한 것은 그 구동의 쓸모보다 오래 살지 않는다. 실패한 반복의 잔여물은 세션이 멈췄든, 종료됐든, 공유되든 치운다(공유 인스턴스라면 인스턴스가 아니라 잔여물을 치운다). 스킬 표류 때문에 생긴 doctor 실패는 표류다. 점검을 `blocked`로 부르기 전에 수정 범위 안에서 고치고 한 번 재시도한다. 이때 그 수정이 무효로 만든 것만 다시 시작하고 그 이상은 하지 않는다. 도달할 수 없는 기능은 구체적인 전제 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`이다. 지도에 그 전제 조건이 빠져 있다면 그것도 표류다. 분류에서 나온 하네스 수정은 내보내기 전에 라이브로 다시 구동한다. 최종 정리는 그런 재증명까지 포함해 실행의 마지막 구동이 끝난 뒤에 해서, 아무것도 실행보다 오래 살지 않게 한다(증거는 스킬에 따라 남긴다).

5. **분류.** 사용자 관점 설명이 틀렸거나 빠졌으면 문서 표류이므로 고친다. 동작은 하는데 하네스가 구동하지 못하면 하네스 공백이므로 고친다. 하네스 수정은 생성 때와 같은 helpers 규칙을 따른다(스크립트는 실행 가능하게, 호출법은 스킬 본문에 문서화). 앱 동작이 실제로 망가졌다면 제품 공백이다. 사용자에게 기록해 두고 이 PR에는 넣지 않는다.

6. **내보내거나 멈추기.** changed라면 증명된 수정을 PR 하나로 내며, 먼저 바뀐 파일을 모두 다시 읽는다. clean이나 blocked라면 PR 없이 결과와 커버리지를 정직하게 보고한다.

간결한 실행 메모(다룬 기능, 도달 불가 전제 조건, 확인된 표류, 결과)를 임시 위치에 남긴다. 커밋하지 않는다.
