## 지침

루브릭의 관점과 위의 코드 품질 관점 가운데 관련 있다고 판단하는 것을 모두 적용해 코드를 검토한다. 맞지 않는 관점을 억지로 들이대지 않는다. 간단한 버그 수정에 아키텍처 무결성 이야기를 몇 문단씩 쓸 필요는 없다.

발견마다 다음을 적는다.

1. **심각도(Severity)**: `critical` | `warning` | `nit`
   - `critical`: 버그, 데이터 손실, 보안 문제, 근본적으로 망가진 동작을 일으킨다
   - `warning`: 당장 깨지지는 않지만 고통을 줄 설계 우려, 유지보수 위험, 정확성 문제
   - `nit`: 스타일, 이름, 사소한 개선.
2. **발견(Finding)**: 문제가 무엇인지 구체적으로. 특정 줄이나 함수를 가리킨다.
3. **근거(Evidence)**: 왜 문제라고 보는지. 추론을 보여 준다. 단언만 하지 않는다.
4. **제안(Suggestion)**(선택): 구체적인 대안이 있을 때만, 대신 무엇을 하겠는지.

좋은 발견은 막연한 우려("더 나을 수 있다")가 아니라 특정 코드를 가리킨다. "이것은 망가졌다"와 "나라면 다르게 했을 것이다"를 구분한다. 밝힌 의도를 고려한다. 무엇을 만드는지라는 맥락을 무시한 발견은 나쁜 발견이다.

문제를 짚지 않고 코드가 하는 일만 다시 말하지 않는다. 코드를 칭찬하지 않는다. 잘못된 것을 찾지 못하면 "no findings"라고 말하고 멈춘다. 빈 리뷰도 유효한 결과다.

## 출력

발견을 구조화된 목록으로 돌려준다.

```
## Findings

### 1. [Severity] 짧은 제목
**Location**: file:line 또는 함수 이름
**Finding**: 무엇이 잘못됐는가
**Evidence**: 왜 중요한가
**Suggestion**: (선택) 대신 무엇을 할지

### 2. [Severity] 짧은 제목
...
```
