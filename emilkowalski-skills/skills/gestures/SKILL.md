# 제스처로 움직이는 UI

물리적으로 느껴지는 제스처를 만드는 방법이다. 제스처는 직접 조작이다. 손가락이 닿아 있는 동안 UI는 곧 손가락이고, 손가락이 떨어지는 순간 물리가 넘겨받는다. 아래 규칙은 모두 이 구분에서 나온다.

## 첫 결정: 직접 만들까, 있는 해법을 쓸까?

드로어 제스처를 *제대로* 만들려면 관성 기반 드래그, 드래그 진행도에 맞춘 오버레이 불투명도, 속도를 고려한 닫기, 포커스 가두기, Escape로 닫기가 필요하다. 오후 한나절이 아니라 몇 주짜리 엣지 케이스다. **바텀 시트나 드로어에는 기본으로 [Vaul](https://vaul.emilkowal.ski/)을 쓴다.** Vaul은 바로 이것을 직접 짜기 어려워서 생겼다. 제스처를 직접 만드는 것은 그 상호작용을 다루는 라이브러리가 없을 때(직접 만든 스와이프 카드, 맞춤형 드래그 상호작용)뿐이다. 확신이 없으면 `../pick-ui-library/SKILL.md`를 읽는다.

## 모든 제스처의 두 단계

만드는 제스처마다 이 구분을 따라간다. 두 단계를 섞는 것이 제스처가 어색하게 느껴지는 가장 큰 원인이다.

```
지금 포인터가 눌려 있는가?
├── 예 → 추적(TRACK) 단계: 위치가 포인터에 1:1로 대응한다.
│         이징 없음. 지속 시간 없음. 스프링 없음. 요소가 곧 손가락이다.
└── 아니요 → 놓기(RELEASE) 단계: 물리가 모션을 마무리한다.
          놓을 때의 속도를 넘겨받은 스프링, 또는 컴포넌트가 CSS로만 되어 있으면
          (Vaul, 길게 눌러 확인하기) CSS 트랜지션. 키프레임은 절대 쓰지 않는다.
```

### 추적 단계 규칙

- **1:1은 정말 1:1이다.** 위치는 `useMotionValue`(또는 `transform` 직접 쓰기)로 움직이고, 스프링이나 트랜지션은 절대 쓰지 않는다. 추적하는 동안 스프링을 쓰면 요소가 손가락 뒤로 끌려와 따로 노는 느낌이 든다. 시럽 속에서 무언가를 끄는 것 같다.
- **드래그하는 요소에 `transform`을 직접 쓴다.** 자식을 움직이려고 부모의 CSS 변수를 바꾸지 않는다. CSS 변수는 상속되므로 값이 바뀔 때마다 모든 자손의 스타일을 다시 계산한다. 바로 이 버그 때문에 Vaul은 목록 항목이 20개쯤을 넘으면 드래그가 느려졌다. 요소에 `transform`을 직접 쓰자 고쳐졌다.
- **move 이벤트마다 React 상태를 바꾸지 않는다.** pointermove마다 다시 렌더링하면 프레임이 떨어진다. 모션 값과 스타일 직접 쓰기는 렌더링 주기를 거치지 않는다.
- **가장자리에서는 러버밴드를 건다.** 경계를 넘겨 드래그하면 딱 멈추지 말고 거리의 일부만 움직여야 한다(Motion: `dragElastic` ≈ 0.2). 딱 멈추면 벽에 부딪힌 느낌이 든다. 저항은 "더 갈 데가 없다"는 것을 물리적으로 전한다.

### 놓기 단계 규칙

- **직접 만든 드래그는 제스처 속도를 넘겨받은 스프링으로 끝낸다.** 요소는 손가락에서 움직이던 속도 그대로 떠나야 한다. 여기서 고정 지속 시간 이징을 쓰면 어떻게 튕겨도 똑같이 내려앉아서 가짜처럼 보인다.
- **거리나 속도 중 하나만 넘어도 닫는다.** 거리 임계값(이동 범위의 40–50%쯤)을 넘기면 닫고, 짧은 거리라도 빠르게 튕기면 닫는다. Motion에서는 `onDragEnd`의 `info.offset`과 `info.velocity`에서 둘 다 읽는다. 거리만 보는 임계값은 튕기는 동작을 무시하는 것처럼 느껴진다.
- **바운스는 드래그가 끝날 때만 쓴다.** 드래그는 힘을 가한다. 벽에 공을 던지는 것과 같아서, 놓을 때 살짝 튕기면 물리적으로 느껴진다. 같은 요소라도 버튼으로 닫으면 바운스는 **0**이다. 가한 힘이 없기 때문이다. 바운스는 0.1–0.3으로 두고, 바운스는 요소 크기에 반비례한다는 것을 기억한다(작은 요소는 같은 느낌을 주려면 바운스가 더 필요하다).
- **제자리로 돌아오는 것은 빠르게 한다.** 제스처가 임계값을 넘지 못하면 스프링으로 재빨리 돌아온다. 느리게 돌아오면 UI가 슬로 모션으로 사용자에게 반대하는 것처럼 느껴진다.

## 중단 가능성은 양보할 수 없다

사용자는 닫히는 시트를 도중에 잡아서 다시 끌어올 수 있어야 한다. 스프링은 이것을 해낸다. 날아가는 도중에 목표가 바뀌어도 현재 속도를 유지하므로 방향 전환이 매끄럽다. CSS `@keyframes`는 0에서 다시 시작해서 도중에 잡을 수 없다. Sonner 초기의 CSS 등장 애니메이션이 두 번째 토스트가 올 때 토스트를 튀게 만든 이유가 이것이다. **제스처가 건드릴 수 있는 것에는 절대 키프레임 애니메이션을 쓰지 않는다.** CSS 트랜지션과 스프링만 쓴다.

## 연결된 값

드래그하는 요소가 혼자인 경우는 드물다. 오버레이가 흐려지고 뒤의 페이지가 작아진다. 이런 값은 따로 애니메이션하지 말고 드래그 진행도에서 끌어낸다.

```jsx
const y = useMotionValue(0);
const overlayOpacity = useTransform(y, [0, drawerHeight], [1, 0]);
```

기준이 하나면 오버레이는 늘 드로어가 닫힌 만큼 정확히 흐려진다. 제스처 도중에도, 사용자가 방향을 되돌릴 때도 그렇다. 따로 도는 두 애니메이션은 제스처가 중단되는 순간 어긋난다.

## Motion 드래그 props

```jsx
const y = useMotionValue(0);

<motion.div
  drag="y"
  style={{ y }}
  dragConstraints={{ top: 0 }}
  dragElastic={0.2}
  dragMomentum={false}
  onDragEnd={(e, info) => {
    if (info.offset.y > threshold || info.velocity.y > 500) dismiss();
    else animate(y, 0, { type: 'spring', duration: 0.5, bounce: 0.2, velocity: info.velocity.y });
  }}
/>
```

`dragMomentum`은 기본으로 켜져 있다. 튕겨 보내는 카드에는 맞고 단순히 위치를 옮기는 데는 틀리다. 손가락이 멈춘 곳에 요소가 멈춰야 하면 끈다. 위 예시는 `onDragEnd`가 놓기를 자체 스프링에 넘기기 때문에 끈다. `dragConstraints`는 ref나 경계 객체를 받는다.

## 스프링 없는 시트: Vaul 곡선

Vaul은 크기를 작게 유지하려고 iOS 시트를 순수 CSS로 흉내 낸다. **500ms** 동안 `cubic-bezier(0.32, 0.72, 0, 1)`이다. 이 곡선은 시작이 아주 가파르다. 그래서 500ms라는 지속 시간에도 빠릿하게 느껴지면서 스프링처럼 부드럽게 내려앉는다. 여기서 규칙 두 가지가 나온다.

- **작은 떠 있는 드로어**(화면 가장자리에 붙지 않은 것)는 200ms쯤으로 덮어쓴다. 500ms iOS 타이밍은 가장자리에 붙은 전체 너비 시트에서만 맞게 읽힌다.
  ```css
  [data-vaul-drawer]  { transition: transform 0.2s cubic-bezier(0.165, 0.84, 0.44, 1); }
  [data-vaul-overlay] { transition: opacity  0.2s cubic-bezier(0.165, 0.84, 0.44, 1); }
  ```
- **컴포넌트는 하나의 덩어리처럼 느껴져야 한다.** 드로어가 200ms에 열리면 높이 변화와 콘텐츠 크로스페이드도 같은 타이밍 계열에 있어야 한다. 하위 애니메이션 하나만 느려도 전체가 망가진 것처럼 느껴진다.

드로어 안의 버튼을 누를 때 드래그가 시작되지 않도록 상호작용하는 자식에는 `data-vaul-no-drag`를 붙인다.

## 공간 일관성

**요소는 들어온 방향으로 닫힌다.** Sonner 토스트는 아래에서 위로 미끄러져 들어오므로 아래로 스와이프하면 닫힌다. 등장과 퇴장이 같은 축을 공유하기 때문에 설명 없이도 제스처를 발견하고 직관적으로 느낀다. 요소가 한 번도 움직인 적 없는 축으로 닫는 제스처는 배워야 한다. 등장을 거꾸로 되짚는 제스처는 *느껴진다*.

## 길게 누르는 제스처는 비대칭이다

길게 눌러 삭제하기 같은 길게 누르는 상호작용은 누르는 동안 **`linear`** 를 쓴다. 애니메이션이 흐르는 시간을 보여 주는데 시간은 선형으로 흐른다. 다른 곡선은 남은 시간을 속인다. 끝나기 전에 손을 떼면 `ease-out`으로 빠르게 되돌린다. 의도적인 단계는 느리고 정직하고, 취소는 즉각적이다. 여기서 대칭 타이밍은 버그다.

## 터치 체크리스트

내보내는 제스처마다 확인한다.

- **실제 휴대폰에서 테스트한다.** 로컬 IP로 개발 서버에 접속한다. 트랙패드 시뮬레이션은 터치를 제대로 보여 주지 않고, 60Hz 데스크톱 모니터는 120Hz 휴대폰에서 드러나는 불투명도 트랜지션의 거친 부분을 숨긴다.
- **터치 영역은 44×44px 이상.** 작은 시각적 대상은 레이아웃을 키우지 말고 보이지 않는 `::before` 히트박스로 넓힌다.
- 브라우저가 기본 스크롤로 제스처와 다투지 않게 드래그 축에 맞춰 **`touch-action`** 을 건다(세로 드래그에는 `touch-action: pan-x` 등).
- **hover 효과는** `@media (hover: hover) and (pointer: fine)` 뒤로 **막는다.** 터치는 탭할 때 가짜 hover를 일으킨다.

## 모션 줄이기

추적은 직접 조작이다. 모션을 만드는 것이 사용자이므로 추적은 그대로 둔다. 줄이는 것은 관성으로 튕겨 가는 움직임, 바운스, 제스처 주변의 장식 모션이다. `prefers-reduced-motion`에서 손을 떼면 통통 튀는 스프링 대신 짧은 불투명도나 위치 변화로 자리를 잡는다.

## 그래도 어색하게 느껴질 때

"이상한" 스프링은 보통 `damping`을 올리면 고쳐진다. 끊기는 제스처는 성능 문제다. 위의 추적 단계 규칙을 먼저 확인하고, 그다음 `animation-performance` 스킬을 쓴다. 이름 붙이기 어려운 느낌을 진단하려면 제스처를 녹화해서 프레임 단위로 넘겨 본다.
