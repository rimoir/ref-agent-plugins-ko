### Shipping

**머지되는 것은 네 책임이다. PR마다 따로 검증하고, 루트에서부터 검증된 구간만 머지한 뒤 큐에서 손을 뗀다.**

`playbooks/babysit.md` 다음에 오는 나머지 절반이다.

1. **forge를 정하고 PR마다 따로 검증한다.** 기본은 GitHub CLI(`gh`)다. `command -v origin`이 성공하고 Origin이 레포를 찾을 수 있으면 PR 조회, watch, 수정, 머지 작업에 `origin pr ...`을 쓴다. 그렇지 않으면 `gh`를 쓰고 대체했다는 사실을 기록한다. Graphite(`gt`)를 요구하지 않는다. PR마다 subagent 하나를 쓰고 묶지 않는다. 각각 Cursor 클라우드 에이전트이며, 맞는 control skill(`cursor-team-kit`의 `control-ui`나 `control-cli` 등)로 실제 화면을 parent와 head에서 비교하며 조작한다. 각자 `PASS`, `PASS+NOTES`, `FAIL` 중 하나를 돌려주고 그 판정을 자기 PR에 올린다. 안전하다는 것은 코드를 쓰지 않은 에이전트가 판정했다는 뜻이다. CI 통과는 판정이 아니고, 승인한 봇 리뷰도 판정이 아니다.
2. **맨 아래에서 시작해 끊김 없이 검증된 구간만 머지한다.** 머지되지 않은 가장 아래 PR부터 위로 올라가다가 통과 판정이 없는 첫 PR에서 멈춘다. `PASS`와 `PASS+NOTES`는 둘 다 통과다. 검증되지 않은 PR 위에 있는 검증된 PR은 머지할 수 없다. 상한선(ceiling)을 PR 번호로 보고하고, 무엇이 사슬을 끊는지 말한다.
3. **각 판정이 여전히 그 패치를 설명하는지 다시 확인한다.** 판정 시점의 head SHA, base SHA, 그 PR의 base에서 head까지 diff의 안정적인 `git patch-id`를 기록한다. rebase나 base 대상 변경은 SHA를 다시 쓰고, 검사 하나 건드리지 않고도 판정을 조용히 무효로 만들 수 있다. PR을 머지하기 전에 기록한 patch-id와 현재 base-to-head patch-id를 비교한다. 두 패치가 테스트, 문서, lint 설정만 다르면 각 레인이 돌린 것을 빌드한다. 판정 SHA에서 두 번, 현재 head에서 한 번 빌드한다. 판정 SHA의 두 빌드에서도 나타나는 차이거나 내장된 커밋 SHA라면 그 차이는 소음이다. 파일 단위가 아니라 차이 하나하나를 판단하고, 소음의 종류마다 해당 파일과 함께 보고한다. 소음만 다르면 그 레인의 결과는 유효하고, 검사와 변경 리뷰는 새로 돌린다. dev 서버나 그 밖에 빌드 산출물이 없는 것에서 나온 레인 결과는 재사용하지 않는다. 그 레인은 다시 돌린다. 패치가 바뀌었으면 나머지는 모두 다시 검증한다. 바뀌지 않았으면 코드 판정은 유지하되 현재 head에서 mergeability와 CI를 다시 돌린다. 커밋 메시지가 같다거나 옛 SHA의 통과 검사가 있다는 것으로 대신하지 않는다.
4. **맨 아래 PR만 준비한다.** 현재 trunk를 fetch한다. 필요하면 검증된 가장 아래 브랜치를 정확한 trunk 끝으로 rebase하고 push한 뒤, `origin pr edit <pr> --base <trunk>`나 `gh pr edit <pr> --base <trunk>`로 그 PR만 trunk를 대상으로 바꾼다. push 뒤에 3단계를 다시 돌린다. 하위 PR은 아직 대상 변경, 예약, 머지를 하지 않는다.
5. **한 번에 PR 하나씩 머지한다.** 맨 아래 PR이 지금 머지 가능하면 `origin pr merge <pr> --squash`나 `gh pr merge <pr> --squash`로 squash한다. 요구 조건이 아직 돌고 있고 사용자가 merge-when-ready를 요청했으면 `origin pr merge <pr> --squash --auto`나 `gh pr merge <pr> --squash --auto`로 그 PR만 예약한다. Origin의 `--auto`는 Origin merge-when-ready다. GitHub의 `--auto`는 GitHub auto-merge다. 그 PR이 머지될 때까지 기다린 뒤 다음 PR을 준비한다.
6. **GitHub `autoMergeRequest`를 스택 준비 상태로 읽지 않는다.** 기껏해야 GitHub PR 하나에 GitHub auto-merge가 요청되었다는 뜻이다. Origin merge-when-ready가 예약되었는지, 하위 PR이 큐에 들어갔는지, 패치 판정이 최신인지, 이어진 스택이 안전한지는 증명하지 못한다. 현재 맨 아래 PR에 대한 활성 forge의 상태를 확인하고, 활성 forge가 보고하지 못하면 상태를 알 수 없다고 말한다.
7. **머지할 때마다 다시 계산한다.** trunk를 fetch하고, 머지된 SHA가 있는지 확인하고, 고정해 둔 아래에서 위로의 목록에서 머지된 PR을 빼고, 새 맨 아래 PR의 base, head, 검사, patch-id를 살펴본다. 호스트가 자식 PR의 대상을 자동으로 바꿀 수도 있지만 그랬다고 가정하지 않는다. 그 PR 하나에 3~6단계를 반복한다. 독립 작업은 이 사슬 밖에 두고 따로 출시한다.
8. **현재 최전선 PR이 머지되거나 실패할 때까지 지켜본다. 그 주변의 큐를 바꾸지 않는다.** Origin에서는 `origin pr view <pr> --checks --comments`와 `origin pr checks <pr> --watch`를 쓰고, PR이 merged나 blocked를 보고할 때까지 다시 읽는다. GitHub에서는 `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>`를 이벤트로 깨우는 용도로만 쓰고, 깰 때마다 `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest`를 조회한다. `mergedAt`이 null이 아니거나 `state`가 `MERGED`가 될 때까지 `READY`는 무시한다. 그때에만 7단계를 돌린다. 확정 실패는 `state`가 `mergedAt` 없이 `CLOSED`일 때, auto-merge가 더 이상 대기 중이 아닌 상태에서 필수 검사가 `FAILURE`나 `CANCELLED`로 끝나 머지를 막을 때, auto-merge 대기 없이 `mergeStateStatus`가 `UNSTABLE`이나 `DIRTY`일 때뿐이다. 검사가 대기 중이거나 auto-merge가 예약된 동안의 `BLOCKED`는 실패가 아니다. 여기서는 Babysit의 큐 대기 `WAITING`/`merge-queue` 중단 조건을 쓰지 않는다. 동적 모드의 `/loop`로 지켜보기를 유지한다. 머지마다 새 상한선과 함께 보고한다. 큐가 멈추면 바꾸기 전에 진단한다.
9. **상한선에서 멈춘다.** 검증된 구간이 머지되면 무엇이 머지되었는지, 검증되지 않은 다음 PR이 무엇인지, 그것을 검증하려면 무엇이 필요한지 보고한다. 구간을 늘리려면 1단계부터 새로 진행한다.

**답변:** 검증된 구간과 그 상한선, 각 PR의 판정과 판정한 주체, 무엇을 예약했고 어떻게 확인했는지, 무엇이 머지되었는지, 다음 빈틈에 무엇이 필요한지.
