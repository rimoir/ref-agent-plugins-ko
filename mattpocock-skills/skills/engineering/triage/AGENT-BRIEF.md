# 에이전트 작업 지시서 쓰기

에이전트 작업 지시서(agent brief)는 GitHub 이슈나 PR이 `ready-for-agent`로 옮겨질 때 올리는 구조화된 댓글이다. AFK 에이전트(사람 없이 에이전트 혼자 진행)가 작업할 때 기준으로 삼는 최종 스펙이다. 원래 본문과 논의는 참고용 맥락일 뿐이고, 에이전트가 따라야 할 기준은 에이전트 작업 지시서다.

작업 지시서는 **에이전트가 무엇을 해야 하는지** 적고, 이슈와 PR 모두에 적용된다. 이슈라면 변경을 처음부터 만드는 일이다. PR이라면 *이미 있는 diff에* 남은 일이다. diff를 마무리하고, 빠진 부분을 채우고, 리뷰 지적 사항을 반영한다. 원칙은 어느 쪽이든 같다. 차이는 아래 PR 예시에서 볼 수 있다.

## 원칙

### 정확한 위치보다 오래 유효한 설명

이슈는 며칠에서 몇 주 동안 `ready-for-agent`에 머물 수 있다. 그동안 코드베이스는 바뀐다. 파일 이름이 바뀌거나, 파일이 옮겨지거나, 리팩터링되더라도 쓸모가 남도록 작업 지시서를 쓴다.

- 인터페이스, 타입, 동작 규약을 설명**한다**
- 에이전트가 찾거나 고쳐야 할 구체적인 타입, 함수 시그니처, 설정 구조의 이름을 적**는다**
- 파일 경로를 적**지 않는다**. 금방 실제와 달라진다
- 줄 번호를 적**지 않는다**
- 지금의 구현 구조가 그대로 유지된다고 가정하**지 않는다**

### 절차가 아니라 동작

시스템이 **무엇을** 해야 하는지 설명하고, **어떻게** 구현할지는 적지 않는다. 에이전트는 코드베이스를 새로 살펴보고 구현 방식을 스스로 정한다.

- **좋음:** "`SkillConfig` 타입이 `CronExpression` 타입의 선택 필드 `schedule`을 받아야 한다"
- **나쁨:** "src/types/skill.ts를 열고 42번째 줄에 schedule 필드를 추가한다"
- **좋음:** "사용자가 인자 없이 `/triage`를 실행하면 확인이 필요한 이슈 요약을 볼 수 있어야 한다"
- **나쁨:** "메인 핸들러 함수에 switch 문을 추가한다"

### 빠짐없는 인수 기준

에이전트는 언제 작업이 끝나는지 알아야 한다. 모든 에이전트 작업 지시서에는 구체적이고 테스트할 수 있는 인수 기준이 있어야 한다. 기준 하나하나를 따로 검증할 수 있어야 한다.

- **좋음:** "`gh issue list --label needs-triage`를 실행하면 첫 분류를 거친 이슈가 나온다"
- **나쁨:** "분류가 제대로 동작해야 한다"

### 명시적인 범위 경계

범위 밖인 것을 적는다. 그래야 에이전트가 요청하지 않은 기능을 덧붙이거나 인접 기능을 멋대로 가정하지 않는다.

## 템플릿

```markdown
## 에이전트 작업 지시서

**유형:** bug / enhancement
**요약:** 무엇을 해야 하는지 한 줄 설명

**현재 동작:**
지금 어떻게 동작하는지 적는다. 버그라면 고장 난 동작이다.
개선이라면 새 기능의 바탕이 되는 현재 상태다.

**원하는 동작:**
에이전트의 작업이 끝난 뒤 어떻게 동작해야 하는지 적는다.
경계 사례와 오류 상황을 구체적으로 적는다.

**핵심 인터페이스:**
- `TypeName`: 무엇을 왜 바꿔야 하는지
- `functionName()` 반환 타입: 지금 무엇을 반환하고 앞으로 무엇을 반환해야 하는지
- 설정 구조: 새로 필요한 설정 옵션

**인수 기준:**
- [ ] 구체적이고 테스트할 수 있는 기준 1
- [ ] 구체적이고 테스트할 수 있는 기준 2
- [ ] 구체적이고 테스트할 수 있는 기준 3

**범위 밖:**
- 이 이슈에서 바꾸거나 다루면 안 되는 것
- 관련 있어 보이지만 별개인 인접 기능
```

## 예시

### 좋은 에이전트 작업 지시서 (bug)

```markdown
## 에이전트 작업 지시서

**유형:** bug
**요약:** 스킬 설명을 자를 때 단어 중간에서 잘려 출력이 깨진다

**현재 동작:**
스킬 설명이 1024자를 넘으면 단어 경계와 상관없이 정확히 1024자에서
잘린다. 그래서 설명이 단어 중간에서 끝난다
(예: "Use when the user wants to confi").

**원하는 동작:**
1024자 이전의 마지막 단어 경계에서 자르고, 잘렸다는 표시로
"..."를 붙인다.

**핵심 인터페이스:**
- `SkillMetadata` 타입의 `description` 필드: 타입은 바꿀 필요가 없다.
  다만 이 필드를 채우는 검증과 처리 로직이 단어 경계를 지켜야 한다
- SKILL.md frontmatter를 읽고 description을 뽑아내는 모든 함수

**인수 기준:**
- [ ] 1024자 미만인 설명은 바뀌지 않는다
- [ ] 1024자를 넘는 설명은 1024자 이전의 마지막 단어 경계에서
      잘린다
- [ ] 잘린 설명은 "..."로 끝난다
- [ ] "..."를 포함한 전체 길이가 1024자를 넘지 않는다

**범위 밖:**
- 1024자 제한 자체를 바꾸는 일
- 여러 줄 설명 지원
```

### 좋은 에이전트 작업 지시서 (enhancement)

```markdown
## 에이전트 작업 지시서

**유형:** enhancement
**요약:** 거절한 기능 요청을 기록하는 `.out-of-scope/` 디렉터리 지원 추가

**현재 동작:**
기능 요청을 거절하면 이슈를 `wontfix` 라벨과 댓글과 함께 닫는다.
결정과 이유를 남기는 영구 기록이 없다. 나중에 비슷한 요청이 오면
메인테이너가 이전 논의를 기억해 내거나 찾아봐야 한다.

**원하는 동작:**
거절한 기능 요청을 `.out-of-scope/<concept>.md` 파일에 기록한다.
이 파일에는 결정, 이유, 그 기능을 요청한 모든 이슈의 링크를 담는다.
새 이슈를 분류할 때 이 파일들과 일치하는지 확인한다.

**핵심 인터페이스:**
- `.out-of-scope/`의 마크다운 파일 형식: 각 파일에는
  `# 개념 이름` 제목, `**결정:**` 줄, `**이유:**` 줄,
  이슈 링크를 담은 `**이전 요청:**` 목록이 있어야 한다
- 분류 워크플로는 초반에 `.out-of-scope/*.md` 파일을 모두 읽고
  들어온 이슈를 개념의 유사성으로 비교해야 한다

**인수 기준:**
- [ ] 기능을 wontfix로 닫으면 `.out-of-scope/`에 파일을 만들거나 갱신한다
- [ ] 파일에 결정, 이유, 닫은 이슈의 링크가 들어간다
- [ ] 일치하는 `.out-of-scope/` 파일이 이미 있으면 중복 파일을 만들지 않고
      새 이슈를 그 파일의 "이전 요청" 목록에 추가한다
- [ ] 분류 중에 기존 `.out-of-scope/` 파일을 확인하고, 새 이슈가 이전 거절과
      일치하면 알린다

**범위 밖:**
- 자동 비교 (일치 여부는 사람이 확인한다)
- 이전에 거절한 기능 다시 열기
- 버그 보고 (`.out-of-scope/`에는 enhancement 거절만 기록한다)
```

### 좋은 에이전트 작업 지시서 (PR)

PR이면 "현재 동작"에 diff의 현재 상태를 적고, 에이전트에게 처음부터 만들지 말고 diff를 마무리하거나 고치라고 요청한다.

```markdown
## 에이전트 작업 지시서

**유형:** enhancement
**요약:** 기여자가 만든 `triage list`의 `--json` 출력 플래그 마무리

**현재 동작:**
이 PR은 이슈 목록을 JSON으로 직렬화하는 `--json` 플래그를 추가한다. 정상
경로는 동작하고 diff도 프로젝트의 명령 구조에 맞는다. 빠진 부분이 남아 있다.
오류가 여전히 사람이 읽는 텍스트로 출력되고(JSON이 아님), 새 플래그에
테스트가 없다.

**원하는 동작:**
`--json`을 주면 모든 출력(오류 포함)이 stdout에 올바른 형식의 JSON으로 나오고,
명령의 종료 코드는 바뀌지 않는다. 플래그가 없으면 기존의 사람이 읽는 출력은
그대로다.

**핵심 인터페이스:**
- `--json`일 때 명령의 오류 경로는 일반 텍스트 오류 대신
  `{ "error": string }`을 출력해야 한다
- PR이 이미 추가한 직렬화 함수를 재사용한다. 두 번째 직렬화 함수를 만들지 않는다

**인수 기준:**
- [ ] `triage list --json`이 성공과 오류 모두에서 올바른 JSON을 출력한다
- [ ] 종료 코드가 JSON이 아닌 명령과 같다
- [ ] `--json` 성공 출력과 오류 사례 하나를 테스트가 다룬다
- [ ] 기본(JSON이 아닌) 출력은 바이트 단위까지 바뀌지 않는다

**범위 밖:**
- 다른 명령에 `--json` 추가
- PR이 이미 정한 성공 응답의 JSON 구조 변경
```

### 나쁜 에이전트 작업 지시서

```markdown
## 에이전트 작업 지시서

**요약:** 분류 버그 수정

**할 일:**
분류 기능이 고장 났다. 메인 파일을 보고 고친다.
150번째 줄 근처 함수에 문제가 있다.

**바꿀 파일:**
- src/triage/handler.ts (150번째 줄)
- src/types.ts (42번째 줄)
```

나쁜 이유:
- 유형이 없다
- 설명이 모호하다("분류 기능이 고장 났다")
- 금방 실제와 달라질 파일 경로와 줄 번호를 적었다
- 인수 기준이 없다
- 범위 경계가 없다
- 현재 동작과 원하는 동작 설명이 없다
