# 로직 프로토타입

누구나 버튼을 눌러 상태 모델을 조작해 볼 수 있는, 필요한 것을 모두 담은 HTML 파일 하나(**공유용 데모**)다. 질문이 **비즈니스 로직, 상태 전이, 데이터 형태**에 관한 것일 때 쓴다. 종이 위에서는 그럴듯해 보이지만 실제 사례로 돌려 봐야 문제가 드러나는 종류의 것이다.

설치할 것 없는 파일 하나이므로 개발자가 아닌 사람(디자이너, PM, 도메인 전문가)에게 넘겨 모델을 직접 써 보게 할 수 있다. 그래서 코드의 말이 아니라 그 사람들의 말로 쓴다.

## 이 형태가 맞는 경우

- "이 상태 기계가 X 다음에 Y가 오는 예외 상황을 처리하는지 확실하지 않다."
- "이 데이터 모델로 정말 이런 경우를 표현할 수 있나..."
- "API를 작성하기 전에 어떤 모양이어야 할지 직접 써 보며 감을 잡고 싶다."
- 누군가 **버튼을 누르고 상태가 바뀌는 것을 보고** 싶어 하는 모든 경우

질문이 "이게 어떤 모습이어야 하는가"라면 잘못 고른 갈래다. [UI.md](UI.md)를 쓴다.

## 절차

### 1. 질문을 적는다

코드를 쓰기 전에 어떤 상태 모델을, 어떤 질문으로 프로토타입하는지 적는다. 한 문단으로 데모 맨 위에 둔다(주석만이 아니라 화면에 보이는 소개 글로). 엉뚱한 질문에 답하는 로직 프로토타입은 완전한 낭비다. 그러니 질문을 명시해서 나중에 확인할 수 있게 한다. 사용자가 지금 지켜보고 있든, AFK(사람 없이 에이전트 혼자 진행)로 작업이 끝난 뒤에 돌아와서 보든 마찬가지다.

### 2. 로직을 옮겨 쓸 수 있는 모듈로 분리한다

실제 로직(질문에 답하는 부분)은 `<script>` 블록 하나에 작고 순수한 모듈로 작성한다. 나중에 그대로 떼어 실제 코드베이스에 넣을 수 있어야 한다. 이 모듈을 감싸는 페이지는 버릴 코드지만 이 모듈은 버리지 않는다.

알맞은 형태는 질문에 따라 다르다.

- **순수 리듀서**: `(state, action) => state`. 동작이 개별 이벤트이고 상태가 값 하나일 때 알맞다.
- **상태 기계**: 상태와 전이를 명시한다. "지금 어떤 동작이 허용되는가"가 질문의 일부일 때 알맞다.
- 단순한 데이터 타입을 다루는 **작은 순수 함수 묶음**. 암묵적인 현재 상태 없이 변환만 있을 때 알맞다.
- 로직이 계속 유지되는 내부 상태를 정말로 소유할 때는 **메서드 구성이 분명한 클래스나 모듈**

페이지에 연결하기 가장 쉬운 형태가 _아니라_ 지금 묻는 질문에 가장 맞는 형태를 고른다. 모듈은 순수하게 유지한다. DOM도, `document`도 쓰지 않고, 버튼 핸들러가 모듈 안으로 파고들지도 않게 한다. 페이지가 모듈을 호출하고, 반대 방향으로는 아무것도 흐르지 않는다. 이렇게 해야 프로토타입이 역할을 다한 뒤에도 쓸모가 있다. 질문에 답이 나오면 검증된 리듀서, 상태 기계, 함수 묶음을 그대로 실제 모듈로 옮길 수 있다.

### 3. 공유용 HTML 파일을 만든다

파일 하나에 순수 HTML/CSS/JS만 쓴다. 프레임워크, 번들러, 서버 없이 모든 것을 파일 안에 넣어서 더블클릭으로 열리고 이메일로 주고받아도 문제없게 한다. 누구든 파일을 열기만 하면 실행할 수 있어야 한다.

개발자가 아닌 사람을 위해 쓴다. 모든 라벨은 코드 용어가 아니라 **도메인 용어**로 쓴다. 버튼과 상태는 리듀서가 아니라 비즈니스 용어로 읽혀야 한다. 무슨 일이 일어나는지 쉬운 말로 설명한다.

위에서 아래로 계층이 분명하게 보이도록 배치한다.

1. **제목과 한 줄 설명**: 이 데모로 무엇을 탐색할 수 있는지(1단계의 질문)
2. **현재 상태**: 관련 상태 전체를 읽기 쉬운 패널로 보여 준다(JSON을 그대로 쏟아 놓지 말고 라벨을 붙인 필드로). 클릭할 때마다 다시 그려서 변화가 보이게 한다. 개발자가 아닌 사람이 따라가는 데 도움이 되면 방금 무엇이 바뀌었는지 표시한다.
3. **자유 조작 버튼**: 동작마다 버튼 하나를 두고 항상 누를 수 있게 해서, 누구든 원하는 순서로 모델을 눌러 볼 수 있게 한다. 클릭하면 해당 동작을 실행하고 상태를 다시 그린다.
4. **단계별 시나리오**: 탭마다 **시나리오** 하나를 둔다. 각 탭에는 시나리오를 쉬운 말로 짧게 설명하고(어떤 상황을 만드는지, 무엇을 지켜봐야 하는지), 그 아래에 그 시나리오에서 순서대로 **누를 버튼**을 둔다. 각 단계는 실제 버튼이다. 누르면 그 동작을 실행하고 다음 단계로 넘어간다. 시나리오를 시작하면 정해진 초기 상태로 초기화해서 시나리오가 매번 똑같이 진행되게 한다.

종이 위에서 따져 보기 어려운 까다로운 경우를 보여 주는 시나리오를 고른다. 정상 흐름, 까다로운 예외 상황, 허용되면 안 되는 동작을 시도하는 경우 같은 것들이다.

보기 좋게 만들되 절제한다. 깔끔한 글꼴, 넉넉한 여백, 강조 색 하나를 쓴다. 애니메이션이나 눈길을 끄는 장식은 넣지 않는다. 상태와 버튼보다 눈에 띄는 것은 아무것도 두지 않는다.

### 4. 넘겨준다

파일을 보내거나 사용자 대신 열어 준다. 사용자는 시간이 날 때 시나리오와 자유 조작 버튼을 눌러 본다. 중요한 순간은 사용자가 "잠깐, 이건 가능하면 안 되는데"나 "어, X는 다르게 동작할 줄 알았는데"라고 말할 때다. 그것이 _아이디어_ 자체의 버그이고, 바로 그것을 찾는 것이 이 작업의 목적이다. 새 동작이나 새 시나리오를 원하면 추가한다. 프로토타입은 계속 바뀐다.

### 5. 답과 프로토타입을 기록으로 남긴다

프로토타입이 질문에 답했으면 답을 기록하고, [SKILL](SKILL.md)에 적힌 방식으로 프로토타입을 남긴다. 로직 프로토타입에서는 이렇게 나뉜다. 검증된 리듀서, 상태 기계, 함수 묶음은 실제 모듈로 옮긴다(결정을 반영하는 부분). HTML 페이지는 프로토타입을 1차 자료로 남기는 보관용 브랜치로 함께 옮긴다. 필요한 것을 모두 담은 파일 하나이므로 그 브랜치에서도 언제든 쉽게 다시 실행할 수 있다.

## 피해야 할 패턴

- **테스트를 추가하지 마라.** 테스트가 필요한 프로토타입은 더 이상 프로토타입이 아니다.
- **실제 데이터베이스에 연결하지 마라.** 질문이 저장 방식에 관한 것이 아니면 메모리 안의 상태를 쓴다.
- **일반화하지 마라.** "나중에 X도 지원하고 싶다면" 같은 고려는 하지 않는다. 프로토타입은 질문 하나에 답한다.
- **로직과 페이지를 섞지 마라.** 순수 모듈이 DOM, `document`, 버튼 핸들러를 참조하면 더 이상 떼어 옮길 수 없다. 페이지는 순수 모듈 위에 얹은 로직을 화면에 보여 주기만 하는 얇은 코드로 유지한다.
- **프레임워크, 번들러, 서버를 쓰지 마라.** 받는 사람이 더블클릭하는 파일 하나여야 한다. React 앱이나 개발 서버를 쓰면 공유할 수 있다는 장점이 사라진다.
- **HTML 페이지를 운영 코드에 넣지 마라.** 이 페이지는 사람이 직접 눌러 보는 용도에 맞춰 만든 것이다. 남길 가치가 있는 것은 그 뒤의 로직 모듈이다.
