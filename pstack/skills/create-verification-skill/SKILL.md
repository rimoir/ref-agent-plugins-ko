# 검증 스킬 만들기

진지한 프로젝트라면 실제 앱을 조작해 동작을 증명하는 스크립트화된 방법이 있어야 한다. 앱을 띄우고, 사용자처럼 기능을 실행하고, 증거를 남기는 방법이다. 이 스킬은 그 방법을 레포에 맞춘 프로젝트 로컬 스킬(`.cursor/skills/verify-<app>/`)로 만든다. 만들어 내는 결과물은 사람이 아니라 다음 에이전트가 읽는다. 앱을 본 적 없는 에이전트가 작업 도중 아무 맥락 없이 읽게 된다.

## 1. 사용자가 아니라 레포를 인터뷰한다

다음 질문에 코드베이스로 답하고, 관찰할 수 없는 것만 사용자에게 묻는다.

- **표면(surface):** 사용자가 실제로 손대는 것은 무엇인가? 웹 UI, CLI나 TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리인가? 레포에 여러 개가 있을 수 있다. 주된 것 하나를 고르고 나머지는 적어 둔다.
- **실행:** 앱을 로컬에서 어떻게 띄우는가? 레포가 직접 문서화한 개발 명령(패키지 스크립트, Makefile, README 빠른 시작)을 우선한다. 포트, 환경변수, 시드 데이터, 인증을 적어 둔다.
- **조작:** 에이전트가 프로그램으로 앱과 어떻게 상호작용할 수 있는가? 기존 하네스를 먼저 본다. Playwright나 Cypress 스펙, expect 스크립트, PTY 헬퍼, curl로 부를 수 있는 엔드포인트, 디버그 포트다. 그다음에야 범용 레시피를 고른다. 웹과 Electron에는 브라우저나 CDP, CLI와 TUI에는 tmux나 PTY 하네스, 서비스에는 평범한 HTTP다.
- **관찰:** 어떤 증거를 남길 수 있는가? 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태다.
- **격리:** 인스턴스 두 개를 나란히 띄울 수 있는가(포트, 데이터 디렉터리, 프로필)? 없으면 생성한 스킬에 그렇게 적는다. 공유 인스턴스를 두 곳에서 조작하길 거부하는 편이 사용자 세션을 망가뜨리는 것보다 낫다.

체크아웃이 지금 상태로 빌드되거나 시작되지 않으면 생성하기 전에 먼저 고친다(또는 정확히 보고한다). 깨진 기반 위에서 쓴 스킬은 틀린 단계를 가르친다. 상관없는 빠진 자산(API가 한 번도 제공하지 않는 정적 디렉터리, 샘플 설정)이 시작을 막으면 생성한 스킬이 그것을 만들어도 된다. 검증용 비계(scaffolding)라고 분명히 표시하고 정리 단계에서 지운다.

## 2. 스킬 생성

YAML frontmatter(`name: verify-<app>`, 그리고 앱, 표면, 언제 꺼내 쓸지를 밝히는 `description`. frontmatter가 없으면 스킬이 등록되지 않는다)와 다음 섹션을 갖춘 `.cursor/skills/verify-<app>/SKILL.md`를 쓴다. 섹션마다 인터뷰에서 실제로 찾은 것에 근거해 쓰고 자리표시자를 남기지 않는다.

- **Launch:** 검증용으로 앱을 띄우는 정확한 명령과, 준비됐는지 알아보는 방법(로그 한 줄, 응답하는 포트, 프롬프트)이다. 종료 방법도 넣는다. 수명이 짧은 CLI나 TUI는 살려 둘 서버가 없다. 이때 launch는 바이너리를 한 번 빌드(또는 의존성을 설치)하고, 조작할 때마다 격리된 PTY나 tmux 세션을 새로 시작한다는 뜻이다.
- **Doctor:** "이 인스턴스를 조작할 가치가 있는가?"에 답하는 읽기 전용 점검 하나다. 프로세스가 떠 있는지, 버전과 빌드가 맞는지, 포트를 우리가 쥐고 있는지, 인증이 유효한지 본다. 무언가 이상해 보이면 에이전트가 이것부터 실행한다.
- **Drive:** 예시가 아니라 이 레포의 실제 셀렉터와 명령으로 쓴 하네스 레시피다. 좌표나 탭 순서보다 안정적인 손잡이(ARIA 라벨, data 속성, 프롬프트 문자열, 라우트 경로)를 우선한다.
- **Evidence:** 증명을 위해 무엇을 남기고 어디에 두는지다. 증명 기준을 밝힌다. 내부 setter나 테스트 전용 엔드포인트가 아니라 실제 사용자 경로를 실행한다. 마지막 화면만이 아니라 동작과 그 결과 상태를 남긴다. 눈에 보이는 것과 함께 부수 효과(쓴 파일, 추가된 행, 보낸 메시지)를 검증한다. 목(mock)은 운영 경계가 이미 외부 시스템을 격리하는 곳에서만 쓴다. 안전한 경로가 dry-run이나 테스트 모드라면, 이름을 믿지 말고 실제로 무엇을 건너뛰는지 관찰(파일, 네트워크, git ref)해서 검증한다. 어떤 dry-run은 여전히 네트워크에 닿거나 브라우저를 연다.
- **Cleanup:** 실행이 만든 인스턴스를 내리는 방법이다. 프로세스 이름으로 죽이지 않는다. 직접 시작한 것을 죽인다. 정리는 인스턴스와 임시 상태를 지우지만 증거는 절대 지우지 않는다. 증명 산출물은 스킬이 지정한 위치에 남아 종료 뒤에도 살아남는다.
- **Helpers:** 스킬에 딸린 스크립트는 모두 실행 가능해야 하고, 호출 방법을 스킬 본문에 보여 준다. 읽는 사람이 역설계해야 하는 헬퍼는 헬퍼가 아니다.

## 3. 기능 맵 씨앗 뿌리기

`.cursor/skills/verify-<app>/features/README.md`와, 찾을 수 있는 사용자 대상 기능마다 파일 하나씩을 만든다(라우트, 명령, 메뉴, 문서에서 상위 3~5개로 시작하는 것을 목표로 한다). [`references/feature-map-example/`](references/feature-map-example/)의 모양을 따라 README 색인 하나와 기능마다 파일 하나를 둔다. 각 파일은 사용자 관점에서 기능이 무엇인지, 어떻게 도달하는지, 하네스로 어떻게 조작하는지, 동작을 증명하는 관찰 가능한 최종 상태가 무엇인지 답한다. H2 네 개는 `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, `Gotchas`다. 맵은 레포가 관리하는 검증 원천이다. 맵에 다른 진입점이 있는데 편한 진입점 하나만 조작한 증명은 불완전하다.

## 4. 넘기기 전에 생성한 스킬 증명하기

스킬 자체의 지침을 처음부터 끝까지 한 번 실행한다. launch, doctor, 맵에 있는 기능 하나 조작(하나면 충분하다. 맵은 나머지를 이후 실행에서 다루려고 있다), 증거 남기기, 정리다. 정리한 뒤 지정한 위치에 증거가 아직 있는지 확인한다. 증명을 먹어 치우는 정리는 이 단계를 통과하지 못한다. 실패한 것은 고치고, 실패한 시도마다 생성한 정리 단계도 실행해 깨진 시도가 프로세스와 포트를 남기지 않게 한다. 한 번도 실행하지 않은 생성 스킬은 결과물이 아니라 초안이다.

## 5. 유지 관리 루프 제안

앱이 바뀌어도 맵이 정직하게 유지되도록 사용자에게 `/maintain-verification-skill`을 알려 준다. 주기는 사용자가 물을 때만 제안한다.
