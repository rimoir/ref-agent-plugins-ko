# 코드베이스 아키텍처 개선

아키텍처 때문에 작업이 어려워지는 지점을 찾아내고 **모듈을 깊게 만들 기회**를 제안한다. 여기서 말하는 기회는 얕은 모듈(인터페이스가 구현만큼 복잡한 모듈)을 깊은 모듈(작은 인터페이스 뒤에 많은 동작을 담은 모듈)로 바꾸는 리팩터링이다. 목표는 테스트하기 쉽고 AI가 탐색하기 쉬운 코드다.

이 명령은 프로젝트의 도메인 모델을 _근거로_ 판단하고, 공통 설계 용어를 바탕으로 동작한다.

- Skill 도구로 "codebase-design"을 호출해 아키텍처 용어(**모듈**, **인터페이스**, **깊이**, **교체 지점**(seam, 그 자리의 코드를 고치지 않고 동작을 바꿔 끼울 수 있는 위치이자 모듈 인터페이스가 놓이는 곳), **어댑터**, **활용도**(leverage, 호출자가 배우는 인터페이스 단위당 얻는 기능), **지역성**(locality, 변경과 버그와 지식이 한곳에 모이는 성질))와 원칙(삭제 테스트, "인터페이스가 곧 테스트 지점이다", "어댑터가 하나면 가정일 뿐인 교체 지점이고, 둘이면 실제 교체 지점이다")을 가져온다. 모든 제안에서 이 용어를 정확히 그대로 쓰고, "컴포넌트(component)", "서비스(service)", "API", "경계(boundary)" 같은 말로 바꿔 쓰지 않는다.
- `GLOSSARY.md`의 공통 언어(ubiquitous language, 팀과 코드가 함께 쓰는 도메인 용어)는 좋은 교체 지점에 붙일 이름을 준다. `docs/adr/`의 ADR(아키텍처 결정 기록)은 이 명령이 다시 문제 삼지 말아야 할 결정을 담고 있다.

## 절차

### 1. 탐색

**살펴보기 전에 범위부터 정한다(YAGNI).** 모듈을 깊게 만들면 그 모듈을 앞으로 고치기 쉬워지는 이득이 생긴다. 그래서 최근에 바뀐 부분에 더 큰 비중을 둔다. 살펴보기 전에 *어디를* 볼지 먼저 정한다.

- 사용자가 방향(특정 모듈, 하위 시스템, 불편한 점)을 정해 주었으면 그대로 따르고 아래의 추론 과정은 건너뛴다.
- 그렇지 않으면 커밋 기록(`git log --oneline`)을 충분히 거슬러 올라가며 변경이 몰리는 곳, 즉 계속 등장하는 파일과 영역을 찾고 그 경로부터 먼저 살펴본다. 변경이 흩어져 있고 뚜렷하게 몰리는 곳이 없으면 범위를 넓힌다.

프로젝트의 도메인 용어집(`GLOSSARY.md`)과 작업할 영역의 ADR을 먼저 읽는다.

그다음 서브에이전트를 띄워 코드베이스를 둘러보게 한다. 정해진 규칙을 기계적으로 따르지 말고 코드를 따라가며 자유롭게 탐색하면서, 작업이 어려워지는 지점을 기록한다.

- 개념 하나를 이해하려고 작은 모듈 여러 개를 오가야 하는 곳은 어디인가?
- 인터페이스가 구현과 거의 같을 만큼 복잡한 **얕은** 모듈은 어디인가?
- 테스트하기 쉽게 하려고 순수 함수를 따로 뽑아냈지만 실제 버그는 그 함수를 호출하는 방식에 숨어 있는 곳(**지역성** 없음)은 어디인가?
- 강하게 결합된 모듈의 세부 구현이 교체 지점 밖으로 새어 나가는 곳은 어디인가?
- 테스트가 없거나, 지금 인터페이스로는 테스트하기 어려운 부분은 어디인가?

얕다고 의심되는 모듈에는 **삭제 테스트**를 적용한다. 이 모듈을 지우면 복잡성이 한곳에 모이는가, 아니면 자리만 옮겨 가는가? "그렇다, 한곳에 모인다"는 답이 찾고 있는 신호다.

### 2. 후보를 HTML 보고서로 보여 주기

저장소에 아무것도 남지 않도록 OS 임시 디렉터리에 독립 실행되는 HTML 파일 하나를 쓴다. 임시 디렉터리는 `$TMPDIR`에서 찾고, 없으면 `/tmp`(Windows에서는 `%TEMP%`)를 쓴다. 실행할 때마다 새 파일이 생기도록 `<tmpdir>/architecture-review-<timestamp>.html`에 쓴다. 파일을 사용자에게 열어 주고(Linux는 `xdg-open <path>`, macOS는 `open <path>`, Windows는 `start <path>`) 절대 경로를 알려 준다.

보고서의 레이아웃과 스타일은 **CDN으로 불러온 Tailwind**로 만들고, 그래프, 흐름, 시퀀스로 구조를 확실히 전달할 수 있는 다이어그램은 **CDN으로 불러온 Mermaid**로 그린다. Mermaid와 직접 만든 CSS/SVG 시각 자료를 섞어 쓴다. 관계가 그래프 형태(호출 그래프, 의존성, 시퀀스)이면 Mermaid를 쓰고, 편집 디자인 성격이 강한 시각 자료(크기 비교 다이어그램, 단면도, 합쳐지는 애니메이션)가 필요하면 div와 SVG를 직접 만든다. 후보마다 **변경 전·후 시각 자료**를 넣는다. 글보다 시각 자료를 적극적으로 쓴다.

후보마다 다음 항목을 담은 카드를 만든다.

- **파일**: 관련된 파일과 모듈
- **문제**: 지금 아키텍처가 왜 작업을 어렵게 만드는지
- **해결책**: 무엇이 바뀌는지를 쉬운 말로 설명
- **이점**: 지역성과 활용도 측면의 설명, 그리고 테스트가 어떻게 나아지는지
- **변경 전·후 다이어그램**: 나란히 놓고 직접 그린 그림으로, 얕은 상태와 깊게 만든 상태를 보여 준다
- **추천 강도**: `Strong`, `Worth exploring`, `Speculative` 중 하나를 배지로 표시

보고서 끝에는 **최우선 추천** 섹션을 둔다. 어떤 후보를 가장 먼저 다룰지와 그 이유를 쓴다.

**도메인은 GLOSSARY.md의 용어로, 아키텍처는 `/codebase-design` 용어로 말한다.** `GLOSSARY.md`가 "Order"를 정의한다면 "FooBarHandler"나 "Order 서비스"가 아니라 "Order 접수 모듈"이라고 쓴다.

**ADR과 충돌하는 경우**: 후보가 기존 ADR과 어긋나면, 그 ADR을 다시 검토할 만큼 어려움이 실제로 클 때만 보고서에 올린다. 카드에 이 사실을 분명히 표시한다(예: 경고 상자에 _"ADR-0007과 어긋나지만 다음 이유로 다시 검토할 만하다…"_). ADR이 금지하는 이론상의 리팩터링을 모두 나열하지 않는다.

전체 HTML 기본 구조, 다이어그램 패턴, 스타일 지침은 [HTML-REPORT.md](HTML-REPORT.md)를 본다.

아직 인터페이스를 제안하지 마라. 파일을 다 쓰고 나면 사용자에게 "이 중 어떤 것을 더 살펴보고 싶으신가요?"라고 묻는다.

### 3. 집요한 질문 루프

사용자가 후보를 고르면 Skill 도구로 "grilling"을 호출해 설계 결정 트리(결정 하나가 그 결정에 딸린 결정들로 갈라지는 구조)를 사용자와 함께 따라간다. 다룰 내용은 제약, 의존성, 깊게 만든 모듈의 형태, 교체 지점 뒤에 무엇을 둘지, 어떤 테스트가 살아남는지다.

결정이 확정되는 대로 그 자리에서 관련 문서를 고친다. Skill 도구로 "domain-modeling"을 호출해 진행하는 동안 도메인 모델을 최신 상태로 유지한다.

- **깊게 만든 모듈에 `GLOSSARY.md`에 없는 개념의 이름을 붙이는가?** 그 용어를 `GLOSSARY.md`에 추가한다. 파일이 없으면 이때 처음 만든다.
- **대화 중에 모호한 용어의 뜻을 분명히 했는가?** 그 자리에서 `GLOSSARY.md`를 고친다.
- **사용자가 앞으로의 판단에 영향을 주는 중요한 이유로 후보를 거절했는가?** ADR 작성을 제안한다. 이렇게 묻는다. _"이 내용을 ADR로 기록해서 이후 아키텍처 리뷰에서 같은 제안이 다시 나오지 않게 할까요?"_ 나중에 코드베이스를 살펴볼 사람이 같은 제안을 반복하지 않으려면 그 이유를 실제로 알아야 할 때만 제안한다. 일시적인 이유("지금은 할 가치가 없다")나 누가 봐도 뻔한 이유는 건너뛴다.
- **깊게 만든 모듈의 다른 인터페이스 안을 살펴보고 싶은가?** Skill 도구로 "codebase-design"을 호출하고 그 스킬의 두 번 설계하기(Design It Twice) 병렬 서브에이전트 패턴을 쓴다.
