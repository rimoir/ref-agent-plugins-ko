## 하는 일

`code-review`는 `HEAD`와 사용자가 정한 기준점(커밋, 브랜치, 태그, `main`, `HEAD~5`) 사이의 diff를 두 축으로 리뷰한다. **코딩 표준(Standards)** 축은 코드가 이 저장소의 코드 작성 방식을 따르는지 본다. **스펙(Spec)** 축은 코드가 원래 이슈나 [스펙](https://www.aihero.dev/ai-coding-dictionary/spec)이 요구한 일을 하는지 본다. 각 축은 자기만의 [서브에이전트](https://www.aihero.dev/ai-coding-dictionary/subagent)에서 실행되므로 어느 쪽도 다른 쪽의 추론을 보지 못한다.

두 축의 결과는 합치지 않고 순위도 다시 매기지 않는다. 보고는 *축마다* 가장 심각한 문제를 적고 끝나며, 두 축을 통틀어 가장 심각한 것 하나를 고르지 않는다. 변경이 한 축은 통과하고 다른 축에서는 실패할 수 있기 때문이다. 모든 규칙을 따르면서 잘못된 것을 구현한 코드는 코딩 표준을 통과하고 스펙에서 실패한다. [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)이 요구한 대로 정확히 동작하면서 저장소 규칙을 어기는 코드는 그 반대다. 두 축을 섞어 판정하면 통과한 축이 실패한 축을 가린다.

## 언제 쓰나

`/code-review`를 입력해서 실행하거나, 브랜치, PR, 작업 중인 변경, 또는 "X 이후"의 무엇이든 리뷰해 달라고 하면 에이전트가 자동으로 실행한다.

| 상황 | 쓸 스킬 |
| --- | --- |
| diff가 있고, 제대로 만들었는지 *그리고* 맞는 것을 만들었는지 알고 싶다 | `code-review` |
| diff에서 버그를 찾고 싶다(null 경로, 경쟁 조건, 경계값이 하나 어긋나는 오류(off-by-one)) | 이 스킬이 아니라 Claude Code의 기본 리뷰(아래 이름 충돌 참고) |
| 아직 아무것도 작성하지 않았고, 테스트 먼저 작성하고 싶다 | [tdd](https://aihero.dev/skills-tdd) |
| 스펙 전체를 리뷰까지 포함해 구현해야 한다 | [implement](https://aihero.dev/skills-implement)(이 스킬을 직접 호출한다) |
| diff 하나가 아니라 코드베이스 전체가 원래 설계에서 벗어났다 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) |
| 무언가 고장 났는데 이유를 모른다 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

기준점은 사용자가 반드시 알려 줘야 한다. 알려 주지 않으면 스킬은 추측하지 않고 기준점을 묻는다. 그다음 아무것도 띄우기 전에 ref가 실제 커밋으로 해석되는지와 diff가 비어 있지 않은지 확인한다. 그래서 브랜치 이름에 오타가 있으면 서브에이전트 두 개 안에서가 아니라 사용자가 바로 보는 곳에서 실패한다.

## 사전 준비

코딩 표준 축은 따로 준비할 것이 없다. 저장소가 문서화한 것(`CODING_STANDARDS.md`, `CONTRIBUTING.md` 등)을 무엇이든 읽고, 저장소가 아무것도 문서화하지 않았으면 내장된 기본 목록을 쓴다.

스펙 축은 스펙이 있고 찾을 수 있어야 한다. 다음 순서로 찾는다.

1. 커밋 메시지 안의 이슈 참조(`#123`, `Closes #45`, GitLab `!67`). `docs/agents/issue-tracker.md`에 적힌 방식으로 가져온다.
2. 사용자가 인자로 넘긴 경로
3. `docs/`, `specs/`, `.scratch/` 아래에서 브랜치 이름이나 기능 이름과 맞는 스펙 파일
4. 사용자에게 묻기

1번 방법은 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills)가 작성하는 `docs/agents/issue-tracker.md`에 의존한다. 이 파일이 없어도 경로를 직접 넘기면 스펙 축은 동작한다. 스펙이 전혀 없으면 스펙 서브에이전트를 건너뛰고, 보고에는 요구사항을 지어내지 않고 "no spec available"(사용 가능한 스펙 없음)이라고 적는다.

## 코딩 표준 축과 스펙 축

| | 코딩 표준 | 스펙 |
| --- | --- | --- |
| 질문 | 제대로 만들었는가? | 맞는 것을 만들었는가? |
| 읽는 것 | 저장소에 문서화된 표준과 기본 코드 스멜 목록 | 원래 이슈나 스펙 |
| 보고하는 것 | 문서화된 표준 위반(명백한 위반일 수 있다)과 스멜(항상 판단이 필요한 항목) | 빠졌거나 일부만 구현된 요구사항, 범위 확장, 잘못 구현된 요구사항 |
| 모든 발견 항목이 인용하는 것 | 표준 파일과 규칙, 또는 스멜 이름과 해당 변경 블록(hunk) | 스펙의 해당 줄 |

이 설계가 피하려는 것은 사용자의 표준을 모르는 범용 리뷰 스킬이다. 그런 스킬은 코드베이스에서 일부러 그렇게 한 부분을 문제로 짚고, 코드베이스가 실제로 기대는 불변 조건은 놓친다. 그래서 코딩 표준 축에서는 저장소 자체 문서가 [1차 자료](https://www.aihero.dev/ai-coding-dictionary/primary-source)이고, **저장소 규칙이 항상 우선한다**.

**기본 코드 스멜 목록**은 저장소 문서에 더해 항상 적용되는 최소 기준이다. 코드 스멜은 리팩터링이 필요할 수 있다는 징후이고, 이 목록은 Fowler의 _Refactoring_ 3장에서 고른 코드 스멜로 이루어진다. Mysterious Name(뜻을 알 수 없는 이름), Duplicated Code(중복 코드), Feature Envy(다른 객체 데이터에 의존), Data Clumps(늘 함께 다니는 데이터), Primitive Obsession(기본 타입 남용), Repeated Switches(반복되는 분기), Shotgun Surgery(흩어진 수정), Divergent Change(여러 이유로 바뀌는 모듈), Speculative Generality(추측성 일반화), Message Chains(메시지 체인), Middle Man(중개자), Refused Bequest(상속 거부). 각 스멜은 이름을 붙인 경험 법칙("possible Feature Envy"처럼 "~일 수 있음"으로 표시)이고 명백한 위반으로 다루지 않는다. 또 각 스멜은 *무엇인지* → *어떻게 고치는지* 순서로 적혀 있어서, 발견 항목에는 불만만 있는 것이 아니라 고치는 방법이 함께 붙는다. 린터가 이미 강제하는 것은 두 축 모두 건너뛴다.

## 자주 묻는 질문

**Claude Code에 들어 있는 `/code-review`와 이름이 겹쳐요. 어떻게 해야 하나요?**

이 스킬에서 가장 많이 보고된 문제이고, 아직 고쳐지지 않았다. Claude Code에는 자체 `/code-review`가 들어 있고, 하는 일이 다르다. 그 스킬은 diff에서 버그를 찾고, 이 스킬은 스펙을 따랐는지와 저장소 표준을 확인한다. 이 라이브러리를 설치하면 둘 중 하나만 그 이름으로 실행되고, 어느 쪽이 실행되는지는 설치 방법에 달려 있다. 플러그인 마켓플레이스로 설치하면 모든 스킬이 `mattpocock-skills:` 접두사가 붙은 별칭으로 등록되고, 접두사 없는 이름으로는 기본 스킬을 호출하기 어려워진다. 일반 스킬 설치 방식으로 설치하면 로컬 파일이 우선해서 이 스킬이 기본 스킬을 가린다. 깔끔한 해결책 하나는 Claude Code의 기본 스킬을 모두 없애는 것이다. [컨텍스트](https://www.aihero.dev/ai-coding-dictionary/context)를 크게 아낄 수 있고, 이름 충돌도 더는 문제가 되지 않는다. 기본 스킬이 가려지는 것 자체는 Claude Code [하네스](https://www.aihero.dev/ai-coding-dictionary/harness)의 버그로 볼 수도 있다(스킬 작성자는 스킬 이름을 마음대로 정할 수 있어야 한다). 그래서 다른 해결책은 로컬 사본의 이름을 바꾸는 것이다. frontmatter를 고치거나 디렉터리 이름을 바꾸면 `npx skills update`가 되돌린다. 업데이트 뒤에도 유지되는 우회 방법으로 사용자들이 보고한 것은 스킬을 새 이름으로 포크하고 `code-review`를 관리 대상 목록에서 빼는 것이다. 나중에 직접 다시 맞출 수 있도록 포크한 커밋을 적어 둔다.

**서브에이전트가 `/code-review`를 계속 다시 호출해서 에이전트를 더 띄워요.**

아직 해결되지 않은 알려진 버그이고, 여러 사람이 여러 하네스에서 재현했다. 코딩 표준 프롬프트와 스펙 프롬프트가 위임을 금지하지 않아서, 서브에이전트가 이 스킬을 다시 찾아 에이전트를 또 여러 개 띄울 수 있다. 에이전트가 50개 넘게 늘어났다는 보고도 있다. 포크에서 사람들이 적용한 수정은 두 서브에이전트의 지시 요약 끝에 다음 한 줄을 붙이는 것이다. "`/code-review`를 호출하거나 에이전트를 추가로 띄우지 않는다. 이 리뷰를 직접 수행한다." 모든 스킬에 같은 방지 장치가 적용되도록 하네스 수준에서 처리하는 쪽을 선호하는 사람도 있다. 배포된 스킬에는 아직 둘 다 들어 있지 않다. 지켜보는 사람 없이 실행한다면 에이전트 수를 지켜본다.

**코드를 작성한 그 [세션](https://www.aihero.dev/ai-coding-dictionary/session)에서 실행해도 되나요?**

새 세션이 낫다. 한 독자는 이렇게 말했다. "같은 컨텍스트가 자기 자신을 리뷰하는 건 리뷰가 아니라 슬래시 명령이 붙은 확증 편향이다." 코드를 작성한 세션에서 리뷰하는 에이전트는 그 코드를 만든 가정을 모두 갖고 있다. 독립된 리뷰어라면 갖고 있지 않을 바로 그 컨텍스트다. 사람들이 [implement](https://aihero.dev/skills-implement)에서 내장 리뷰 단계를 빼 달라고 요청하는 이유도 이것이다. implement는 방금 diff를 작성한 세션 안에서 리뷰를 실행한다. 새 세션에서 직접 `/code-review`를 호출해야 제대로 된 리뷰가 된다.

**티켓마다 실행하나요, 마지막에 한 번 실행하나요?**

둘 다 된다. 스킬이 대신 정해 주지는 않는다. 티켓마다 실행하면 diff가 충분히 작게 유지되어 스펙 축이 대조할 분명한 스펙이 하나로 정해진다. `implement`가 쓰는 방식이 이것이다. 브랜치 끝에 한꺼번에 실행하면 티켓별 리뷰가 각각 놓치는 티켓 사이의 상호작용을 잡아낸다. 잘 모르겠으면 티켓마다 리뷰하고, 마지막에 브랜치가 갈라진 지점을 기준으로 한 번 더 실행한다.

**발견 항목을 믿어도 되나요?**

확인하기 전에는 믿으면 안 된다. 서브에이전트의 출력은 근거가 아니라 가설이다. 한 팀은 글로 설명하는 방식의 리뷰가 그냥 통과시킨 호환성을 깨는 변경을 십여 건 찾았다고 보고했다. 이 스킬은 두 보고를 그대로 또는 조금만 다듬어서 모을 뿐, 각 주장을 파일과 대조해 다시 검증하지 않는다. 그래서 발견 항목이 잘못된 위치를 인용하거나 영향을 부풀릴 수 있다. 발견 항목에 따라 조치하기 전에 항목마다 인용을 읽는다. 모든 발견 항목이 인용(표준 규칙, 스멜과 해당 변경 블록, 또는 스펙의 줄)을 반드시 달아야 하기 때문에 이런 확인이 가능하다.

**실행할 때마다 왜 새 문제를 찾나요?**

수정하면 새로 리뷰할 코드가 생기고, 코딩 표준 축에서 판단이 필요한 항목 쪽은 실행할 때마다 결과가 달라지기 때문이다. 한 독자는 이 반복을 있는 그대로 이렇게 말했다. "/code-review와 /improve-code-architecture는 매번 새로운 걸 찾아낸다. 수정을 구현하고, 이 스킬들을 다시 실행하고, 이걸 계속 되풀이한다." 결과가 언젠가 수렴한다는 보장은 없다. 한 번 실행한 결과를 살펴볼 단서 목록으로 보고, 인용된 규칙이 뒷받침하는 항목만 조치한 다음 멈춘다. 문제가 하나도 나오지 않을 때까지 반복해서 실행하지 않는다. 그런 결과는 나오지 않는다.

**커밋하지 않은 작업도 리뷰하나요?**

아니다. 이 스킬은 점 세 개를 쓴 `<fixed-point>...HEAD`로 diff를 만든다. 이 diff는 merge-base부터 계산하고, 스테이징한 변경과 작업 트리의 변경은 포함하지 않는다. `implement`가 중간 커밋을 만들지 않았다면 곧 커밋할 작업은 리뷰에 보이지 않는다. 먼저 커밋하고, 리뷰한 다음, 커밋을 amend하거나 fixup 커밋을 추가한다.

## 잘 동작하고 있다는 신호

- ref가 잘못됐거나 diff가 비어 있으면 서브에이전트를 하나도 띄우기 전에 시작을 거부한다.
- 보고가 하나로 합친 목록이 아니라 `## 코딩 표준`과 `## 스펙` 아래 따로 나뉜 블록으로 나온다.
- 코딩 표준 발견 항목은 모두 저장소 파일 중 하나에 있는 규칙이나 기본 목록의 스멜 하나를 밝히고 해당 변경 블록을 인용한다. 스펙 발견 항목은 모두 스펙의 줄을 인용한다.
- 마지막 요약은 축마다 가장 심각한 문제를 적고, 전체에서 가장 심각한 것 하나를 고르지 않는다.
- 스펙이 없으면 스펙 블록이 코드에서 추론한 요구사항을 나열하지 않고 스펙이 없다고 밝힌다.

## 전체 흐름에서의 위치

`code-review`는 구현 흐름 `grill-with-docs → to-spec → to-tickets → implement → code-review`의 끝에 있는 리뷰 단계다. 지정한 브랜치나 PR 어디에든 단독으로도 쓸 수 있다.

- [implement](https://aihero.dev/skills-implement)가 가장 가까운 관련 스킬이다. 구현을 진행하고, 커밋하기 전에 마지막 리뷰로 이 스킬을 호출한다.
- [to-spec](https://aihero.dev/skills-to-spec)과 [to-tickets](https://aihero.dev/skills-to-tickets)는 스펙 축이 대조하는 문서를 만든다. 스펙이 모호하면 스펙 축의 리뷰도 모호해진다.
- [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)는 코드베이스 전체를 보는 짝이다. 이 스킬은 언제나 diff 하나만 본다.

상황에 어떤 스킬이 맞는지 모를 때는 [ask-matt](https://aihero.dev/skills-ask-matt)가 전체 스킬 중 알맞은 것을 알려 준다.
