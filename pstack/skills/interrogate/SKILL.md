# Interrogate

설정된 모델마다 리뷰어 하나씩 띄워 코드 변경을 적대적으로 리뷰한다. 모든 모델은 같은 프롬프트와 루브릭을 받는다. 적대적 신호는 배정된 페르소나가 아니라 모델의 다양성에서 나온다.

산출물은 종합된 판정이다. 변경을 자동으로 적용하지 않는다.

## 1단계, 범위 정하기

맥락에서 리뷰할 대상을 찾는다.

- 사용자가 특정 파일이나 diff를 가리키면 그것을 쓴다
- feature 브랜치에 있다면 `git diff main...HEAD`(또는 알맞은 base 브랜치)를 돌려 전체 변경을 얻는다
- 사용자 메시지가 최근 작업을 언급하면 관련 파일을 모은다

diff(또는 파일 내용)와 함께, 리뷰어가 코드를 이해하는 데 필요한 주변 맥락 파일을 묶는다.

## 2단계, 의도 밝히기

리뷰어를 띄우기 전에 의도를 명시적으로 밝힌다. 다음에서 끌어낸다.

- 사용자 메시지
- 커밋 메시지
- PR 설명(있다면)
- 코드 자체

명확한 문단 하나로 쓴다. 의도가 확실하지 않으면 진행하기 전에 사용자에게 묻는다.

## 3단계, 리뷰어 띄우기

Task 도구로 모든 리뷰어를 메시지 하나에서 띄운다. `~/.cursor/rules/pstack-models.mdc`의 `interrogate reviewers` 줄을 쓰고, 항목마다 리뷰어 하나를 두며, 아래 Reviewer A/B/C 라벨은 설정된 항목 수에 맞춰 늘리거나 줄인다. 규칙이나 그 줄이 없으면 표의 기본값을 쓴다.

| Subagent | 기본 모델 |
|----------|---------------|
| Reviewer A | `claude-opus-5-5-max` |
| Reviewer B | `gpt-5.6-sol-max` |
| Reviewer C | `grok-4.7-xhigh-fast` |

리뷰어마다:
- `subagent_type`: `generalPurpose`
- `model`: 설정된 `interrogate reviewers` 항목, 설정된 줄이 없으면 표의 기본값. `auto`나 `inherit-parent` 항목이면 `model`을 생략해 그 리뷰어가 부모 모델로 돌게 한다.
- `readonly`: `true`

Task 도구가 설정된 항목을 거부하면 그 리뷰어를 같은 계열의 표 기본값으로 돌리고 그렇다고 알린다. 계열은 접두사로 구분한다. `claude-*`, `gpt-*`, `grok-*`. 맞는 계열이 없으면 Reviewer A의 기본값을 쓴다. 표 기본값이 거부되면 Task 도구 오류 메시지에서 유효한 slug를 확인하고, 가장 가까운 대응(같은 계열에서 추론 등급이 가장 높은 것을 선호)을 골라 띄운 뒤, 기본값 표를 갱신하는 PR을 따로 연다. slug 문제로 리뷰를 막지 않는다. 별칭 항목은 절대 거부된 slug로 다루지 않고, 어느 대체 규칙도 적용하지 않는다.

`references/reviewer-prompt.md`를 읽고 템플릿을 다음으로 채운다.
1. 밝힌 의도
2. diff나 파일 내용
3. `references/rubric.md`의 리뷰 루브릭
4. `references/code-quality-review.md`의 코드 품질 관점

같은 채워진 템플릿이 모든 리뷰어에게 가므로 모든 모델이 코드 품질 관점을 적용한다.

## 4단계, 종합하기

결과가 돌아오는 대로 하나로 합친 그림을 만든다.

1. **모든 지적을 파싱한다**. 리뷰어들이 낸 것 전부.
2. **합의를 찾는다**. 2개 이상의 모델이 독립적으로 낸 지적이 가장 강한 신호다.
3. **한 모델만 낸 지적을 찾는다**. 여전히 읽을 가치가 있지만 그만큼 가중치를 낮춘다.
4. **중복을 없앤다**. 다른 모델이 같은 문제를 다르게 묘사할 수 있다. 합치고 어느 모델이 냈는지 적는다.
5. **불일치를 적는다**. 한 모델이 무언가를 지적하고 다른 모델이 명시적으로 반대를 말한다면, 판정에 쓸모 있는 맥락이다.

## 5단계, 리드의 판단

나는 중립적인 집계자가 아니라 리드 리뷰어이자 실용적인 시니어 엔지니어다.

전체 틀은 `references/lead-judgment.md`를 읽는다.

모든 지적을 다음 분류로 나눈다.

- **조치(Act on)**. 실제 목표에 비춰 정확성, 보안, 유지보수성에 영향을 주는 진짜 문제. 실제 PR이라면 막을 것들이다.
- **검토(Consider)**. 타당한 지적이지만 지금 다루는 비용보다 큰지 확신이 없다. 사용자가 주목할 만하다.
- **참고(Noted)**. 기술적으로는 맞지만 조치할 것은 아니다. 맥락에 달렸거나, 섣부른 최적화이거나, 현재 단계에서는 영향이 작다.
- **기각(Dismissed)**. 틀렸거나, 사소한 트집이거나, 맥락을 놓쳤다. 이유를 짧게 적는다.

지적마다 다음을 넣는다.
- 어느 모델이 냈는지
- 분류(조치 / 검토 / 참고 / 기각)
- 분류 근거 한 줄

## 출력 형식

판정은 이 구조로 낸다.

### 의도
> [2단계에서 밝힌 의도 문단]

### 리뷰어
- Reviewer [label]: [모델 이름], [지적 N개] (리뷰어마다 글머리표 하나)

### 조치
[다뤄야 할 지적. 각각 설명, 낸 모델, 왜 중요한지.]

### 검토
[생각해 볼 만한 지적. 각각 설명, 낸 모델, 걸린 트레이드오프.]

### 참고
[타당하지만 우선순위가 낮은 것. 짧은 목록.]

### 기각
[기각한 지적과 짧은 근거.]

### 합의 지도
[모델들이 어디서 일치했고 어디서 갈렸는지, 그 일치와 불일치의 패턴이 무엇을 말해 주는지.]
