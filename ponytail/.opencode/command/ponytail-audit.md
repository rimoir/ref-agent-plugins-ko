---

저장소 전체(또는 사용자가 지목한 폴더)를 막 물려받은 시니어 개발자처럼 감사한다. 먼저 전체를 파악한다. README, 배포와 빌드 설정, 의존성, 진입점, 테스트를 읽는다. 예상 부하(한 사람인지, 많은 사용자와 프로세스인지)를 찾는다. 주요 흐름을 따라가고 사용자 입력, 돈, 인증, 데이터 쓰기, 백그라운드 작업, 공유 상태가 있는 경로는 끝까지 읽는다. 다음 순서로 찾는다. 버그, 위험(보안 구멍, 데이터 손실), 규모(경쟁 상태, 모든 프로세스가 반복하는 같은 일, 늘기만 하는 메모리, 항목마다 보내는 쿼리, O(n^2)), 테스트 없는 위험한 로직, 느린 코드(크면 문제, 작으면 제안), 간결함(죽은 코드, 중복 헬퍼, 직접 만든 코드나 의존성 대신 쓸 표준 라이브러리나 플랫폼 기능, 구현이 하나뿐인 추상화, 합쳐야 할 거의 같은 사본, 관계없는 여러 일을 해서 나눠야 할 함수. 줄 수로는 절대 나누지 않는다). 코드가 안 쓰인다고 말하기 전에 테스트, 픽스처, 설정, 문자열 참조까지 포함해 트리 전체를 grep으로 찾는다. 모든 항목에는 구체적인 사례가 있어야 한다. 한계를 적은 shortcut:(예전 코드는 ponytail:) 주석이 달린 지름길은 지적 대상이 아니라 결정이다. 가장 작은 수정을 제안하고, 코드를 지우는 수정을 우선하고, 계층은 절대 더하지 않는다. 아주 쉬운 말로 쓴다. '이 저장소가 하는 일:'과 가정한 부하로 시작한다. 그다음 번호를 붙인 항목을 최대 20개, 꼭 고칠 것 / 고치면 좋은 것 / 있으면 좋은 것으로 묶어 중요한 것부터 쓴다. 각 항목은 file:lines가 붙은 굵은 제목 아래 네 불릿(이게 뭔가, 문제, 수정, 그냥 두면)으로 쓴다. '판정:', '간결함: -N줄, 의존성 -M개 줄일 수 있다.', 읽지 않은 부분을 적은 '확인 못 함:'으로 끝낸다. 코드는 바꾸지 않는다.
