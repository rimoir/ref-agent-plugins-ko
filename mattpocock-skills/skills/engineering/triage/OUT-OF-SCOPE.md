# 범위 밖 기록 저장소

저장소의 `.out-of-scope/` 디렉터리는 거절한 기능 요청을 영구 기록으로 보관한다. 쓰임새는 다음과 같다.

- **결정 기록 보존**: 기능을 왜 거절했는지 남겨서, 이슈를 닫은 뒤에도 그 이유가 사라지지 않게 한다
- **중복 방지**: 새 이슈가 이전에 거절한 요청과 일치하면, 같은 논의를 다시 하지 않고 이전 결정을 스킬이 바로 보여 줄 수 있다

## 디렉터리 구조

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

파일은 이슈 하나당이 아니라 **개념** 하나당 하나다. 같은 것을 요청한 여러 이슈는 파일 하나에 모은다.

## 파일 형식

파일은 딱딱한 데이터베이스 항목보다는 짧은 설계 문서처럼 편하게 읽히도록 쓴다. 문단, 코드 예시, 사례를 써서 처음 보는 사람도 이유를 분명하게 이해하고 활용할 수 있게 한다.

```markdown
# 다크 모드

이 프로젝트는 다크 모드와 사용자용 테마 기능을 지원하지 않는다.

## 범위 밖인 이유

렌더링 파이프라인은 `ThemeConfig`에 정의한 색상 팔레트 하나만 있다고
가정한다. 여러 테마를 지원하려면 다음이 필요하다.

- 컴포넌트 트리 전체를 감싸는 테마 컨텍스트 프로바이더
- 컴포넌트마다 테마를 반영하는 스타일 결정 로직
- 사용자 테마 설정을 저장하는 저장 계층

이는 큰 아키텍처 변경이고, 콘텐츠 작성에 집중하는 이 프로젝트의 방향과
맞지 않는다. 테마는 결과물을 가져다 넣거나 다시 배포하는 하위 사용자가
다룰 문제다.

```ts
// 현재 ThemeConfig 인터페이스는 런타임에 테마를 바꾸도록 설계되지 않았다:
interface ThemeConfig {
  colors: ColorPalette; // 팔레트 하나, 빌드 시점에 결정됨
  fonts: FontStack;
}
```

## 이전 요청

- #42: "Add dark mode support"
- #87: "Night theme for accessibility"
- #134: "Dark theme option"
```

### 파일 이름 짓기

개념을 나타내는 짧고 설명적인 kebab-case 이름을 쓴다. 예: `dark-mode.md`, `plugin-system.md`, `graphql-api.md`. 디렉터리를 훑어보는 사람이 파일을 열지 않고도 무엇을 거절했는지 알아볼 수 있는 이름이어야 한다.

### 이유 쓰기

이유에는 실제 내용이 있어야 한다. "원하지 않는다"가 아니라 왜 원하지 않는지 쓴다. 좋은 이유는 다음을 근거로 든다.

- 프로젝트의 범위나 철학("이 프로젝트는 X에 집중한다. 테마는 하위 사용자가 다룰 문제다")
- 기술적 제약("이를 지원하려면 Y가 필요한데, 이는 우리의 Z 아키텍처와 충돌한다")
- 전략적 결정("B 대신 A를 쓰기로 했다. 이유는 ...")

이유는 시간이 지나도 유효해야 한다. 일시적인 사정("지금은 너무 바쁘다")은 적지 않는다. 그런 것은 실제 거절이 아니라 미룬 것이다.

## `.out-of-scope/`를 확인할 때

분류 중(1단계: 맥락 수집)에 `.out-of-scope/`의 파일을 모두 읽는다. 새 이슈를 검토할 때는 다음을 한다.

- 요청이 기존 범위 밖 개념과 일치하는지 확인한다
- 키워드가 아니라 개념의 유사성으로 비교한다. "야간 테마"는 `dark-mode.md`와 일치한다
- 일치하면 메인테이너에게 알린다. "`.out-of-scope/dark-mode.md`와 비슷한 요청입니다. 전에 [이유] 때문에 거절했습니다. 지금도 같은 생각이신가요?"

메인테이너는 다음 중 하나를 고를 수 있다.

- **확인**: 새 이슈를 기존 파일의 "이전 요청" 목록에 추가하고 닫는다
- **재검토**: 범위 밖 파일을 지우거나 고치고, 이슈는 일반 분류 절차를 따른다
- **이견**: 두 이슈가 관련은 있지만 서로 다르다. 일반 분류 절차를 따른다

## `.out-of-scope/`에 기록할 때

**enhancement**(bug가 아님)를 `wontfix`로 *거절*할 때만 기록한다. enhancement PR에도 이슈와 똑같이 적용한다. 거절한 PR을 여기에 기록해 두면 같은 요청이 새 코드로 다시 들어오지 않는다.

**이미 구현돼 있어서** `wontfix`로 닫는 경우에는 여기에 기록하지 **않는다**. 그것은 이미 만든 기능이지 거절한 기능이 아니다. 기록하면 중복 확인 때 실제로는 거절하지 않은 요청이 거절 기록으로 잡혀 결과가 틀어진다. 대신 이슈를 닫는 댓글에 그 기능이 이미 어디에 있는지 알려 준다.

절차:

1. 메인테이너가 기능 요청을 범위 밖으로 결정한다
2. 일치하는 `.out-of-scope/` 파일이 이미 있는지 확인한다
3. 있으면 새 이슈를 "이전 요청" 목록에 추가한다
4. 없으면 개념 이름, 결정, 이유, 첫 번째 이전 요청을 담은 새 파일을 만든다
5. 이슈에 결정을 설명하고 `.out-of-scope/` 파일을 언급하는 댓글을 올린다
6. `wontfix` 라벨을 붙여 이슈를 닫는다

## 범위 밖 파일 고치기와 지우기

메인테이너가 이전에 거절한 개념을 두고 생각을 바꾸면 다음과 같이 한다.

- 해당 `.out-of-scope/` 파일을 지운다
- 스킬은 예전 이슈를 다시 열지 않아도 된다. 예전 이슈는 과거 기록으로 남는다
- 재검토의 계기가 된 새 이슈는 일반 분류 절차를 따른다
