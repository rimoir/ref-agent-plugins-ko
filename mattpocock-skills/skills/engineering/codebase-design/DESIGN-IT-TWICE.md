# 두 번 설계하기(Design It Twice)

사용자가 이미 고른 깊게 만들 후보에 대해 다른 인터페이스 안을 살펴보고 싶어 하면 이 병렬 서브에이전트 패턴을 쓴다. Ousterhout의 "Design It Twice"를 바탕으로 한다. 처음 떠올린 안이 최선일 가능성은 낮다.

[SKILL.md](SKILL.md)의 용어(**모듈**, **인터페이스**, **교체 지점**, **어댑터**, **활용도**)를 쓴다.

## 절차

### 1. 문제 공간 정리하기

서브에이전트를 띄우기 전에, 고른 후보의 문제 공간을 사용자가 읽을 설명으로 쓴다.

- 새 인터페이스라면 어떤 것이든 충족해야 하는 제약
- 인터페이스가 기댈 의존성과 각 의존성이 속하는 유형([DEEPENING.md](DEEPENING.md) 참고)
- 제약을 구체적으로 보여 주는 대략적인 예시 코드. 제안이 아니라 제약을 눈에 보이게 하는 수단일 뿐이다

이 설명을 사용자에게 보여 주고 곧바로 2단계로 넘어간다. 서브에이전트들이 병렬로 작업하는 동안 사용자는 설명을 읽고 생각한다.

### 2. 서브에이전트 띄우기

서브에이전트를 3개 이상 병렬로 띄우고, 각각 새 컨텍스트 창으로 시작한다. 각 서브에이전트는 깊게 만든 모듈의 인터페이스를 **서로 완전히 다르게** 내놓아야 한다.

서브에이전트마다 별도의 기술 지시 요약(파일 경로, 결합 관계의 세부 사항, [DEEPENING.md](DEEPENING.md)의 의존성 유형, 교체 지점 뒤에 무엇을 둘지)을 프롬프트로 준다. 이 지시 요약은 1단계에서 사용자에게 보여 준 문제 공간 설명과 별개다. 에이전트마다 다른 설계 제약을 준다.

- 에이전트 1: "인터페이스를 최소화한다. 진입점은 최대 1~3개로 한다. 진입점 하나당 활용도를 최대로 높인다."
- 에이전트 2: "유연성을 최대로 높인다. 많은 사용 사례와 확장을 지원한다."
- 에이전트 3: "가장 흔한 호출자에 맞춘다. 기본 사용법을 아주 쉽게 만든다."
- 에이전트 4(해당할 때): "교체 지점을 넘나드는 의존성은 포트와 어댑터(ports & adapters)를 중심으로 설계한다."

지시 요약에는 [SKILL.md](SKILL.md)의 용어와 GLOSSARY.md의 용어를 모두 넣는다. 그래야 각 서브에이전트가 아키텍처 용어와 프로젝트의 공통 언어(ubiquitous language, 팀과 코드가 함께 쓰는 도메인 용어)에 맞게 이름을 붙인다.

각 서브에이전트가 내놓을 결과:

1. 인터페이스(타입, 메서드, 매개변수와 함께 불변 조건, 호출 순서, 오류 발생 방식)
2. 호출자가 어떻게 쓰는지 보여 주는 사용 예시
3. 구현이 교체 지점 뒤에 무엇을 숨기는지
4. 의존성 전략과 어댑터([DEEPENING.md](DEEPENING.md) 참고)
5. 장단점: 활용도가 높은 곳과 낮은 곳

### 3. 보여 주고 비교하기

사용자가 하나씩 이해할 수 있도록 설계안을 차례로 보여 준 다음, 글로 비교한다. **깊이**(인터페이스에서 얻는 활용도), **지역성**(변경이 어디에 모이는지), **교체 지점 위치**를 기준으로 대조한다.

비교가 끝나면 직접 추천을 내놓는다. 어떤 설계가 가장 좋다고 보는지와 그 이유를 말한다. 서로 다른 설계의 요소를 합치면 잘 맞겠다면 혼합안을 제안한다. 분명한 의견을 낸다. 사용자는 선택지 나열이 아니라 확실한 판단을 원한다.
