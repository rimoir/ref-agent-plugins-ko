# 안목 배우기

사용자가 하는 교정은 모두 에이전트에게 없던 안목이다. 적어 두지 않으면 다음 세션도 같은 실수를 하고 사용자는 또 고친다. 이 스킬은 그런 교정을 찾아 하나하나를 이유가 붙은 규칙으로 바꾸고, 다음 에이전트가 읽을 곳에 적는다.

하는 일은 **하나**다. 규칙을 쓴다. 컴포넌트 코드는 절대 바꾸지 않고, 사용자가 드러내지 않은 규칙은 절대 더하지 않는다.

## 철칙

1. **사용자의 안목만.** 모든 규칙은 사용자가 말하거나, 고치거나, 확인한 것으로 거슬러 올라가야 한다. 좋은 관행 같아 보인다는 이유로 규칙을 더하지 않는다. 그건 에이전트의 안목이고, 사용자가 고치던 것이 바로 그 안목이다.
2. **이유를 지어내지 않는다.** 사용자가 이유를 말하지 않았으면 *추정*이라고 표시한 이유를 제안하고, 쓰기 전에 확인을 받는다. 틀린 이유는 이유가 없는 것보다 나쁘다. 다음 에이전트가 맞지 않는 경우까지 그 논리를 넓혀 적용한다.
3. **제안하고 멈춘다.** 후보를 모두 보여 주고 사용자가 승인한 것만 쓴다. 틀린 규칙은 실수가 그랬을 것과 똑같이 앞으로의 모든 세션에서 되풀이된다.
4. **문장보다 검사가 낫다.** 코드를 맞춰 보는 것으로 위반을 찾을 수 있으면(금지된 값, 토큰 대신 쓴 생 hex 값, 금지된 속성) 린트 규칙, 토큰 제한, 테스트를 제안한다. 검사는 매번 돈다. 긴 파일 속 문장은 에이전트의 컨텍스트가 가득 차면 건너뛰어진다.
5. **여기 없던 에이전트를 위해 쓴다.** "아까 얘기한 것처럼"이나 "앞에서 본 카드" 같은 말을 쓰지 않는다. 컴포넌트 부류, 값, 토큰, 파일을 이름으로 밝힌다.

## 작업 흐름

### 1단계: 교정 모으기

현재 대화를 첫 턴부터 읽는다. 사용자가 이전 세션을 지목했고 그 기록을 읽을 수 있으면(Claude Code는 `~/.claude/projects/<project>/` 아래에 JSONL로 저장한다) 그것도 읽는다.

명시적인 교정은 일부일 뿐이다. 다섯 가지 신호를 모두 찾는다.

| 신호 | 예 | 알려 주는 것 |
| --- | --- | --- |
| 명시적 교정 | "아니, 테두리 말고 반투명 그림자로" | 규칙. 이유가 함께 오는 경우가 많다 |
| 말없는 편집 | 에이전트가 쓴 파일에서 사용자가 `duration: 400`을 `200`으로 바꿈 | 에이전트의 기본값이 틀렸고 사용자의 값이 규칙이다. 에이전트가 고치지 않았는데 파일이 바뀌었다는 알림을 보거나, 마지막으로 쓴 내용과 파일을 diff해서 찾는다 |
| 반복된 조정 | "더 작게." → "아직도 커." → "됐어" | 에이전트의 기본값이 전체 이동 거리만큼 어긋나 있었다. 거쳐 간 단계가 아니라 최종 도착점을 기록한다 |
| 되돌리기나 거부 | "그거 되돌려", A 대신 B 버전 고르기, 에이전트가 더한 것을 지우기 | 하지 말아야 할 것. 이유는 보통 빠져 있으니 3단계의 질문으로 넘긴다 |
| 확인받은 비자명한 선택 | "응, 아이콘은 버튼 밖에 둬" | 처음 보는 에이전트가 되풀이하지 않을 수도 있는 선택. 처음 보는 에이전트가 다르게 할 법할 때만 기록한다 |

하나마다 사용자의 정확한 말(또는 diff), 에이전트가 했던 것, 사용자가 대신 원한 것, 사용자가 댄 이유를 적는다.

안목이 아닌 것은 건너뛴다. 기능 버그, 한 화면에만 해당하는 내용("헤드라인은 Pricing이라고 써야 해"), 작업을 잘못 이해해서 받은 교정이 그렇다.

**완료 기준:** 모든 턴을 읽었고, 모든 교정이 출처 인용이나 diff와 함께 목록에 있다.

### 2단계: 거르기

모든 교정을 이 트리로 따라간다.

```
처음 보는 에이전트가 이 저장소에서 '다른' 컴포넌트를 만들 때도 같은 실수를 할까?
├── 아니요 (일회성: 이번 캠페인의 색, 이 페이지의 레이아웃) → 건너뜀(Skipped)
└── 예
    ├── 기존 규칙이 다루는가? DESIGN.md, CLAUDE.md / AGENTS.md, 프로젝트 스킬을 확인한다.
    │   ├── 예, 같은 말을 한다 → 규칙이 실패했다. 중복을 더하지 말고
    │   │   더 엄격하게(숫자, 토큰, "절대") 다시 쓴다(Rewrite).
    │   ├── 예, 서로 어긋난다 → 충돌(Conflict). 둘 다 보여 주고 사용자가 고른다.
    │   └── 아니요 → 계속
    ├── 코드를 맞춰 보는 것으로 위반을 찾을 수 있는가? → 검사 후보(Check candidate).
    │   이유가 어딘가에 남도록 한 줄 규칙도 함께 둔다.
    └── 사용자가 여기만이 아니라 어디에나 적용된다고 말했는가? → 전역 규칙을 어디에 두는지 묻는다.
        아니면 프로젝트 규칙이다.
```

**완료 기준:** 1단계의 모든 교정이 건너뜀, 다시 쓰기, 충돌, 검사 후보, 일반화할 규칙 중 하나로 끝난다.

### 3단계: 일반화하고 이유 찾기

다음에 만들 다른 컴포넌트에서 실수를 막았을 가장 좁은 수준을 고른다.

| 수준 | 예 | 판정 |
| --- | --- | --- |
| 개별 | "가격 카드에는 테두리 대신 그림자를 쓴다" | 너무 좁다. 이 카드만 지킨다 |
| 부류 | "떠 있는 표면(카드, 팝오버, 메뉴)은 `shadow-raised`로 배경과 분리하고 실선 테두리는 절대 쓰지 않는다" | 이렇게 쓴다 |
| 보편 | "테두리를 절대 쓰지 않는다" | 너무 넓다. 입력 필드, 구분선, 표가 망가진다 |

같은 교정이 서로 다른 컴포넌트 두 개 이상에서 나왔다면 부류 수준이라는 증거다. 두 수준이 다 맞아 보이면 묻는다.

규칙은 엄격하게 쓴다. 이 코드베이스의 값과 토큰 이름을 쓰고, "항상"이나 "절대"를 쓰고, "되도록"이나 "~하려고 해 본다"는 쓰지 않는다. 사용자가 선호로 말했을 때만 부드러운 표현을 쓴다.

그다음 이유다. 사용자가 이유를 말했으면 사용자의 말로 쓴다. 아니면 가장 그럴듯한 후보를 쓰고 *추정*으로 표시한 뒤 사용자에게 할 질문에 넣는다.

**제안 전 자체 점검:** 규칙과 이유만 읽고 원래 작업을 떠올린다. 다른 것은 아무것도 모르는 에이전트가 사용자가 원한 결과를 만들어 낼까? 여전히 틀린 버전을 만들 수 있다면 규칙이 너무 막연하다. 값, 토큰, 예외를 더한다.

**완료 기준:** 남긴 규칙마다 수준이 있고, 이유에는 사용자의 것인지 *추정*인지 표시가 있다.

### 4단계: 둘 곳 정하기

```
검사 후보인가?
├── 예 → 린트 규칙, 토큰 제한, 또는 테스트. 그리고 DESIGN.md에 한 줄 규칙
└── 아니요
    ├── 이 측면을 다루는 DESIGN.md 섹션이 ~40줄을 넘고, 일부 작업에만 관련 있는가
    │   (설정 폼을 만들 때 모션 규칙은 상관없다)?
    │   └── 예 → 섹션 전체를 프로젝트 스킬로 옮기고 DESIGN.md에는 한 줄 포인터를 남긴다
    └── 기본 → 저장소 루트의 DESIGN.md, 알맞은 섹션 아래:
        Surfaces · Color · Typography · Spacing & layout · Motion · Interaction · Copy
```

DESIGN.md나 섹션이 없으면 만든다.

**읽히도록 한다.** 어떤 에이전트도 불러오지 않는 DESIGN.md는 아무것도 바꾸지 못한다. CLAUDE.md와 AGENTS.md 어느 쪽도 DESIGN.md를 가리키지 않으면 프로젝트가 쓰는 쪽에 이 줄을 더하자고 제안한다: `Before building or changing UI, read DESIGN.md.`

항목 형식:

```md
## Surfaces

- **떠 있는 표면(카드, 팝오버, 메뉴)은 `shadow-raised`를 쓰고 실선 테두리는 절대 쓰지 않는다.**
  Why: 실선 테두리는 떠 있는 표면을 납작하고 무거워 보이게 한다. 반투명 그림자는 표면을 배경과 분리하고 두 테마 모두에 맞춰진다.
  <!-- 2026-11-12: "아니, 테두리 말고 반투명 그림자로" -->
```

주석에는 날짜와 사용자의 말을 담는다. 나중의 교정과 충돌할 때 어느 규칙이 더 새로운지, 사용자가 실제로 뭐라고 했는지 보여 준다.

### 6단계: 승인되면 쓰기

승인된 항목만 쓴다. DESIGN.md(와 스킬이나 설정 파일)의 결과 diff를 보여 준다. 검사는 구현해서 코드베이스 전체에 돌린다. 기존 코드에서 걸리는 것이 있으면 개수를 보고하고 경고로 둘지 위반을 고칠지 묻는다. 고치면 컴포넌트 코드가 바뀌므로 묻지 않고 고치지 않는다.

## 필수 출력 형식

### 추가할 규칙

| # | 사용자가 한 말 | 규칙 | 이유 | 위치 |
| --- | --- | --- | --- | --- |
| 1 | "아니, 테두리 말고 반투명 그림자로" | 떠 있는 표면은 `shadow-raised`를 쓰고 실선 테두리는 절대 쓰지 않는다 | 실선 테두리는 납작하고 무거워 보인다. 그림자는 두 테마 모두에 맞춰진다 | DESIGN.md › Surfaces |
| 2 | `Dropdown.tsx`에서 `duration: 400` → `200`으로 바꿈 | 드롭다운은 200ms에 열린다 | *추정:* 하루에도 여러 번 여는 표면이라 400ms는 굼떠 느껴졌다 | DESIGN.md › Motion |

### 답이 필요한 질문

*추정*한 이유, 애매한 일반화 수준, 전역인지 프로젝트인지 묻는 질문을 각각 한 줄씩 추천과 함께 적는다.

### 충돌

기존 규칙, 새 교정, 그리고 어느 쪽을 남길지.

### 검사로 만들기

검사 후보마다 정확한 구현(규칙 설정이나 테스트)과 현재 코드베이스에서 무엇이 걸릴지.

### 건너뜀

건너뛴 교정마다 한 줄로 이유를 적어 사용자가 뒤집을 수 있게 한다.

마지막은 이렇게 맺는다: "`write all` 또는 `write 1, 3`이라고 말하고 위 질문에 답해 주세요."

세션에 안목 교정이 없었으면 한 줄로 그렇게 말한다. 실패가 아니라 좋은 결과다.
