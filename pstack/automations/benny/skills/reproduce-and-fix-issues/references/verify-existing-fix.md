# 기존 수정 검증

열린 pull request나 병합된 커밋이 보고를 고쳤을 법할 때 이 모드를 쓴다.

수정은 기존 산출물이 소유한다. 그것을 검증한다. 편집하거나, 경쟁 패치를 작성하거나, 또 다른 pull request를 열지 않는다.

## 산출물 자격 판단

구체적인 산출물 하나가 있어야 한다.

- 증상을 다루는 코드 변경이 담긴 열린 pull request
- 병합된 pull request
- 코드와 의도가 일치하는 병합된 커밋

pull request나 커밋 없는 스레드 속 주장, tracker 상태, 브랜치 이름, 원인 가설로는 부족하다.

산출물이 여럿이면 원본 스레드나 tracker에서 링크한 것을 고른다. 그런 것이 없으면 영향받은 코드와 가장 가까운 것을 고르고 이유를 밝힌다.

## 작업 트리 보호

저장소가 지원하면 격리된 worktree나 다른 깨끗한 체크아웃을 쓴다. 사용자 변경을 덮어쓰지 않는다.

다음을 기록한다.

- 기준(baseline) 리비전
- 패치된 리비전
- pull request나 커밋 URL
- 두 실행이 공유하는 빌드와 환경 입력

일반 `github.com` pull request 링크를 쓴다.

## 기준 측정

열린 pull request면 그 base 브랜치를 기준으로 쓴다.

병합된 수정이면, 수정 직전 리비전이 빌드되고 옛 동작을 나타낼 때 그 리비전을 쓴다.

설정된 제어 어댑터로 다음을 한다.

1. 기준 앱을 띄운다.
2. 앱과 환경이 맞는지 확인한다.
3. 보고된 경로를 실제 UI 조작으로 돌린다.
4. 결정적 증상을 관찰한다.
5. 초기화하고 반복한다.
6. 기준 녹화, 스크린샷, 상태 확인을 캡처한다.

기준에서 증상이 두 번 나타나지 않으면 기준이 없는 것이다. 수정이 동작한다고 주장하지 않는다.

## 패치된 빌드 측정

같은 환경과 데이터로 pull request나 수정 커밋을 빌드해 실행한다.

1. 같은 UI 경로를 돌린다.
2. 두 번 반복한다.
3. 깨진 상태가 사라졌는지 확인한다.
4. 기대 상태가 나타나는지 확인한다.
5. 수정 후 녹화, 스크린샷, 같은 상태 확인을 캡처한다.

컴파일이나 테스트에서 멈추지 않는다. 수정 후 결과는 실행 중인 패치된 앱에서 나와야 한다.

## 결과

### 확인됨

기준에서 두 번 재현되고 패치된 빌드에서 두 번 해결된다.

- 운영 상태를 검증됨으로 표시한다.
- 산출물을 링크한다.
- 원본 사전 점검 뒤 원본 스레드에 간결한 답글을 하나 올린다.
- 수정 전후 결과를 넣는다.
- pull request는 열지 않는다.

### 불충분한 수정

기준과 패치된 빌드 모두에서 증상이 나타난다.

- 운영 상태를 재현됐지만 고쳐지지 않음으로 표시한다.
- 산출물을 링크하고 증상을 해결하지 못했다고 말한다.
- 이번 실행에서 아직 쓰지 않았다면 일반적인 재현 확인 원본 업데이트를 올린다.
- 경쟁 pull request는 열지 않는다.

### 결론 불가

기준에서 재현되지 않거나, 패치된 앱이 실행되지 않거나, 증거가 결정적 상태를 보여 주지 않는다.

- 성공을 주장하지 않는다.
- 어느 쪽을 측정하지 못했는지 밝힌다.
- 결과는 운영 스레드나 실행 출력에 남긴다.
- 직접 받은 질문에 답해야 하는 경우가 아니면 원본 스레드에 아무것도 올리지 않는다.

## 정리

두 빌드를 멈추고, 보존 정책에 따라 임시 프로필과 캡처를 지우고, 사용자 작업을 버리지 않은 채 저장소를 이전 상태로 되돌린다.
