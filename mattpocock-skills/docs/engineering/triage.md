## 하는 일

`triage`는 프로젝트 이슈 트래커의 이슈를 하나씩 살피며, 각 이슈를 **분류 역할**(유형 역할 하나와 상태 역할 하나)로 이루어진 작은 상태 기계에 따라 옮긴다. 결과로는 에이전트가 바로 작업할 수 있는 작업 지시서, 보고자에게 보내는 구체적인 질문, 이유를 기록하고 닫은 이슈 중 하나가 남는다.

이 스킬은 **직접 만들지 않은** 이슈에만 쓴다. 정리되지 않은 버그 보고, 새로 들어온 기능 요청, 예고 없이 올라온 외부 풀 리퀘스트처럼 외부에서 트래커로 들어와 보고자가 남긴 모습 그대로인 작업이 대상이다. [to-tickets](https://aihero.dev/skills-to-tickets)가 만든 [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)은 만들어질 때부터 에이전트가 바로 작업할 수 있는 상태이고, 거기에 `triage`를 돌려 봐야 잘해야 헛수고다. 규칙에는 예외가 없다. `/triage`는 들어온 이슈에만 쓰고, 직접 만든 이슈에는 쓰지 않는다.

손으로 라벨을 붙이는 방식과 다른 점이 하나 더 있다. 이 스킬은 추천하고 기다린다. 유형과 상태를 어떻게 판단했는지 이유와 함께 알리고 코드베이스에서 찾은 내용도 전하지만, 사용자가 지시하기 전에는 아무것도 적용하지 않는다.

## 언제 쓰나

`/triage`를 입력하고 원하는 것을 자연어로 설명해서 실행한다. [에이전트](https://www.aihero.dev/ai-coding-dictionary/agent)는 이 스킬을 스스로 실행하지 않는다. 예를 들면 "내가 봐야 할 게 있으면 보여 줘", "#42 좀 보자", "#42를 ready-for-agent로 옮겨 줘"처럼 말한다.

| 가진 것 | 쓸 스킬 |
| --- | --- |
| 다른 사람이 올린 정리되지 않은 보고로 가득한 트래커 | `/triage` |
| 아직 아무것도 적어 두지 않은 대략적인 내 아이디어 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| [스펙](https://www.aihero.dev/ai-coding-dictionary/spec)으로 만들 만큼 결론이 난 대화 | [to-spec](https://aihero.dev/skills-to-spec) |
| 에이전트가 바로 작업할 수 있는 티켓으로 나눌 스펙 | [to-tickets](https://aihero.dev/skills-to-tickets) |
| 라벨이 아니라 근본 원인을 찾아야 하는, 확인된 버그 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

## 사전 준비

`triage`는 이슈 트래커를 읽고 쓰므로, 먼저 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills)로 트래커와 라벨 이름을 설정해 두어야 한다. 아래 역할 이름은 **표준** 이름이다. 트래커에서 실제로 쓰는 라벨 문자열은 다를 수 있고, 그 대응표를 setup이 만들어 준다. 트래커가 이미 표준 이름을 그대로 쓰고 있다면 대응시킬 것도, 설정할 것도 없다.

외부 풀 리퀘스트를 요청 접수 경로로 볼지, 누구를 외부인으로 볼지도 트래커 설정이 정한다. 이 플래그는 기본값이 꺼짐이고 이제 setup이 묻지 않으므로, PR도 분류 대상에 넣으려면 `docs/agents/issue-tracker.md`에서 직접 켠다.

## 상태 기계

분류를 마친 항목에는 모두 유형 역할과 상태 역할이 정확히 하나씩 붙는다. 유형은 `bug`(무언가가 고장 났다)와 `enhancement`(새 기능이나 개선)다. 상태는 다음과 같다.

| 상태 | 뜻 |
| --- | --- |
| `needs-triage` | 검토해야 한다. 라벨이 없는 이슈는 보통 먼저 여기로 온다. |
| `needs-info` | 보고자의 답을 기다린다. 보고자가 답하면 `needs-triage`로 돌아간다. |
| `ready-for-agent` | 스펙이 완전히 정해졌고 에이전트 작업 지시서가 붙어 있다. [AFK](https://www.aihero.dev/ai-coding-dictionary/afk) 에이전트(사람 없이 에이전트 혼자 진행)가 가져갈 수 있다. |
| `ready-for-human` | 같은 작업 지시서에, 에이전트에게 맡길 수 없는 이유(판단, 외부 접근 권한, 수동 테스트)를 더한다. |
| `wontfix` | 이유를 기록하고 닫았다. |

쓰는 이름은 이것이 전부이고, "상태 역할은 정확히 하나"라는 불변 조건 덕분에 조회가 단순해진다. 동시에 이 부분은 이 [스킬](https://www.aihero.dev/ai-coding-dictionary/skill)에서 요청이 가장 많은 영역이기도 하다. 사용자들은 스펙은 정해졌지만 다른 이슈에 막힌 작업을 위한 상태를 하나 더 달라고 했고, 앞으로 어떤 조건이 생겨야 시작할 수 있는 `deferred` 작업용 상태와 종료 상태인 `implemented`도 요청했다. 아직 어느 것도 반영되지 않았다. 아래 질문을 본다.

`wontfix`는 닫는 이유에 따라 나뉜다. 이 가운데 하나만 기록 저장소에 기록하므로 구분이 중요하다.

| 닫는 이유 | 처리 |
| --- | --- |
| 이미 구현됨 | 이미 어디에 있는지 알려 주는 댓글을 남긴다. `.out-of-scope/`에는 아무것도 기록하지 않는다. 거절한 기능이 아니라 이미 만든 기능이고, 여기에 기록하면 중복 방지 검사가 틀린 결과를 내기 때문이다. |
| 거절(bug) | 정중하게 설명하고 닫는다. |
| 거절(enhancement) | `.out-of-scope/`에 파일을 만들고, 닫는 댓글에 그 파일 링크를 남긴 뒤 닫는다. |

`.out-of-scope/`에는 이슈 하나당이 아니라 거절한 **개념** 하나당 마크다운 파일 하나를 둔다. 파일은 데이터베이스 항목보다는 짧은 설계 문서처럼 쓰며, 무엇을 거절했는지, 왜 거절했는지, 그것을 요청한 이슈가 무엇인지 모두 적는다. `triage`는 무엇이든 평가하기 전에 이 디렉터리 전체를 읽고, 키워드가 아니라 개념으로 대조한다. 그래서 "night theme"도 `dark-mode.md`와 일치한다고 본다. 일치하는 파일을 찾으면 요청을 처음부터 다시 논의하지 않고, 이전 결정을 보여 준 뒤 지금도 같은 생각인지 묻는다.

## 작업 지시서를 쓰기 전에 검증한다

[집요한 질문](https://www.aihero.dev/ai-coding-dictionary/grilling)을 하기 전에 `triage`는 주장이 실제로 사실인지 확인한다. 버그면 보고자가 적은 단계대로 재현한다. PR이면 브랜치를 체크아웃하고 관련 테스트를 실행한다. 그다음 결과를 보고한다. 결과는 확인됨(코드 경로 포함), 재현 실패, 시도하기에는 정보 부족 중 하나다. 마지막 경우는 그 자체로 `needs-info`로 가야 한다는 가장 강한 신호다.

같은 과정에서 코드베이스를 대상으로 검사를 더 한다. **중복**(요청 문구가 아니라 도메인 개념으로 찾았을 때 이미 구현돼 있는가?)과 **이전 거절**(`.out-of-scope/`에 이미 거절한 기록이 있는가?)이다. 둘 다 비용이 적게 들고, 해당하면 둘 다 `wontfix`로 이어진다.

이 모든 과정은 산출물 하나를 잘 만들기 위해 있다. 바로 **에이전트 작업 지시서**(agent brief), 즉 이슈를 `ready-for-agent`로 옮길 때 올리는 정해진 구조의 댓글이다. 한번 올라가면 작업 지시서가 작업의 기준이 되고, 처음 보고는 참고용 맥락일 뿐이다. 작업 지시서는 정밀함보다 **오래 유효함**을 우선해 쓴다. 이슈가 `ready-for-agent`에서 몇 주씩 기다리는 동안 코드가 계속 바뀔 수 있기 때문이다. 그래서 타입, 시그니처, 동작 계약을 적고, 파일 경로나 줄 번호는 절대 적지 않는다. 재현으로 확인한 내용이 있으면 짐작으로 쓴 것보다 훨씬 탄탄한 작업 지시서가 된다.

## PR은 코드가 붙은 이슈다

트래커 설정이 외부 풀 리퀘스트를 요청 접수 경로로 본다면, PR도 같은 유형, 같은 상태, 같은 전환으로 같은 상태 기계를 거친다. 상태를 diff 기준으로 읽는 점만 다르다. `ready-for-agent`는 작업 지시서가 붙어 있고 에이전트가 코드에 다음 작업을 해야 한다는 뜻이고, `ready-for-human`은 사람이 병합할 준비가 됐다는 뜻이다. PR에 붙는 작업 지시서는 처음부터 새로 만드는 방법이 아니라, 기존 diff에 남은 작업이 무엇인지 적는다.

목록을 찾을 때는 *외부* PR만 보여 준다. 협업자가 진행 중인 브랜치는 분류 작업이 아니기 때문이다. 이 필터는 목록을 찾을 때만 적용하고, PR을 직접 지정하면 작성자와 상관없이 분류한다. 아직 다듬어지지 않은 부분이 하나 있다. GitHub 템플릿에서 외부 PR 목록을 가져오는 명령은 `gh pr list`에 `authorAssociation` 필드를 요청하는데, `gh`는 이 필드를 제공하지 않는다. 그래서 적힌 그대로의 명령은 바로 실패한다([#468](https://github.com/mattpocock/skills/issues/468)).

## 자주 묻는 질문

**`/to-spec`과 `/to-tickets`를 실행했는데, 그 티켓들이 분류되지 않은 채 남아 있어요. `/triage`를 돌려야 하나요?**
아니다. 그 티켓들은 이미 에이전트가 바로 작업할 수 있는 상태다. `to-tickets`는 게시하면서 `ready-for-agent` 라벨을 붙인다. AFK 실행기가 다른 처리 없이 바로 가져가게 하려는 것이다. 이 문제를 겪은 사용자는 스펙 흐름을 실행한 뒤 결과물에 `needs-triage`가 붙은 것을 보았고, AFK 실행기가 모든 티켓을 무시하는 상황을 겪었다. `triage`는 외부에서 들어오는 작업의 진입 경로이고, 스펙 흐름은 직접 시작한 작업의 경로다. 두 경로는 `ready-for-agent`에서 만나며, 그 전에는 만나지 않는다.

**`to-spec` → `to-tickets` → `implement` 흐름이 생겼는데 `triage`가 아직 필요한가요?**
외부에서 들어오는 작업이 있을 때만 필요하다. `triage`는 그 주 흐름보다 먼저 있었고 하는 일도 다르다. 다른 사람이 올린 보고를 처리하는 경로다. 트래커의 모든 항목이 직접 세운 계획에서 나왔다면 거의 쓸 일이 없다. 공개된 무언가를 관리하거나 팀원이 버그를 보고해 온다면, 그 작업이 가장 먼저 거치는 곳이 `triage`다. 주로 외부 기여자에게서 이슈를 받는 오픈소스 저장소에서 쓴다.

**에이전트가 `ready-for-agent`를 붙이려 했더니 `gh`가 라벨이 없다고 해요.**
알려진 미해결 버그다([#616](https://github.com/mattpocock/skills/issues/616)). `setup-matt-pocock-skills`는 라벨 이름을 `docs/agents/triage-labels.md`에 적지만, 트래커에 라벨을 만들지는 않는다. `gh label create`나 트래커 UI로 상태 라벨 다섯 개와 유형 라벨 두 개를 한 번만 직접 만들면 이 오류가 더는 생기지 않는다. 이슈에 커뮤니티가 만든 수정 브랜치 링크가 있지만 아직 병합되지 않았다.

**상태 다섯 개로는 부족해요. 막힘, 보류, 구현 완료 같은 상태는 어떻게 하나요?**
이 스킬에서 가장 많이 제기된 빈 부분이고, 요청은 여러 형태로 들어왔다. 먼저 스펙은 완전히 정해졌지만 다른 이슈가 닫히기를 기다리는 이슈가 있다([#139](https://github.com/mattpocock/skills/issues/139)). 보고자는 이때 `ready-for-agent`가 "엄밀히 말하면 맞지만" 오해를 부른다고 지적했다. 에이전트가 그 이슈를 가져갔다가 진행하지 못하고 막히기 때문이다. 다음으로 하기로 했지만 어떤 조건이 생겨야 시작할 수 있어서 아직 손댈 수 없는 작업이 있다([#297](https://github.com/mattpocock/skills/issues/297)). 마지막으로 "구현 완료, 검증 대기"를 나타내는 종료 상태가 있다. 이 상태가 없으면 AFK 실행기가 끝난 티켓을 다시 작업 대기열에 올릴 수 있다. Matt은 막힌 경우가 실제 문제라는 데 동의했고, 이름을 `blocked`로 할지 `paused`로 할지는 아직 정하지 않았다. 아직 어느 것도 반영되지 않았다. 사람들이 쓰는 우회 방법은 저장소 안에서만 쓰는 추가 라벨을 유형 라벨과 함께 붙이는 것이다. 이렇게 하면 표준 상태 역할 자리에 사실과 맞는 값이 들어가지만, 스킬은 그 추가 라벨을 모른다. 어떤 커뮤니티 파생 버전은 더 나아가 `needs-slicing`, `tracking`, 작업량 라벨을 추가했다. 그렇게 해도 동작하지만, 그건 그 파생 버전의 방식이지 이 스킬의 방식은 아니다.

**`/diagnosing-bugs`와 무엇이 다른가요?**
여기의 검증 단계는 일부러 얕게 한다. "이게 실제 문제인가, 대략 어디에 있는가"에 답할 만큼만 하고, 근본 원인을 찾지는 않는다. 보고자가 적은 단계로 몇 분 안에 버그가 재현되지 않으면, 솔직한 선택은 `needs-info`다. 지금 바로 파고들고 싶다면 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)를 쓴다. 지금은 두 스킬 모두 본문에서 서로를 언급하지 않는다. 한 사용자가 두 스킬 사이에 연결이 빠져 있다는 점을 찾아냈고, 이 문제는 아직 열려 있다.

**백로그 전체를 맡기고 알아서 돌게 해도 되나요?**
요청할 수는 있지만, 에이전트가 무엇을 읽는지 지켜봐야 한다. "확인이 필요한 항목 보여 주기" 과정은 *고르기* 위한 가벼운 목록이다. 거기서 하나를 고르면 그때 고른 항목의 [컨텍스트](https://www.aihero.dev/ai-coding-dictionary/context)를 전부 모은다. 이슈 스무 개를 한꺼번에 돌리면 에이전트가 알리지 않고 그 가벼운 목록을 근거로 삼을 수 있는데, 그 목록에는 이슈 본문만 있고 댓글은 없다. 한 사용자가 바로 이 문제를 겪었다. 이슈 세 개에 이미 "이미 고쳐졌으니 닫기를 권함"이라는 댓글이 있었는데, 세 개 모두 새 에이전트 작업 지시서를 받았다. 여러 이슈를 한꺼번에 처리하려면 이슈마다 댓글을 읽으라고 분명히 말한다.

**Linear처럼 GitHub Issues가 아닌 트래커에서도 동작하나요?**
그렇다. 트래커는 코드에 고정된 가정이 아니라 설정이고, 사람들은 Linear(`linear` CLI 사용), GitLab, `.scratch/` 아래의 일반 마크다운 파일로 이 스킬을 쓴다. 흔한 구성은 이슈와 계획에는 Linear, 코드와 PR에는 GitHub을 쓰는 것이다. "이슈 트래커"라고 하는 스킬은 Linear에, "PR"이라고 하는 스킬은 GitHub에 대응한다. 로컬 마크다운 트래커에는 아직 해결되지 않은 템플릿 버그가 있어서, 생성된 파일에 인수 기준이 최상위에 한 번, 에이전트 작업 지시서 안에 한 번, 두 번 들어갈 수 있다([#200](https://github.com/mattpocock/skills/issues/200)).

## 잘 동작하고 있다는 신호

- 다룬 항목마다 유형 역할과 상태 역할이 정확히 하나씩 붙어서 끝난다. 하나도 없거나 상태 두 개가 충돌하는 일이 없다.
- 라벨을 바꾸고 넘어가지 않고, 이유를 붙인 추천을 내놓은 뒤 멈춘다.
- `ready-for-agent`로 가기 전에 버그를 재현했거나, PR을 체크아웃해서 실행해 봤다.
- 작성한 작업 지시서에는 타입과 동작이 적혀 있고, 파일 경로와 줄 번호는 없다.
- 여섯 달 전에 거절한 요청이 다시 들어오면, 처음부터 새로 분류하지 않고 그 사실을 알리며 이전 이유를 인용한다.
- 올리는 모든 댓글이 `> *이 글은 분류(triage) 과정에서 AI가 작성했습니다.*`로 시작한다.

## 전체 흐름에서의 위치

`triage`는 주 흐름의 한 단계가 아니라 **진입 경로**다. 주 흐름은 직접 떠올린 아이디어에서 출발한다(집요한 질문, 스펙, 티켓, 구현, 리뷰). `triage`는 그 대신 외부에서 들어온 작업을 위한 나란한 경로다. 두 경로가 합쳐지는 곳은 작업 지시서가 붙고 `ready-for-agent` 라벨이 붙은 이슈다. [implement](https://aihero.dev/skills-implement)는 이 이슈를 [to-tickets](https://aihero.dev/skills-to-tickets)가 만든 티켓과 똑같이 가져간다. 작업 지시서를 쓰기 전에 요청을 더 구체화해야 하면, `triage`는 [grilling](https://aihero.dev/skills-grilling)과 [domain-modeling](https://aihero.dev/skills-domain-modeling)을 함께 실행해 질문 라운드를 한 번에 하나씩 진행한다. 그래서 결정이 날 때마다 `CONTEXT.md`와 ADR(아키텍처 결정 기록)에 바로 기록된다. 어느 경로에 해당하는지 모르겠으면 [ask-matt](https://aihero.dev/skills-ask-matt)가 알맞은 스킬을 알려 준다.
