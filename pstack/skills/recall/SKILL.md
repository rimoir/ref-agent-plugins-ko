# Recall

**작업을 시작하거나 재개하기 전에, 사용자의 최근 작업 맥락을 다시 세우고 지금 상황과 다음 할 일을 담은 짧은 캡슐을 돌려준다.**

짧게, 주제에서 벗어나지 않게 쓴다. 범위 안의 스레드에 필요한 것만 읽고 멈춘다.

맥락은 두 기록에 있다. 자기 채팅 기록에는 내가 한 일과 내린 결정이 있다. 공유 기록에는 같은 코드를 둘러싸고 다른 이름으로 일어난 모든 일이 있다. 사용자가 계속 보고하는 증상, 출시했다가 되돌린 수정, 프로덕션에서 아직 터지고 있는 에러다. 이 두 번째 기록은 소스 관리, 이슈 트래커, 채팅·이슈 채널, 장문 문서, 에러 추적에 있다. 버그 꼬리가 긴 기능은 이야기 대부분이 그쪽에 있으니 대화 기록만으로 재구성하지 않는다.

대화 기록은 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`에 있다. `<slug>`는 워크스페이스 경로에서 맨 앞 슬래시를 빼고 "/"를 모두 "-"로 바꾼 것이다(그래서 `/Users/you/proj`는 `Users-you-proj`가 된다). 한 줄이 채팅 메시지 하나다.

1. 분류하고 나서 넘긴다. 재개할 특정 이전 채팅 하나가 있다면 이 스킬이 아니라 `session-pickup` 플레이북이다. 습관을 오래가는 스킬로 만드는 것은 `automate-me`다. 사람이 읽을 작업 요약은 다른 일이다. Recall은 행동하기 전에 최근 채팅 여러 개에 걸친 작업 맥락을 불러온다. 사용자가 이미 완전한 상태 캡슐(경로, 브랜치, 변경)을 줬다면 그것을 쓰고 캐내기는 건너뛴다.
2. 검색 전에 범위를 고정한다. 기간("최근"은 실제 구간이고 기본값은 지난 7일), 주제가 주어졌다면 주제, 워크스페이스(기본값은 현재 활성 워크스페이스. 요청 없이 다른 프로젝트의 대화 기록을 읽지 않는다)를 정한다. 정한 범위를 되말한다. "전부"를 슬그머니 "최근 N개"로 바꾸지 않는다.
3. 채팅 기록 전반으로 펼친다. 빠르고 싼 모델로 병렬 subagent를 띄우고, 각자 말뭉치의 한 조각을 맡긴다. 모든 subagent에게 다음을 지시한다. 후보는 UUID 이름이 아니라 실제 수정 시각(`ls -t`) 순으로 정렬한다. 주제를 먼저 grep한 뒤 일치하는 채팅의, 관련 있는 부분만 읽는다. 현재 채팅과 뻔한 잡음(subagent, eval, 테스트 채팅)은 건너뛴다. 각 subagent는 같은 스키마로, 채팅마다 블록 하나씩 돌려준다. 주제, 사용자의 목표, 결정, 열린 스레드, 고전한 부분과 교정, 산출물(PR, 티켓, 브랜치)이고, 각 항목에 채팅 UUID를 인용한다. 채팅이 한두 개라면 펼치지 말고 직접 검색한다. 원본 대화 기록은 subagent 안에 남는다. 메인 스레드는 발견한 내용만 받는다. 각 subagent의 추론 수준은 **poteto-mode** 스킬의 Subagents 절에 따라 작업에 맞게 고른다.
4. 주제가 기능, 파일, 하위 시스템, 영역, 버그를 지목하면 언제나 공유 기록을 훑는다. 이것은 판단할 일이 아니라 기본값이고, "X에 대한 내 작업"이라고 해서 면제되지 않는다. 출처마다 조사자 subagent 하나를 agent 모드로 띄운다. readonly는 MCP 접근을 막기 때문이다. 각 조사자에게 "현재 상태는 어떤가, 무엇을 시도했다가 유지되지 못했나, 사용자는 아직 무엇을 보고하고 있나"를 묻는다. 조사자들은 채팅 기록 캐내기와 병렬로 돌린다. 결과 없음도 발견이다. 쓸 수 없는 MCP는 건너뛰고 그렇다고 말한다. 돌아온 것은 브리핑에 녹인다. 지목된 대상이 없는 순수한 활동 회상("이번 주에 뭐 했지")일 때만 이 단계를 건너뛴다. 그때는 자기 기록과 실제 현재 상태가 답의 전부다.
5. 실제 현재 상태와 대조한다. 캐내기와 훑기에서 나온 PR, 브랜치, 티켓을 `git`과 `gh`로 확인한다. 답이 에이전트가 실제로 한 일(실행한 도구, 읽은 파일, 부딪힌 에러)에 달려 있다면, 잘라 낸 로컬 사본만이 아니라 전체 대화 기록을 읽는다.
6. 아래 계약대로 브리핑을 쓴다. 스레드별로 묶는다. 지목된 주제를 벗어나지 않는다.

## 출력 계약

캡슐을 먼저, 그다음 스레드 상태, 그다음 문제, 그다음 다음 수를 둔다. 더 깊은 세부 사항은 아래로 내리거나 잘라 낸다.

- **캡슐.** 최대 5개 항목. 이 작업이 무엇이고 전체적으로 어디에 와 있는지.
- **스레드.** 하나에 한 줄씩, 앞에 상태 태그를 정확히 하나 붙인다. `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[verified, uncommitted]`, `[reverted #N]`, `[planned, not started]` 중 하나다. 태그 없는 스레드는 아직 덜 된 것이니 태그를 붙인다.
- **문제.** 최대 5개, 반복되는 것들. 사용자가 계속 보고하는 증상과 출시했다가 되돌린 수정을 넣어서, 다음 시도가 지난번 실패한 지점에서 시작하게 한다.
- **다음 수.** 가장 쓸모 있는 다음 행동 하나, 구체적으로.

인접한 기능이나 티켓은 이 작업을 막지 않는 한 넣지 않는다. 캡슐과 스레드 줄이 한 화면을 넘으면 스레드보다 세부 사항을 먼저 자른다. 브리핑은 **unslop** 스킬을 거쳐 쓰고, 채팅에서 나온 발견은 UUID로, 공유 기록에서 나온 발견은 출처(PR 번호, 티켓 ID, 채팅 permalink, 에러 트래커 이슈)로 인용하고, 공개 출력 전에는 사적인 맥락을 정리한다.

**답변:** 위 계약에 맞춘 브리핑.
