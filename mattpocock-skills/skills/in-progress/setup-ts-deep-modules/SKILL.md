# TS 깊은 모듈 설정

이 저장소의 모든 패키지를 **깊은 모듈**(작은 인터페이스 뒤에 많은 동작을 담은 모듈)로 만든다. 패키지의 공개 부분은 **진입점**(패키지 루트에 있는 파일)이고, 하위 폴더에 있는 것은 모두 숨겨진다. [dependency-cruiser](https://github.com/sverweij/dependency-cruiser)와 진입점만 유일한 접근 경로로 만드는 규칙을 설치하고, 그 규칙이 실제로 위반을 잡아내는지 확인한다.

용어(깊은 모듈, 인터페이스, 교체 지점(seam), 깊이)는 Skill 도구로 "codebase-design"을 호출해 가져오고, 작업 내내 그 용어를 쓴다.

## 강제하는 구조

```
src/packages/
  <name>/
    index.ts        ← 진입점(공개). 외부에서는 이 파일을 import한다.
    client.ts       ← 또 다른 진입점. 패키지는 진입점을 여러 개 둘 수 있다.
    lib/            ← 구현. 외부에서 숨겨지고, 안에서는 서로 자유롭게 import한다.
    tests/          ← 함께 두는 테스트와 픽스처(하위 폴더이므로 비공개).
```

공개 부분은 지정한 `index.ts` 하나가 아니라 패키지의 **루트 파일들**이다. 관례상 구현은 `lib/`에, 테스트는 `tests/`에 두어 모든 패키지가 같은 두 폴더 구조를 갖는다. 다만 규칙 자체는 일반적이다. *어느* 하위 폴더에 있든 *모든* 파일이 비공개이므로, 폴더를 추가할 때 설정을 늘릴 필요가 없다.

규칙은 다음과 같고 모두 `error`다.

- **진입점 경계**: 패키지 밖의 코드(앱 코드나 다른 패키지)는 그 패키지의 진입점(루트 파일)만 import할 수 있고, 하위 폴더의 파일은 import할 수 없다.
- **패키지 내부 자유**: 한 패키지 안의 파일끼리는 자유롭게 import한다.
- **테스트는 진입점을 거친다**: `<pkg>/tests/` 아래 파일은 어느 패키지의 진입점이든, 자기 `tests/` 픽스처든 import할 수 있다. 하지만 어느 패키지의 하위 폴더 내부도(자기 패키지 것도) import할 수 없다. 여러 패키지에 걸친 통합 테스트는 괜찮지만 내부 경로를 직접 import하는 것은 안 된다.
- **순환 금지**: 의존성 순환이 없어야 한다.

**배럴 파일이 아니라 진입점.** 공개 부분이 루트 파일 *전부*이므로, 패키지는 모든 것을 거대한 `index.ts` 하나로 몰아 내보내지 않고 작은 진입점 여러 개(`index.ts`, `client.ts`, `server.ts`)를 둘 수 있다. 하위 트리 전체를 다시 내보내는 배럴 파일(하위 모듈을 한꺼번에 다시 내보내는 index 파일)은 권장하지 않는다. 진입점은 작게 유지하고 구현은 하위 폴더에 숨긴다.

레이어 구분(어느 패키지가 어느 패키지에 의존할 수 있는지)은 *별개의* 문제다. 설정 파일에 주석 처리된 틀로만 남겨 두고, 이 저장소에서 채우도록 한다.

## 절차

### 1. 환경 파악하기

- **패키지 매니저**: `pnpm-lock.yaml`이 있으면 pnpm, `yarn.lock`이면 yarn, `bun.lockb`이면 bun, 그 밖에는 npm이다. 아래 모든 명령에 이 매니저를 쓴다(`pnpm`/`yarn`/`npm run`/`bunx`).
- **패키지 루트**: `src/`가 있으면 `src/packages`, 없으면 `packages`를 쓴다. 저장소에 이미 다른 뚜렷한 관례가 있으면 사용자에게 선택을 확인받는다.
- **기존 설정**: `.dependency-cruiser.*` 파일이 있는지 확인한다. 있으면 덮어쓰지 **않는다**. 위 규칙과 옵션을 기존 설정에 합치고, 무엇을 추가했는지 사용자에게 알린다.

**완료 기준:** 패키지 매니저, 패키지 루트, 기존 설정 여부를 모두 안다.

### 2. dependency-cruiser 설치하기

파악한 패키지 매니저로 `dependency-cruiser`를 devDependency로 설치한다.

**완료 기준:** `dependency-cruiser`가 `devDependencies`에 들어 있다.

### 3. 설정 파일 쓰기

[`dependency-cruiser.config.cjs`](./dependency-cruiser.config.cjs)를 저장소 루트에 `.dependency-cruiser.cjs`라는 이름으로 복사한다. `PACKAGES_ROOT`를 1단계에서 파악한 루트로 설정한다. 규칙은 경로 깊이를 기준으로 하고 확장자와 상관없으므로 다른 부분은 고칠 필요가 없다.

**완료 기준:** `.dependency-cruiser.cjs`가 올바른 `PACKAGES_ROOT`로 존재하고, 위 규칙을 구현한 forbidden 규칙이 모두 들어 있다.

### 4. 검사 명령에 연결하기

- `lint:boundaries` 스크립트를 추가한다. 내용은 `depcruise <packages-root>`(또는 `depcruise src`)다.
- 이 스크립트를 저장소의 통합 검사 명령, 즉 이미 타입 검사를 실행하는 명령(예: `check` / `ci` / `validate` 스크립트)에 넣는다. `tsconfig`는 건드리지 **않고** 경로 별칭도 추가하지 않는다.
- 통합 검사 스크립트가 없으면 `lint:boundaries`를 추가하고 사용자에게 CI에 넣으라고 알린다.

**완료 기준:** `lint:boundaries`가 있고, 타입 검사와 같은 명령 안에서 실행된다.

### 5. 예시 패키지 만들기

복사해 쓰는 템플릿으로 `<packages-root>/example/`을 만들어 커밋한다.

- `index.ts`는 진입점이다. 내부 파일에 일을 넘기는 함수 하나를 export한다(그래야 패키지가 그냥 전달만 하는 것이 아니라 *깊다*는 것이 보인다).
- `lib/impl.ts`: **하위 폴더**에 있는 내부 파일이다. `index.ts`가 import하고, 외부에서는 접근할 수 없다.
- `tests/example.test.ts`는 `../index`(진입점)**만** import하고 공개 함수를 대상으로 단언한다.

사용자에게 이 패키지는 복사하거나 지워도 되는 시작용 템플릿이라고 알린다.

**완료 기준:** 예시 패키지가 있고, 루트 진입점으로 동작을 드러내며, `impl`을 하위 폴더에 숨긴다.

### 6. 규칙이 실제로 위반을 잡는지 확인하기

이 단계가 스킬 전체의 완료 기준이다. 위반에서 실패하지 않는 설정은 쓸모가 없다.

1. `lint:boundaries`를 실행한다. 깨끗한 예시 패키지에서 **통과**해야 한다.
2. `tests/example.test.ts`에 내부 경로 import를 잠시 추가한다(예: `import { thing } from "../lib/impl"`). `lint:boundaries`를 다시 실행한다. `tests-through-entrypoints`로 **실패**해야 한다.
3. 내부 경로 import를 되돌린다. 한 번 더 실행하면 **통과**해야 한다.

**완료 기준:** 통과, 내부 경로 import에서 실패, 다시 통과를 직접 확인했다. 2번에서 실패하지 않으면 규칙이 제대로 연결되지 않은 것이므로 고친 뒤에 끝낸다.

### 7. 관례 문서화하기

**패키지 폴더 안에** `README.md`를 쓴다(`<packages-root>/README.md`, 이 문서가 다루는 패키지들 옆). 다음 내용을 담는다. `src/packages/<name>/` 구조(루트에 진입점, 구현은 `lib/`, 테스트는 `tests/`), "패키지는 진입점(루트 파일)으로만 import한다"는 규칙, `lint:boundaries` 실행 방법. **배럴 파일을 쓰지 말라고** 분명히 적는다. 하위 트리 전체를 index 하나로 다시 내보내지 말고 작은 진입점 여러 개를 두라고 쓴다. 내용은 복사해 쓰는 코드 조각과 각 규칙을 한 문단씩 설명한 것으로 제한한다.

그다음 저장소의 에이전트 지침 파일(`CLAUDE.md`가 있으면 그것, 없으면 `AGENTS.md`, 둘 다 없으면 `AGENTS.md`를 만든다)에 이 README를 가리키는 **컨텍스트 포인터**(컨텍스트 밖 자료를 가리키고 언제 읽을지 조건을 담은 짧은 참조)를 추가한다. 한 줄이면 된다. 예: `Packages are deep modules: see [src/packages/README.md](./src/packages/README.md) before adding or importing one.`(패키지는 깊은 모듈이다. 패키지를 추가하거나 import하기 전에 src/packages/README.md를 본다.) 이 줄이 있어야 에이전트가 경계 규칙을 모르고 어기는 대신 미리 알게 된다.

**완료 기준:** `<packages-root>/README.md`가 있고 배럴 파일을 쓰지 말라고 적혀 있으며, 저장소의 `CLAUDE.md`/`AGENTS.md`가 그 파일로 링크한다.

## 참고

- 설정의 `$1` 역참조(dependency-cruiser의 그룹 매칭)가 있어서 패키지는 자기 내부에 접근할 수 있고 외부는 접근할 수 없다. 이것을 패키지별 규칙 여러 개로 풀어 쓰지 않는다.
- 공개와 비공개는 **깊이**로 정한다. 패키지 루트 파일은 진입점이고, 하위 폴더에 있는 것은 모두 비공개다. 관례상 하위 폴더는 `lib/`(구현)와 `tests/`이지만 규칙은 이 이름을 고정하지 않는다. 어떤 하위 폴더든 비공개이므로 새 폴더를 만들어도 설정을 바꿀 필요가 없다. 진입점을 추가하려면 루트 파일을 하나 추가하기만 하면 된다(배럴 파일 없이).
- 패키지는 **한 단계로만** 둔다. 루트 바로 아래 자식만 패키지다. 패키지 내부는 얼마든지 깊게 중첩해도 되지만, 패키지 안에 다른 패키지를 둘 수는 없다.
- `.js`가 아니라 `.cjs`를 쓴다. 그래야 `"type": "module"` 저장소에서도 설정의 `module.exports`가 동작한다.
