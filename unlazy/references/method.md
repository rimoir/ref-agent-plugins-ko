# 깊이 트리

깊이 트리(Depth Tree)는 작업이 원래 나뉘는 경계와 통합 지점을 드러내는 데 쓴다. 깊이를 노력이나 토큰의 양을 산술적으로 약속하는 값으로 다루지 않는다.

원래 v1 방법은 이분할을 할 때마다 노력이 몇 배로 늘어난다고 주장했다. 이후 메인테이너가 진행한 소규모 비교에서는 에이전트가 그 산술을 따르기보다 깊이를 꼼꼼함의 신호로 받아들이는 것으로 보였다. 저장소에는 그 과거 수치를 재현하는 데 필요한 원본 자료가 없으므로, 그 수치는 벤치마크 증거가 아니라 설계 이력으로 본다. [../research/validation-protocol.md](../research/validation-protocol.md)를 본다.

## 규칙

1. **1층을 요청받은 작업으로 둔다.** 실제 도메인, 구성 요소, 검증 경계에서만 분할한다. 이분할은 필수가 아니다.
2. **리프(leaf, 트리 맨 아래의 작업 단위) 하나는 일관된 산출물 하나로 만든다.** 리프마다 정확한 소유권, 의존성, 완료 판정 게이트(완료로 인정하려면 충족해야 하는 조건 한 항목)를 준다. 붙어 있는 아주 작은 리프는 합치고, 독립된 결과 여러 개를 감춘 리프는 분할한다.
3. **분산 배정 전에 계약을 확정한다.** 원래 요청과 현재까지의 변경 사항을 다시 읽는다. 따로 빠뜨릴 수 있는 필수 결과와 완료 판정 기준을 바꾸는 제약을 모두 `PLAN.md`에 빠짐없이 목록으로 적는다. 그다음 리프가 시작되기 전에 인터페이스, 형식, 공유 가정, 오류 규칙, 이름 규칙, 소유권을 기록한다.
4. **중간 노드(branch)에는 통합 게이트를 준다.** 자식 게이트 파일을 다시 검증한 뒤, 합친 작업 전체에서 인터페이스, 엔드투엔드 동작, 회귀를 테스트한다.
5. **노력의 양은 게이트와 회차로 조절한다.** 구현, 전문가 재검토, 결함 찾기, 비용이 적게 드는 다듬기를 끝낸다. 모든 필수 게이트에 최신 증거가 있고 개선 회차를 한 번 더 해도 찾는 것이 없을 때만 멈춘다.

## 깊이 고르기

- 기능 하나, 범위가 정해진 버그 찾기, 문서 하나에는 얕은 트리나 단독 게이트 파일을 쓴다.
- 일관된 산출물 여러 개가 새 컨텍스트나 독립된 소유권의 이점을 얻을 때는 오케스트레이션(총괄 에이전트가 리프를 여러 에이전트에 나눠 맡기고 검증과 통합을 하는 방식) 트리를 쓴다.
- 더 깊은 트리는 추가되는 중간 노드가 실제 통합 경계와 맞을 때만 쓴다. 숫자를 맞추려고 빈 계층을 더하지 않는다.
- 명시적인 `tree N` 요청은 따르되 리프가 의미 있게 유지되도록 한다. 요청한 깊이 때문에 채우기용 리프가 생기면, 그 불일치를 밝히고 실제 작업 구조에 맞는 분해 중 가장 가까운 것을 쓴다.

깊이를 요청받지 않았으면, 독립된 산출물과 통합 지점을 모두 드러내는 가장 작은 트리를 고른다.

## 계약 확인 목록

배정(dispatch) 전에 다음 사항을 명시적으로 정한다.

- 담당, 그리고 확인 게이트나 수동 검토에 연결된 안정적인 계약 항목 id
- 리프마다 소유하는 정확한 파일이나 상대 glob
- 리프 사이에 공유하는 인터페이스와 스키마
- 의존성 id와 준비 상태
- 툴체인, 셸, 작업 디렉터리 요구 사항
- 오류 규칙과 호환성 규칙
- 통합을 증명하는 중간 노드 게이트
- 위험이 큰 수동 검토를 맡을 사람

선택 사항인 아이디어는 요구 사항이 아니다. 완료 판정에 관련된 사실만 바꿔 말해 적고, 인증 정보, 비공개 요청 원문, 관련 없는 컨텍스트를 저장소 상태에 복사하지 마라. 사용자가 범위를 바꾸면 계약 개정 번호를 올리고, 새로 배정하기 전에 영향을 받는 대응 관계를 모두 대조해 맞추고, `REMOVED_BY_USER`는 사용자가 명시적으로 권한을 준 경우에만 쓴다.

동시에 실행하는 두 리프가 같은 경로를 소유하게 하지 마라. 공유 작업을 나눌 수 없으면 그 작업을 앞선 의존성으로 두거나 전용 통합 리프로 만든다.

## 완료 계층

| 층 | 증명 |
|---|---|
| 리프 | 최신 실행 증거와 검토한 수동 증거 |
| 중간 노드 | 재검증한 자식과 자식 간 통합 검사 |
| 루트 | 현재 요청 다시 읽기, 모든 계약 행 대조, 모든 중간 노드 통합, 회귀 확인, 최종 주장 재측정 |

부분 단위의 완료가 통합을 뜻하지는 않는다. 리프에서 위쪽으로 검증하고, 루트 게이트 파일과 현재 계약 항목 목록이 충족된 뒤에만 보고한다. 담당이나 확인 수단이 빠졌거나, 참조가 최신이 아니거나, 포기, 연기, 담당자 결정이 있으면 완료가 아니라 눈에 보이는 인계다.
