# 타입 시스템 규율

타입 검사기는 증명 보조기다. 불가능한 상태, 어긋난 원시 타입, 처리하지 않은 변형을 컴파일 시점에 없애는 데 쓴다. 타입이 무시하게 놔두는 경우는 컴파일러가 막을 수 있었던 런타임 실패가 된다. 처리기를 늘리기보다 오류와 특수 경우가 애초에 존재할 수 없게 정의하는 편을 택한다. 표현할 수 없는 상태, 전함수(total function), 인터페이스 재설계(아래 패턴들)가 그 도구다.

어떤 타입 언어에도 적용된다. `typescript-best-practices` 같은 스킬이 구체적인 문법으로 뒷받침한다.

**패턴:**

- **불가능한 상태를 표현할 수 없게 만든다.** 변형은 합 타입(sum type)으로 모델링한다. TypeScript의 판별 유니언, Rust/Swift/Kotlin의 페이로드를 가진 enum, Scala의 sealed class, Haskell/OCaml의 ADT가 그것이다. 모순된 조합이 컴파일되는 선택적 필드 묶음으로 상태를 모델링하지 않는다. 미묘한 안티패턴이 있다. `{ completed: boolean; completedAt?: Date }`는 의미 없는 `completed: true; completedAt: undefined`를 허용한다. 불리언은 `completedAt !== null` 같은 단일 출처에서 유도하거나, 변형을 `{ kind: 'open' } | { kind: 'done'; at: Date }`처럼 명시적으로 모델링한다. 버그 때문에 "잠깐, 이 조합이 실제로 생길 수 있나?"라고 묻게 된다면 타입이 너무 느슨한 것이다.
- **타입은 제한이 아니라 구성이다.** 느슨한 타입에서 검사로 원하는 값을 깎아 내지 말고, 원하는 값에서 출발해 타입을 쌓아 올린다. 정제 타입(refinement type)이 필요해 보이는 불변식은 대개 구성 한 번이면 해결된다. 비어 있지 않은 리스트는 길이를 검사한 리스트가 아니라 머리와 나머지다. 유효한 시간 범위는 순서를 지켜야 하는 타임스탬프 두 개가 아니라 시작과 지속 시간이다. 특권을 가진 표현은 없다. 쌍의 리스트는 그렇게 해석하면 짝수 길이 리스트다. 그러니 불가능한 값을 만들 수 없는 모양을 고르고, 호출자에게 필요한 인터페이스는 그 위에 노출한다.
- **의미 있는 원시 타입에 브랜드를 붙인다.** `UserId`와 `OrderId`는 내부적으로 문자열이지만 서로 바꿔 쓸 수 있으면 안 된다. Rust의 newtype, Swift의 opaque type, Kotlin의 value class, Haskell의 phantom type, TypeScript의 브랜드 교차 타입을 쓴다. 생성할 때 한 번 검증하고, 그다음부터는 타입을 믿는다.
- **외부 데이터는 파싱하기 전까지 타입이 없다.** RPC 페이로드, JSON, IPC 메시지, CLI 인자, 설정 파일, 환경변수, 데이터베이스 행이 그렇다. 모든 경계에 비정형 입력을 타입 있는 모델로 바꾸는 파싱 함수를 둔다. 검증을 어디에 둘지는 **boundary-discipline** 원칙 스킬을 본다.
- **타입 시스템을 속이지 않는다.** 컴파일러를 우회하는 캐스트, 안전하지 않은 강제 변환, assertion 함수는 잠복한 런타임 크래시다. 컴파일러가 어떤 사실을 증명하지 못하면 직접 증명하거나(검증하고, 좁히고, 모델을 정제한다) 그 캐스트가 위험 요소임을 받아들인다.
- **빠짐없는 매칭은 컴파일러의 일이다.** 합 타입에 매칭할 때, 새 변형이 추가되었는데 처리하지 않으면 컴파일이 실패해야 한다. 언어가 주는 관용구를 쓴다. TypeScript의 `never` 타입 바인딩, Rust의 타입 주석 없는 `match`, Haskell의 `-Wincomplete-patterns`, Kotlin의 sealed class 매칭 완전성 검사다.
- **권위 있는 스키마에서 타입을 유도한다.** protocol buffer, OpenAPI 명세, GraphQL 스키마, 데이터베이스 마이그레이션, 디자인 시스템 토큰 파일이 모양을 정의하면, 나란한 타입을 손으로 만들지 말고 거기서 유도한다. **encode-lessons-in-structure** 원칙 스킬을 본다.
- **부분성이 드러나는 곳에서만 타입을 강화한다.** 런타임 assertion, null 검사, "이런 일은 절대 없어야 한다"는 throw는 타입이 너무 약한 곳을 표시한다. 그 검사를 타입으로 끌어올린다. 그리고 멈춘다. 타입 시스템의 일은 데이터를 최대한 정밀하게 묘사하는 것이 아니라 각 사용처가 처리해야 할 경우를 추적하는 것이다. 전함수를 택한다. 빈 리스트의 `sum`은 0이므로 평범한 리스트를 받는다. 빈 리스트의 `head`는 답이 없으므로 비어 있지 않은 리스트를 요구한다.

**점검 질문:**

- "이 필드 조합이 언제 유효한지 설명하는 주석을 쓸 수 있나?" 그렇다면 타입이 너무 느슨하다. 합 타입으로 나눈다.
- "함수 인자 두 개가 같은 원시 타입이지만 뜻이 다른가?" 브랜드를 붙인다.
- "이 `any`, 이 `as`, 이 `assertNotNull`은 어디서 왔나?" 경계까지 추적해서 거기서 검증한다.
- "다음 달에 새 변형이 추가되면 컴파일러가 다음 에이전트에게 어디에 케이스를 추가할지 알려 주나?" 아니라면 매칭이 빠짐없지 않은 것이다.
- "이 타입이 다른 파일이 소유한 모양을 복제하고 있나?" 대신 유도한다.
- "연산을 전함수로 유지하려고 이 타입을 강화하나, 아니면 그저 더 정밀하게 하려고 하나?" 그러지 않아도 panic이 나지 않는다면 평범한 타입을 유지한다.
