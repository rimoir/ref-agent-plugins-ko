# 경계 규율

검증, 타입 좁히기, 에러 처리는 시스템 경계에 둔다. 내부 코드는 조건 없이 믿는다. 비즈니스 로직은 순수 함수에 산다. 껍데기는 얇고 기계적이다.

**이유:** 흩어진 검증은 시끄럽고 중복되며 안전하다는 착각을 준다. 로직을 프레임워크 연결 코드 밖에 두어야 프레임워크 없이 테스트할 수 있다.

**패턴:**
- **경계에서**(CLI 인자, 설정 파일, 외부 API, 네트워크 프로토콜): 검증하고, 에러를 반환하고, 방어적으로 처리한다.
- **시스템 안에서:** 타입이 붙은 데이터, 에러 전파, 재검증 없음. 타입을 믿는다.
- **경계를 넘을 때.** 경계의 사적인 표현이 아니라 도메인 개념을 노출한다. 범용 메커니즘은 안쪽에, 특수 목적 정책은 가장자리에 둔다.

**적용:**

검증과 에러 처리
- 설정은 비즈니스 로직 안이 아니라 파싱 시점(경계)에 검증한다
- 원본 데이터는 경계에서 도메인 타입으로 파싱한다
- 전송, 저장, 프레임워크, wire 타입을 공개 표면으로 다시 내보내지 않는다
- 경계에서 이미 검증했다면 호출 사슬 깊은 곳에 중복 nil 체크를 두지 않는다

코드 구성
- 비즈니스 로직은 프레임워크 의존성 없는 순수 함수에 둔다
- 파싱 함수: 원본 바이트를 타입이 붙은 상태로 바꾸는 순수 변환
- 프롬프트 구성: 구조화된 상태를 넣으면 문자열이 나온다
- 점수 매기기와 평가: 상태를 결과로 바꾸는 순수 변환

**점검:**
- "이 데이터는 지금 시스템 경계를 넘고 있나?" 아니라면 검증은 중복이다.
- "껍데기가 그냥 부르기만 하는 순수 함수로 만들 수 있나?" 그렇다면 뽑아낸다.
