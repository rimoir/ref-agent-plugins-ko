# 이슈 재현과 수정

원본 스레드에 신뢰할 수 있는 분류 마커가 달릴 때까지 기다린다. 대상 앱의 실제 UI로 정확한 증상을 재현한다. 기존 수정이 있으면 그 수정을 검증한다. 재현이 확인된 뒤에만 범위를 제한한 수정을 시도한다.

자동화가 넘겨주는 외부 Benny 설정을 불러온다. 설정, 필수 액션, 제어 어댑터, 완성된 기능 맵 중 하나라도 없으면 안전하게 실패(fail closed)한다.

## 절대 안전 규칙

- 작업을 시작하기 전에 원본 채널과 루트 스레드 좌표를 고정한다.
- 원본 채널에 루트 메시지를 절대 올리지 않는다.
- 원본 스레드에 글을 올리기 전마다 원본 부모 메시지를 사전 점검한다.
- Slack에 글을 올리는 주체는 코디네이터 하나뿐이다.
- 위임받은 분석 워커는 읽기 전용이며 발견 사항이나 미디어 메모만 돌려준다.
- 수정 단계의 코드 워커는 그 환경에서 Slack 자격 증명과 모든 Slack 쓰기 액션이 빠져 있음을 입증할 수 있을 때만 편집할 수 있다. 그렇지 않으면 코디네이터가 편집한다.
- 모든 하위 프롬프트는 `SendSlackMessage`, `PostToSlack`, `chat.postMessage`를 비롯한 모든 Slack 쓰기를 명시적으로 금지해야 한다.
- 하위 에이전트에게 Slack 토큰, 게시 지침, 게시용 원본 좌표, 외부 보고 권한을 절대 주지 않는다.
- 하위 에이전트가 실행에 Slack 쓰기 권한을 필요로 하면 띄우지 않는다.
- 유틸리티 봇은 증거 출처다. 사람이 명시적으로 수정을 맡기지 않는 한 수정을 소유하지 않는다.
- 결정적 증상(discriminating symptom)이 실제 UI 조작으로 정확히 두 번 나타나야 한다.
- 상태 검사는 관찰을 확인하는 데 쓸 수 있다. 증상을 주입하거나 강제로 만들어서는 안 된다.
- 재현이 확인되지 않으면 직접 작성한 수정도 없다.
- 기존 pull request나 커밋이 있으면 실행을 검증 모드로 바꾼다. 그 위에 덮어쓰지 않는다.
- pull request 링크는 `github.com` 형식을 쓴다.
- 캡처, 녹화, 로그, 토큰은 소스 관리에 넣지 않는다.
- 위임 분석에는 pstack의 `principle-guard-the-context-window`를 쓴다.
- 재현, 수정, 검증 전반에 pstack의 `principle-sequence-verifiable-units`, `principle-fix-root-causes`, `principle-prove-it-works`를 적용한다.

## 1. 원본 좌표 고정

작업 목록을 만들거나 위임하기 전에 다음을 한다.

1. 트리거 채널이 설정된 원본 채널과 같은지 확인한다.
2. `trigger.thread_ts`가 있으면 `SOURCE_THREAD_TS`를 그 값으로 둔다. 없으면 `trigger.ts`를 쓴다.
3. `SOURCE_THREAD_TS`가 비어 있지 않은지 확인한다.
4. `SOURCE_CHANNEL_ID`와 `SOURCE_THREAD_TS`를 불변 값으로 저장한다.
5. 원본 스레드를 읽고 루트가 정확히 그 좌표를 갖는지 확인한다.
6. 원본 퍼머링크를 가져온다.

이 값을 답글 타임스탬프, 운영 타임스탬프, 상태 메시지 타임스탬프로 절대 바꾸지 않는다.

원본 채널에 글을 올리기 전마다 다음을 한다.

1. 불변 좌표로 스레드를 읽는다.
2. 부모 메시지가 존재하고, 삭제되지 않았고, 여전히 원본 채널에 속하는지 확인한다.
3. `channel=SOURCE_CHANNEL_ID`와 `thread_ts=SOURCE_THREAD_TS`로만 보낸다.
4. 스레드를 다시 읽고 새 메시지가 답글인지 확인한다.

하나라도 실패하면 아무것도 올리지 않는다. 루트나 대체 채널로 재시도하지 않는다.

## 2. 분류 계약 대기

설정된 판정 대기 예산 동안 원본 스레드를 지켜본다. 기다리는 동안은 아무 말도 하지 않는다.

판정은 다음을 모두 만족할 때만 받아들인다.

- 작성자가 `slack.triage_identity_user_id`와 일치한다.
- `SOURCE_THREAD_TS` 아래의 답글이다.
- 설정된 마커를 정확히 하나 담고 있다.

공개 마커 형식은 다음과 같다.

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

`bug`나 `performance`일 때만 진행한다. 선택적 tracker URL을 받아 둔다. `other`, 판정 없음, 신뢰할 수 없는 작성자, 충돌하는 마커, 시간 초과일 때는 조용히 멈춘다.

이 마커는 비공개 봇 신원 확인과 자유 형식 판정 매칭을 대신한다.

## 3. 소유권과 수정 산출물 관문 적용

작업을 시작하기 직전에 스레드를 다시 읽는다.

### 누군가 명시적으로 고치고 있을 때

사람이 수정을 맡겠다고 분명히 밝히거나, 구체적인 구현 계획을 내놓거나, 다른 에이전트에게 구현, 패치, 수정, pull request 생성을 요청하면 멈춘다.

다음은 수정 소유로 보지 않는다.

- 봇이 증거를 요약한다.
- 도구가 로그나 티켓을 조회한다.
- 누군가 봇에게 진단, 설명, 조사, 재현을 요청한다.
- 봇이 구현하겠다는 동의 없이 원인 가설을 올린다.

봇이 있는지가 아니라 요청된 행동을 보고 판단한다.

### 수정 산출물이 이미 있을 때

이 보고를 고쳤을 법한 열린 pull request나 병합된 커밋이 있으면 `references/verify-existing-fix.md`로 넘어간다.

산출물은 스레드, tracker 이슈, 저장소 이력, pull request 검색에서 나올 수 있다. 커밋이나 pull request 없는 주장은 수정 산출물이 아니다.

사람이 작업을 맡았지만 아직 산출물을 내지 않았으면 멈춘다. 그 사람과 경쟁하지 않는다.

## 4. 선택적 운영 스레드 열기

`slack.operations_channel_id`가 설정돼 있으면 코디네이터는 그 채널에 루트 상태 메시지를 하나 만들 수 있다. 재현 워크플로에서 허용되는 루트 게시는 이것뿐이다.

그 좌표를 `OPERATIONS_CHANNEL_ID`와 `OPERATIONS_THREAD_TS`로 저장한다. 원본 좌표와 절대 혼동하지 않는다.

설정된 일반 유니코드 상태 문자열을 쓴다. 상태 문구는 짧게 유지한다.

- Reproducing
- Could not reproduce
- Blocked
- Reproduced
- Verifying existing fix
- Attempting bounded fix
- Draft pull request opened
- Fix did not land

설정된 Cursor Slack 액션을 우선한다. `BENNY_SLACK_BOT_TOKEN`은 이 상태 메시지 하나를 편집하는 것처럼 좁은 빠진 기능을 위해 사용자가 설정해 둔 경우에만 쓴다. 토큰을 워커에게 절대 노출하지 않는다.

운영 채널이 설정되지 않았으면 자세한 상태는 자동화 실행 출력에 남긴다. 원본 채널 루트 메시지로 대신하지 않는다.

## 5. 제어 어댑터 불러오기와 점검

`references/control-adapter.md`와 `control.feature_map_path`의 완성된 맵을 읽은 뒤 `control.skill_name`이 가리키는 스킬을 호출한다.

보고된 사용자 경로에 맞는 기능 맵 섹션을 찾는다. 앱을 조작하기 전에 그 섹션을 읽는다. 해당 기능을 다루는 섹션이 없으면 경로나 셀렉터를 지어내지 말고 실행을 차단됨으로 표시한다.

일곱 가지 기능이 모두 있어야 한다.

1. 설정된 대상 앱과 테스트 환경을 띄운다.
2. 맵에 있는 기능으로 이동하고 문서화된 상태를 실행해 본다.
3. 클릭, 타이핑, 키, 스크롤, 드래그, 크기 조절, 이동으로 실제 UI를 조작한다.
4. 상태를 바꾸지 않고 검사한다.
5. 스크린샷을 찍는다.
6. 화면 녹화를 시작하고 멈춘다.
7. 프로세스, 세션, 프로필, 임시 데이터를 정리한다.

어댑터가 없거나 필수 기능이 하나라도 빠지면 운영 상태를 차단됨으로 표시하고 멈춘다. 스크린샷, 단위 테스트, 상태 변경, 소스 읽기를 UI 재현인 척하지 않는다.

## 6. 보고 내용 파악

원본 스레드 전체와 tracker 이슈가 있으면 그것까지 읽는다.

다음을 모은다.

- 정확한 행동 경로
- 기대 동작
- 관찰된 동작
- 둘이 갈라지는 결정적 상태
- 빈도
- 버전, 환경, 플랫폼
- 첨부 파일과 오류 시그니처
- 후보 코드 영역

스크린샷과 영상을 살펴본다. 쓸모가 있으면 코드 이력, 테스트 아이디어, 영향 범위(blast radius) 파악, 미디어 검토에 읽기 전용 병렬 워커를 쓴다. 각 워커는 좁은 질문 하나와 Slack 쓰기 금지 조항을 받는다.

저장소 안에서 그 행동을 추적한다. 회귀 이력과 방어 코드는 pstack의 `why` 스킬로 본다. 경쟁하는 원인 가설을 세우고 그 가설들을 가를 증거를 찾는다.

## 7. 재현

제어 어댑터로 대상 앱을 띄운다.

행동하기 전에 앱, 워크스페이스, 계정, 데이터 세트, 기능 상태가 맞는지 확인한다. 안정적인 앱 마커를 쓴다. 창 순서나 익숙한 제목만 믿지 않는다.

보고된 경로를 실제 UI 조작으로 따라간다.

재현됐다고 말하기 전에 다음을 한다.

1. 올바른 최종 상태를 명시한다.
2. 깨진 최종 상태를 명시한다.
3. 둘이 갈라지는 지점까지 간다.
4. 깨진 상태를 관찰한다.
5. 두 번째 시도가 독립적이도록 상태를 충분히 초기화한다.
6. 같은 경로를 반복해 같은 깨진 상태를 다시 관찰한다.
7. 가능하면 실제 상태 값으로 교차 확인한다.

예상된 대화상자, 로딩 상태, 설정 단계는 버그가 아니다. 올바른 동작과 깨진 동작을 가르는 최종 상태를 캡처한다.

설정된 재현 예산을 쓴다. 예산 안에 증상이 재현되지 않으면 깔끔하게 `Could not reproduce` 결과를 보고한다. 환경이 필수 기능을 제공하지 못하면 `Blocked`를 보고하고 무엇이 빠졌는지 적는다.

## 8. 증거 캡처와 검토

재현에 성공하면 다음을 한다.

- 증상까지 이어지는 전체 경로를 녹화한다.
- 깨진 최종 상태의 스크린샷을 찍는다.
- 정확한 단계와 관찰된 상태를 짧은 메모로 남긴다.
- 산출물은 설정된 임시 산출물 디렉터리에 둔다.

읽기 전용 미디어 검토자에게 질문 하나에만 답하게 한다. 증거가 결정적인 깨진 상태를 눈에 보이게 보여 주는가?

답이 아니오이거나 불확실하면 재현은 확인되지 않은 것이다. 더 나은 증거를 캡처하거나 `Could not reproduce`를 쓴다.

자세한 증거는 운영 스레드가 설정된 경우 그곳에만 올린다. 원본 업데이트는 간결하게 유지한다.

## 9. 재현 결과 보고

운영 상태를 먼저 업데이트한다.

`Could not reproduce`나 `Blocked`이면 원본 스레드에 아무것도 올리지 않는다. 결과는 운영 스레드나 실행 출력이 담는다.

재현이 확인되면 원본 사전 점검을 돌리고 요청받지 않은 원본 답글을 최대 하나 올린다.

- 이슈가 재현됐다고 말한다.
- 운영 증거 스레드가 있으면 링크한다.
- 짧은 발견 사항을 최대 세 개 넣는다.
- tracker 이슈가 있으면 링크한다.
- 기본으로 담당자를 멘션하지 않는다.

설정된 Slack 액션이 증거를 같은 원본 스레드 안에 두고 조직의 보존 정책이 허용할 때만 증거를 첨부한다.

설정된 거부 대기 시간 동안 기다린다. 사람이 설정이나 해석이 틀렸다고 보여 주면 재현을 한 번 바로잡는다. 유효한 거부 없이 대기 시간이 끝나기 전에는 수정 단계를 시작하지 않는다.

## 10. 기존 수정 검증

수정 산출물이 있으면 `references/verify-existing-fix.md`를 따른다.

검증은 기준(baseline) 빌드에서 증상이 나타나고 패치된 빌드에서 사라짐을 보여야 한다. 두 경로 모두 실제 UI로 두 번씩 돌린다.

기존 수정을 편집하거나, 경쟁 패치를 더하거나, 대체 pull request를 열지 않는다.

## 11. 범위를 제한한 수정의 자격 판단

다음을 모두 만족할 때만 수정을 시도한다.

- 결과가 순수하게 확인된 재현이다.
- 미디어 검토가 깨진 최종 상태를 확인했다.
- 기존 수정 산출물이 나타나지 않았다.
- 거부 대기 시간 동안 아무도 수정을 맡겠다고 하지 않았다.
- 런타임 증거가 근본 원인을 짚는다.
- 예상되는 변경이 설정된 수정 예산과 저장소 범위 안에 들어간다.
- 제어 어댑터가 기준 빌드와 패치된 빌드를 모두 돌릴 수 있다.

하나라도 어긋나면 재현 보고만 남기고 pull request 없이 멈춘다.

관문을 통과하면 운영 상태를 `Attempting bounded fix`로 업데이트한다.

## 12. 근본 원인 파악과 구현

모든 Slack 게시, 최종 diff 검토, 커밋, pull request는 코디네이터가 맡는다.

읽기 전용 워커는 다음을 할 수 있다.

- 코드와 이력 추적
- 테스트 제안
- 영향 범위 파악
- diff 검토
- 미디어 검토

워커는 편집하지 않고, 외부 쓰기를 실행하지 않고, 상태를 올리지 않고, 수정을 소유하지 않는다.

이 단계에서 범위가 좁은 코드 편집은 도구 격리로 그 워커에게서 Slack 자격 증명과 모든 Slack 쓰기 액션이 빠졌을 때만 위임할 수 있다. 그래도 프롬프트에는 명시적인 Slack 쓰기 금지를 넣어야 한다. 코디네이터가 편집을 검토하고 필요한 테스트를 돌리거나 검증한다. 도구 격리가 불확실하면 편집은 코디네이터가 한다.

런타임 증거로 메커니즘을 확인한다. 편집하기 전에 경쟁 가설을 제거한다.

정당화되는 가장 작은 변경으로 근본 원인을 고친다.

- 값싼 로컬 테스트 대상이 있으면 pstack의 `tdd` 스킬을 호출하고 수정 전에 실패하는 테스트를 먼저 쓴다.
- 경로가 비싸거나, 불분명하거나, 통합 비중이 크면 TDD를 건너뛴 이유를 밝힌다.
- 관련 없는 정리는 넣지 않는다.
- 변경이 설정된 노력 예산이나 위험 예산을 넘어서면 멈춘다.

## 13. 수정 입증

원래의 기준 증거를 보존한다.

패치된 빌드에서 다음을 한다.

1. 같은 실제 UI 경로를 돌린다.
2. 두 번 반복한다.
3. 깨진 상태가 사라졌음을 보여 준다.
4. 그 자리에 기대 상태가 나타남을 보여 준다.
5. 수정 후 녹화와 스크린샷을 캡처한다.
6. 기준 빌드에서 쓴 것과 같은 실제 상태 값으로 교차 확인한다.

컴파일, 단위 테스트, 코드 리뷰, 그럴듯한 diff는 수정 후 증거가 아니다.

집중 테스트를 돌린 뒤 바뀐 동작 주변의 영향 범위를 스모크 테스트한다. 변경이 영향을 줄 수 있는 인접 상태, 입력, 권한, 플랫폼, 실패 경로를 다룬다. 회귀가 남아 있으면 pull request 없이 멈춘다.

## 14. Draft pull request 열기

수정 전후 증거를 확보한 뒤에만 다음을 한다.

- 최종 diff에 관련 없는 변경이나 비밀 정보가 없는지 검토한다.
- 저장소의 필수 검사를 돌린다.
- 저장소 워크플로가 허용하면 작고 순서 있는 커밋을 만든다.
- Draft pull request를 연다. 이 워크플로에서는 절대 병합하거나 배포하지 않는다.
- tracker가 지원하는 pull request 문법으로 설정된 tracker 이슈를 링크한다.
- 설정된 공개 URL 형식을 쓴다. 보통 `https://github.com/{owner}/{repo}/pull/{number}`다.
- 재현 단계, 근본 원인, 테스트 결과, 수정 전후 증거, 영향 범위 점검 결과를 넣는다.
- pull request 본문과 모든 Slack 업데이트를 pstack의 `unslop` 스킬로 다듬는다.

pull request 생성이 실패하면 성공했다고 주장하지 않는다. 커밋이나 브랜치 상태를 실행 출력에 남기고 운영 상태를 `Fix did not land`로 표시한다.

성공하면 운영 상태를 `Draft pull request opened`로 표시하고 운영 스레드에 pull request 링크를 담은 간결한 답글을 하나 올린다. 원본 채널에 두 번째 루트나 요청받지 않은 원본 답글을 만들지 않는다.

## 15. 후속 대응과 정리

설정된 후속 대응 시간 동안 운영 스레드를 지켜본다.

- 직접 받은 질문에는 이미 모은 증거로 답한다.
- 구체적인 정정이 설정을 무효로 만들면 한 번 반영하고 재현을 한 번 다시 돌린다.
- 사람들 사이의 조율과 잡담에는 끼지 않는다.
- 멈추라고 하면 멈춘다.

제어 어댑터의 정리 기능은 항상 호출한다. 산출물은 설정된 보존 정책이 허용하는 기간까지만 둔다.
