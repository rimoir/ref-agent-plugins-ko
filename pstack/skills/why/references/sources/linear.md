# Linear 티켓

## 이 출처에 담긴 것

- 기능, 버그, 그 동기를 설명하는 이슈
- 이슈에 첨부된 프로젝트 문서(PRD나 명세인 경우가 많다)
- 상위·하위 이슈 관계(넓은 이니셔티브 → 구체적 티켓)
- 이슈 코멘트(설명 보충, 범위 변경, "왜 이걸 하는가"에 대한 근거)
- 동기의 종류를 알려 주는 라벨(예: `compliance`, `customer-request`, `perf`)
- 범위 변경을 설명하는 상태 업데이트
- 첨부 파일과 연결된 GitHub PR

Linear는 제품·비즈니스 맥락이 주로 사는 곳이다. "고객 X가 요청해서 한다"나 "Q3 컴플라이언스 이니셔티브용이다" 같은 층이다.

## 검색하는 법

Linear MCP를 쓴다.

1. **연결된 티켓부터 시작한다.** 시드 커밋이나 PR이 티켓 ID(예: `ENG-1234`, `[BUG-567]`)를 참조하면 `get_issue`로 그것부터 가져온다. 코멘트를 포함해 이슈 전체를 읽는다.
2. **키워드로 관련 이슈를 나열한다.** 기능 이름, 핵심 심볼, 비즈니스 용어로 `list_issues`의 텍스트 검색을 쓴다. 여러 표현을 시도한다.
3. **이슈 트리를 따라간다.** 하위 이슈에 닿으면 상위 이슈를 가져온다. 하위 이슈는 전술적이다. "왜"는 상위 이슈에 있을 때가 많다.
4. **프로젝트 문서를 읽는다.** 이슈가 프로젝트에 속해 있으면 `get_project`를 쓰고 첨부 문서를 확인한다. 명세와 근거가 가장 자주 기록되는 곳이 프로젝트 수준 문서다.
5. **라벨과 마일스톤을 확인한다.** 라벨은 동기의 범주(customer-request, incident-followup, compliance)를 암시한다. 마일스톤은 작업을 마감과 묶으며, 마감이 동기를 드러낼 때가 많다.

## 여기서 좋은 증거의 모습

- 비즈니스 문제를 밝힌 이슈 설명: "Customer Acme needs X because of their SOC2 audit"(고객 Acme가 SOC2 감사 때문에 X가 필요하다)
- 결정을 기록한 코멘트: "We decided to go with approach B because approach A would require touching the billing service"(A 접근은 결제 서비스를 건드려야 해서 B 접근으로 가기로 했다)
- 이니셔티브처럼 제목을 단 상위 이슈: "Q3 Enterprise Readiness"나 "Reduce Payment Failures"
- 첨부된 PRD나 명세
- `customer:acme`, `incident-followup`, `compliance`, `perf-regression` 같은 라벨

## 흔한 함정

- **범위 이탈.** PR이 참조하는 티켓이 닫혔다가 다른 범위로 다시 열렸을 수 있다. 히스토리 전체를 읽는다.
- **기계적 템플릿.** "Why" 섹션을 의무화하고는 상투적인 문구로 채우는 팀도 있다. 일반적인 문구("사용자 경험 개선")는 아마 진짜 답이 아니다.
- **낡은 티켓.** 오래된 티켓은 이미 바뀐 계획의 한 버전을 반영할 때가 많다. 날짜를 확인하고 코드의 출시 날짜와 대조한다.
- **중복으로 닫힌 사슬.** duplicate-of 관계를 따라 정규 티켓까지 거슬러 올라간다.
- **비공개 워크스페이스 콘텐츠.** 이슈에 접근할 수 없으면 추측하지 말고 빈틈으로 기록한다.

## 돌려줄 것

관련 티켓마다 다음을 돌려준다.
- 티켓 ID와 제목
- 설명이나 코멘트에서 인용한 문제·동기(풀어 쓰지 않는다. synthesizer가 인용하려면 정확한 원문이 필요하다)
- 라벨, 상위 이슈, 프로젝트
- 작성자, 생성 날짜, 종료 날짜
- 가능하면 티켓 링크
