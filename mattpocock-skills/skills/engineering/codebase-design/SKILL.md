# 코드베이스 설계

**깊은 모듈**을 설계한다. 깊은 모듈은 작은 인터페이스 뒤에 많은 동작을 담고, 깔끔한 교체 지점(seam)에 놓이며, 그 인터페이스로 테스트할 수 있는 모듈이다. 코드를 설계하거나 구조를 바꾸는 곳이면 어디서든 이 용어와 원칙을 쓴다. 목표는 호출자에게는 활용도(leverage), 유지보수하는 사람에게는 지역성(locality), 모두에게는 테스트하기 쉬운 코드다.

## 용어집

아래 용어를 정확히 그대로 쓴다. "컴포넌트(component)", "서비스(service)", "API", "경계(boundary)"로 바꿔 쓰지 않는다. 일관된 용어를 쓰는 것이 이 스킬의 목적이다.

**모듈(Module)**: 인터페이스와 구현이 있는 모든 것. 일부러 크기를 따지지 않는다. 함수, 클래스, 패키지, 여러 계층을 가로지르는 조각 모두 모듈이다. _Avoid_: 유닛, 컴포넌트, 서비스.

**인터페이스(Interface)**: 호출자가 모듈을 올바르게 쓰려면 알아야 하는 모든 것. 타입 시그니처뿐 아니라 불변 조건, 호출 순서 제약, 오류 발생 방식, 필요한 설정, 성능 특성까지 포함한다. _Avoid_: API, 시그니처(범위가 너무 좁다. 타입 수준의 겉모습만 가리킨다).

**구현(Implementation)**: 모듈 안에 들어 있는 것, 즉 모듈의 코드 본문. **어댑터**와 구분한다. 어떤 것은 구현이 큰 작은 어댑터(Postgres 저장소)일 수 있고, 구현이 작은 큰 어댑터(인메모리 가짜 객체)일 수도 있다. 교체 지점이 주제일 때는 "어댑터"를, 그 밖에는 "구현"을 쓴다.

**깊이(Depth)**: 인터페이스에서 얻는 활용도. 호출자(또는 테스트)가 배워야 하는 인터페이스 단위당 실행할 수 있는 동작의 양이다. 작은 인터페이스 뒤에 많은 동작이 있으면 모듈이 **깊다**. 인터페이스가 구현만큼 복잡하면 모듈이 **얕다**.

**교체 지점(Seam)** _(Michael Feathers)_: 그 자리의 코드를 고치지 않고도 동작을 바꿔 끼울 수 있는 곳. 모듈의 인터페이스가 놓이는 *위치*다. 교체 지점을 어디에 둘지는 그 뒤에 무엇을 둘지와 별개인 설계 결정이다. _Avoid_: 경계(DDD의 bounded context와 뜻이 겹친다).

**어댑터(Adapter)**: 교체 지점에서 인터페이스를 충족하는 구체적인 것. 안에 무엇이 들어 있는지가 아니라 *역할*(어느 자리를 채우는지)을 가리킨다.

**활용도(Leverage)**: 호출자가 깊이에서 얻는 것. 배워야 하는 인터페이스 단위당 더 많은 기능을 얻는다. 구현 하나가 호출 지점 N곳과 테스트 M개에서 두루 이득을 준다.

**지역성(Locality)**: 유지보수하는 사람이 깊이에서 얻는 것. 변경, 버그, 지식, 검증이 호출자들 사이에 흩어지지 않고 한곳에 모인다. 한 번 고치면 모든 곳이 고쳐진다.

## 깊은 모듈과 얕은 모듈

**깊은 모듈** = 작은 인터페이스 + 많은 구현:

```
┌─────────────────────┐
│   작은 인터페이스   │  ← 메서드가 적고 매개변수가 단순하다
├─────────────────────┤
│                     │
│      깊은 구현      │  ← 복잡한 로직을 숨긴다
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 적은 구현(피한다):

```
┌─────────────────────────────────┐
│       큰 인터페이스             │  ← 메서드가 많고 매개변수가 복잡하다
├─────────────────────────────────┤
│  얇은 구현                      │  ← 받은 것을 그대로 넘기기만 한다
└─────────────────────────────────┘
```

인터페이스를 설계할 때 다음을 묻는다.

- 메서드 수를 줄일 수 있는가?
- 매개변수를 단순하게 만들 수 있는가?
- 더 많은 복잡성을 안에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 성질이다.** 깊은 모듈도 안쪽은 작고 모킹할 수 있고 바꿔 끼울 수 있는 부품으로 이루어질 수 있다. 그 부품들이 인터페이스에 드러나지 않을 뿐이다. 모듈에는 인터페이스에 있는 **외부 교체 지점**뿐 아니라 **내부 교체 지점**(구현 내부에 감춰져 있고 모듈 자체 테스트가 쓰는 교체 지점)도 있을 수 있다.
- **삭제 테스트.** 모듈을 지운다고 가정한다. 복잡성이 사라지면 그 모듈은 받은 것을 그대로 넘기기만 하던 모듈이다. 복잡성이 호출자 N곳에 다시 나타나면 그 모듈은 존재할 이유가 있던 모듈이다.
- **인터페이스가 곧 테스트 지점이다.** 호출자와 테스트는 같은 교체 지점을 거친다. 인터페이스를 *건너뛰어* 안쪽을 테스트하고 싶다면 모듈의 형태가 잘못되었을 가능성이 크다.
- **어댑터가 하나면 가정일 뿐인 교체 지점이고, 둘이면 실제 교체 지점이다.** 교체 지점을 사이에 두고 실제로 바뀌는 것이 없으면 교체 지점을 만들지 않는다.

## 테스트하기 쉽게 설계하기

좋은 인터페이스는 테스트를 자연스럽게 만든다.

- **의존성을 직접 만들지 말고 인자로 받는다.**

  ```typescript
  // 테스트하기 쉽다
  function processOrder(order, paymentGateway) {}

  // 테스트하기 어렵다
  function processOrder(order) {
    const gateway = new StripeGateway();
  }
  ```

- **부수 효과를 일으키지 말고 결과를 반환한다.**

  ```typescript
  // 테스트하기 쉽다
  function calculateDiscount(cart): Discount {}

  // 테스트하기 어렵다
  function applyDiscount(cart): void {
    cart.total -= discount;
  }
  ```

- **드러나는 면을 작게 만든다.** 메서드가 적으면 필요한 테스트도 적다. 매개변수가 적으면 테스트 준비가 단순해진다.

## 관계

- **모듈**에는 **인터페이스**가 정확히 하나 있다(호출자와 테스트에 드러내는 면).
- **깊이**는 **모듈**의 성질이며 그 **인터페이스**를 기준으로 잰다.
- **교체 지점**은 **모듈**의 **인터페이스**가 놓이는 곳이다.
- **어댑터**는 **교체 지점**에 놓여 **인터페이스**를 충족한다.
- **깊이**는 호출자에게 **활용도**를, 유지보수하는 사람에게 **지역성**을 준다.

## 받아들이지 않는 관점

- **구현 줄 수를 인터페이스 줄 수로 나눈 비율로 깊이를 재는 관점**(Ousterhout): 구현을 부풀리기만 해도 깊이가 커진다. 여기서는 깊이를 활용도로 본다.
- **"인터페이스"를 TypeScript `interface` 키워드나 클래스의 public 메서드로 보는 관점**: 범위가 너무 좁다. 여기서 말하는 인터페이스는 호출자가 알아야 하는 모든 사실을 포함한다.
- **"경계(Boundary)"**: DDD의 bounded context와 뜻이 겹친다. **교체 지점**이나 **인터페이스**라고 쓴다.
