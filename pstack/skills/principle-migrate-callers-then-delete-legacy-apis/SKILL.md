# 호출자를 옮기고 레거시 API를 지운다

새 API가 옳은 설계라고 결정했으면, 호환 계층을 보존하지 말고 같은 리팩터링 흐름에서 호출자를 옮기고 옛 API를 없앤다.

**규칙:**
- 내부 호출자가 아직 있다는 이유만으로 레거시 API 경로를 남기지 않는다
- 호출자 목록을 만들고, 옮기고, 옛 API를 바로 지운다
- 임시 어댑터는 기본 아키텍처가 아니라 기한을 정한 예외로 다룬다
- 테스트는 새 계약을 검증하도록 고치고, 리팩터링 전 구현 세부만 지키는 테스트는 지운다

**적용하는 경우:**
- 하위 호환성에 기대는 외부 사용자가 없다
- 프로젝트가 조율된 호환성 파괴 변경을 감당할 수 있다
- 새 API가 단순화나 리팩터링 계획의 일부다

옛 API와 새 API를 둘 다 두면 이중 경로의 복잡도가 생기고, 정리가 느려지고, 코드베이스가 덧붙이기만 하는 것처럼 느껴진다.
