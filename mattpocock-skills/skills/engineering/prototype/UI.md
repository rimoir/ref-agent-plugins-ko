# UI 프로토타입

한 라우트 안에 **서로 완전히 다른 UI 변형을 여러 개** 만들고, 화면 아래에 떠 있는 막대로 전환하게 한다. 사용자는 브라우저에서 변형을 바꿔 가며 보고 하나를 고르거나(또는 여러 변형에서 좋은 부분을 가져오고) 나머지는 버린다.

질문이 무언가의 모습이 아니라 로직이나 상태에 관한 것이라면 잘못 고른 갈래다. [LOGIC.md](LOGIC.md)를 쓴다.

## 이 형태가 맞는 경우

- "이 페이지는 어떤 모습이어야 할까?"
- "확정하기 전에 이 대시보드의 선택지를 몇 개 보고 싶다."
- "설정 화면에 다른 레이아웃을 적용해 봐."
- 이 방식이 없으면 사용자가 머릿속의 흐릿한 목업 몇 개 중에서 고르느라 하루를 쓸 모든 경우

## 하위 형태: A를 강하게 우선한다

UI 프로토타입은 **앱의 나머지 부분과 함께 놓여 있을 때** 훨씬 판단하기 쉽다. 실제 헤더, 실제 사이드바, 실제 데이터, 실제 밀도가 함께 보여야 한다. 일회용 라우트 하나만 따로 있으면 주변 맥락이 없어서 어떤 변형이든 그럴듯해 보인다. 변형을 넣을 만한 기존 페이지가 있으면 하위 형태 A를 기본으로 쓴다. 프로토타입을 넣을 만한 가까운 페이지가 정말로 없을 때만 하위 형태 B를 쓴다.

### 하위 형태 A: 기존 페이지 수정 (우선)

라우트가 이미 있다. 변형은 **같은 라우트 안에서** 렌더링하고, `?variant=` URL 검색 파라미터로 어떤 변형을 보여 줄지 정한다. 기존 데이터 조회, 파라미터, 인증은 모두 그대로 둔다. 렌더링만 바꾼다. 이것이 기본값이다. 쓰지 않을 구체적인 이유가 없으면 이것을 고른다.

프로토타입 대상이 아직 페이지가 없지만 *자연스럽게 어떤 페이지 안에 들어갈* 것이라면(대시보드의 새 섹션, 설정 화면의 새 카드, 기존 흐름의 새 단계) 역시 하위 형태 A다. 변형을 그 페이지 안에 넣는다.

### 하위 형태 B: 새 페이지 (최후의 수단)

프로토타입 대상이 들어갈 기존 페이지가 정말로 없을 때만 쓴다(예: 완전히 새로운 최상위 화면, 또는 적당한 곳 어디에도 넣을 수 없는 흐름).

프로젝트가 이미 쓰는 라우팅 규칙을 따라 **일회용 라우트**를 만든다. 새 최상위 구조를 만들지 않는다. 프로토타입임이 분명히 보이게 이름을 붙인다(예: 경로나 파일 이름에 `prototype`이라는 단어를 넣는다). `?variant=` 방식은 똑같이 쓴다.

하위 형태 B로 정하기 전에 확인한다. 이것을 넣을 기존 페이지가 정말 없는가? 빈 라우트에서는 내용이 채워진 라우트라면 드러났을 설계 문제가 가려진다.

어느 하위 형태든 화면 아래에 떠 있는 막대는 똑같다.

## 절차

### 1. 질문을 적고 N을 정한다

기본은 **변형 3개**다. 5개를 넘으면 더 이상 서로 완전히 다르지 않고 쓸모없는 차이만 늘어나므로 5개를 상한으로 둔다.

계획을 한 줄로 프로토타입 위치나 파일 맨 위 주석에 적는다.

> "설정 페이지의 변형 3개, 기존 `/settings` 라우트에서 `?variant=`로 전환한다."

사용자가 지금 반박할 수 있는 자리에 있든 없든 이 방식은 통한다.

### 2. 서로 완전히 다른 변형을 만든다

변형마다 초안을 만든다. 각 변형은 다음에 맞춘다.

- 페이지의 목적과 페이지가 쓸 수 있는 데이터
- 프로젝트의 컴포넌트 라이브러리나 스타일 체계(TailwindCSS, shadcn, MUI, 순수 CSS 등 무엇이든)
- 분명한 export 컴포넌트 이름. 예: `VariantA`, `VariantB`, `VariantC`

변형은 **구조가 달라야** 한다. 색만 다른 것이 아니라 레이아웃, 정보 계층, 사용자가 주로 조작하는 요소가 달라야 한다. 조금씩만 바꾼 카드 그리드 여러 개는 UI 프로토타입이 아니라 겉모습만 다른 같은 화면이다. 두 초안이 너무 비슷하게 나오면 "카드 그리드를 쓰지 마라" 같은 명시적인 지시를 주고 하나를 다시 만든다.

### 3. 변형을 하나로 연결한다

라우트에 전환 컴포넌트를 하나 만든다.

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

하위 형태 A(기존 페이지)에서는 기존 데이터 조회를 모두 전환 컴포넌트 위쪽에 그대로 둔다. 변형마다 바뀌는 것은 렌더링되는 하위 트리뿐이다.

하위 형태 B(새 페이지)에서는 `/prototype/<name>` 아래의 일회용 라우트가 같은 전환 컴포넌트를 넣는다.

### 4. 떠 있는 전환 막대를 만든다

화면 아래 가운데에 위치가 고정된 작은 막대를 두고 다음 요소를 넣는다.

- **왼쪽 화살표**: 이전 변형으로 넘어간다(처음에서 누르면 마지막으로 돌아간다).
- **변형 라벨**: 현재 변형 키를 보여 주고, 변형이 이름을 export하면 그 이름도 함께 보여 준다. 예: `B (Sidebar layout)`.
- **오른쪽 화살표**: 다음 변형으로 넘어간다(마지막에서 누르면 처음으로 돌아간다).

동작:

- 화살표를 누르면 URL 검색 파라미터를 바꾼다(프레임워크의 라우터를 쓴다. 예: Next의 `router.replace`, React Router의 `navigate` 등). 그래야 변형을 링크로 공유할 수 있고 새로 고침해도 유지된다.
- 키보드: `←`, `→` 화살표 키로도 전환한다. `<input>`, `<textarea>`, `[contenteditable]`에 포커스가 있을 때는 화살표 키를 가로채지 않는다.
- 페이지와 시각적으로 구분되게 한다(예: 대비가 강한 알약 모양, 옅은 그림자). 평가 중인 디자인의 일부가 아니라는 것이 분명히 보여야 한다.
- 운영 빌드에서는 숨긴다. `process.env.NODE_ENV !== 'production'` 같은 검사로 막아서, 프로토타입이 실수로 병합되어도 막대가 사용자에게 배포되지 않게 한다.

전환 막대는 공용 컴포넌트 하나로 만들어 두 하위 형태가 모두 재사용할 수 있게 한다. 프로젝트에서 공용 UI를 두는 곳에 둔다.

### 5. 넘겨준다

URL(과 `?variant=` 키)을 알려 준다. 사용자는 시간이 날 때 변형을 바꿔 가며 본다. 가장 쓸모 있는 피드백은 대개 **"B의 헤더에 C의 사이드바를 쓰고 싶다"** 같은 것이고, 그것이 사용자가 실제로 원하는 디자인이다.

### 6. 답을 기록하고 정리한다

어떤 변형이 선택되면 답(어떤 변형인지와 그 이유)을 기록하고, [SKILL](SKILL.md)에 적힌 방식으로 프로토타입을 남긴다. 선택된 변형은 실제 코드에 반영하고, 나머지는 main이 아니라 보관용 브랜치로 옮긴다.

- **하위 형태 A**: 선택된 변형을 기존 페이지에 반영한다. 선택되지 않은 변형과 전환 막대는 main에서 뺀다.
- **하위 형태 B**: 선택된 변형을 실제 라우트로 만든다. 일회용 라우트와 전환 막대는 main에서 뺀다.

변형 전체가 1차 자료이므로 버리지 않고 보관용 브랜치에 남긴다. main 브랜치에 남겨 둔 변형 컴포넌트와 전환 막대는 금방 낡아서 다음에 코드를 읽는 사람을 헷갈리게 한다.

## 피해야 할 패턴

- **색이나 문구만 다른 변형.** 그것은 미세 조정이지 프로토타입이 아니다. 진짜 변형은 구조부터 다르다.
- **변형끼리 코드를 너무 많이 공유하기.** 공용 `<Header>`는 괜찮지만 공용 `<Layout>`을 쓰면 프로토타입의 의미가 없어진다. 각 변형은 레이아웃을 자유롭게 버릴 수 있어야 한다.
- **변형을 실제 데이터 변경에 연결하기.** 읽기 전용 프로토타입이면 된다. 변형이 데이터를 바꿔야 한다면 스텁에 연결한다. 질문은 "이게 어떤 모습이어야 하는가"이지 "백엔드가 동작하는가"가 아니다.
- **프로토타입을 그대로 운영 코드로 만들기.** 변형 코드는 프로토타입의 제약(테스트 없음, 최소한의 오류 처리) 아래에서 작성되었다. 실제 코드에 반영할 때 제대로 다시 작성한다.
