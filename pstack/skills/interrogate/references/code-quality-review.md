# 코드 품질 리뷰

각 리뷰어는 루브릭에 더해 이 코드 품질 관점을 적용한다. 구현 품질, 유지보수성, 추상화 품질, 코드베이스 건강에 초점을 둔 엄격한 기준이다.

무엇보다 코드 구조에 야심을 가진다. 국소적인 정리만 짚고 끝내지 않는다. "코드 유도(code judo)" 수, 즉 동작은 보존하면서 구현을 극적으로 더 단순하고, 작고, 직접적이고, 우아하게 만드는 재구성을 적극적으로 찾는다.

## 핵심 프롬프트

다음을 출발점으로 삼는다.

> 현재 브랜치 변경 사항의 코드 품질을 깊이 감사한다.
> 동작에 영향을 주지 않으면서 코드 품질을 의미 있게 높이도록 변경의 구조와 구현을 다시 생각한다.
> 추상화와 모듈성을 개선하고, 스파게티 코드를 줄이고, 간결함과 가독성을 높인다.
> 야심을 가진다. 코드베이스 일부를 재구성해 구현을 개선할 분명한 길이 있다면 그렇게 한다.
> 극도로 철저하고 엄밀하게 한다. 두 번 재고 한 번 자른다.

## 차원

각 차원은 한 번씩만 적는다. 관련 있는 것을 적용한다.

0. **구조 단순화에 야심을 가진다.** "조금 더 깔끔해질 수 있겠다"에서 멈추지 않는다. 분기, 헬퍼, 모드, 조건문, 계층 전체를 사라지게 하는 관점 전환을 찾는다. 코드 유도 수가 있을 때가 많다고 가정한다. 기존 아키텍처를 더 효과적으로 쓰고 변경을 극적으로 단순하게 만드는 수다. 복잡도를 재배치하는 대신 지울 수 있다면 강하게 밀어붙인다.

1. **아주 강한 이유 없이 PR이 1천 줄 미만 파일을 1천 줄 넘게 키우지 못하게 한다.** 이것을 강한 냄새로 본다. 헬퍼, 하위 컴포넌트, 모듈로 추출하는 쪽을 우선한다. diff가 그 경계를 넘으면 코드를 먼저 분해해야 하는지 묻는다. 결과 파일이 분명히 잘 정리된 채로 남는, 설득력 있는 구조적 이유가 있을 때만 면제한다.

2. **기존 코드에서 스파게티가 자라지 못하게 한다.** 새 즉흥 조건문, 흩어진 특수 사례, 관련 없는 흐름에 끼워 넣은 일회성 분기를 의심한다. "아무 데나 있는 이상한 if 문"을 스타일 지적이 아니라 설계 문제로 본다. 기존 경로를 엉키게 하는 대신 로직을 전용 헬퍼, 상태 기계, 모듈로 옮기는 쪽을 우선한다.

3. **동작하는 코드를 받아들이는 데 그치지 않고 설계를 정리하는 쪽으로 기운다.** 동작은 그대로 두고 구조를 의미 있게 깔끔하게 만들 수 있다면 더 깔끔한 버전을 밀어붙인다. 같은 복잡도를 여기저기 퍼뜨리는 리팩터링보다 움직이는 부품을 없애는 단순화를 우선한다.

4. **꼼수나 마법 같은 코드보다 직접적이고 지루하고 유지보수하기 쉬운 코드를 우선한다.** 부서지기 쉽거나 즉흥적이거나 "마법" 같은 동작을 문제로 본다. 단순한 데이터 모양 가정을 숨기는 범용 메커니즘을 의심한다. 명료함은 얻지 못하고 간접층만 더하는 얇은 추상화, 항등 래퍼, 통과용 헬퍼를 짚는다.

5. **유지보수성에 영향을 줄 때는 타입과 경계의 깔끔함을 밀어붙인다.** 더 명확한 타입 경계가 있을 수 있는데 쓸데없는 optional, `unknown`, `any`, 캐스트투성이 코드를 쓰면 문제 삼는다. 느슨한 모양의 즉흥 객체보다 명시적으로 타입이 정해진 모델을 우선한다. 분기가 불분명한 불변식을 덮으려고 조용한 fallback에 기대면 경계를 명시해야 하지 않는지 묻는다.

6. **로직은 정규 계층에 두고 기존 헬퍼를 재사용한다.** 기능 로직이 공용 경로로 새거나 구현 세부가 API로 새는 것을 짚는다. 맞춤형 일회성 코드보다 기존 정규 유틸리티를 우선한다. 어긋남을 정상으로 받아들이지 말고 코드를 올바른 패키지, 서비스, 모듈 쪽으로 옮긴다.

7. **더 깔끔한 구조가 뻔할 때는 불필요한 순차 조율과 원자적이지 않은 갱신을 설계 냄새로 본다.** 독립적인 작업이 이유 없이 직렬화되어 있으면 병렬로 돌려야 하지 않는지 묻는다. 관련 갱신이 상태를 반쯤 적용된 채로 남길 수 있으면 더 원자적인 구조를 밀어붙인다. 미시 최적화에 지나치게 매달리지는 않되, 코드를 더 부서지기 쉽게 만드는 피할 수 있는 조율 복잡도는 짚는다.

## 출력 기대

구조적 코드 품질 회귀와 놓친 단순화를 가장 먼저, 다음으로 스파게티와 분기 복잡도, 그다음 경계·타입·파일 크기 문제, 마지막으로 작은 모듈성·가독성 문제 순으로 우선순위를 둔다.

## 승인 기준

동작이 맞아 보인다는 이유만으로 승인하지 않는다. 작성자가 정당화하지 못하면 다음을 사실상의 차단 사유로 본다. 코드 유도 수로 지울 수 있는 부수적 복잡도를 PR이 많이 남겨 둔다. 파일을 1000줄 미만에서 1000줄 초과로 키운다. 기존 흐름을 엉키게 하는 즉흥 분기를 더한다. 기능 검사를 공용 코드 곳곳에 흩뿌린다. 불필요한 추상화, 래퍼, 캐스트투성이 계약을 더하거나, 분명한 정규 위치가 있는데 기존 헬퍼를 중복하거나 로직을 잘못된 계층에 둔다. 이 조건에 해당하지 않으면 명시적이고 실행 가능한 피드백을 남기고 더 깔끔한 분해를 밀어붙인다.

## 리뷰 어조

품질에 관해서는 직설적이고 진지하고 까다롭게 군다. 무례하지는 않되, 큰 유지보수성 문제를 가벼운 제안으로 누그러뜨리지 않는다. 코드가 코드베이스를 더 지저분하게 만들고 있다면 그렇다고 말한다. 구현이 뻔하고 극적인 단순화를 놓쳤다면 그것도 말한다. 진짜 문제가 구조적인데 "이름을 바꿔 보는 건 어때요" 정도로 만족하지 않는다.
