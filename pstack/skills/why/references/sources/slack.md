# Slack 대화

## 이 출처에 담긴 것

- 문제와 결정을 두고 실시간으로 나눈 논의
- 급박한 결정이 내려진 장애 채널
- 트레이드오프를 두고 논쟁한 설계 논의 스레드
- 문서로 남지 않은, 시니어 엔지니어가 답한 질문
- 무언가를 다시 손본 이유를 설명하는 머지 후 논의
- DM(대개 검색할 수 없으니 그에 맞게 범위를 잡는다)

Slack은 *실제* 결정이 내려진 곳일 때가 많다. 문서까지 쓸 필요가 없던 작은 변경이면 더욱 그렇다. 또한 가장 쉽게 사라지는 출처다. 스레드가 지워지고, 채널이 보관 처리되고, 검색 품질은 시간이 지날수록 떨어진다.

## 검색하는 법

Slack MCP 도구는 제각각이다. 어떤 Slack MCP를 쓸 수 있는지 확인하고 도구 스키마부터 살핀다. `mcp_auth`가 필요할 수 있다. 인증이 실패하면 멈추고 빈틈을 보고한다.

1. **작성자로 좁힌 검색.** PR 머지 날짜 전후의 PR 작성자 메시지. 범위가 극적으로 줄고 노다지를 캐는 경우가 많다.
2. **기능 이름과 핵심 심볼 키워드 검색.** 오타와 편한 말투 표현도 포함한다.
3. **PR URL 검색.** Slack에는 리뷰나 논의 중에 PR 링크가 자주 올라온다. PR URL(또는 그냥 `/pull/<number>`)로 검색한다.
4. **오류 문자열 검색.** 코드가 특정 오류를 처리한다면 그 오류 문자열로 검색한다. 장애 스레드가 자주 드러난다.
5. **채널로 좁힌 검색.** 가능성 높은 채널로 좁힌다.
   - `#eng-*`. 엔지니어링 논의
   - `#proj-*`. 프로젝트 채널
   - `#incident-*` / `#sev-*`. 장애 채널
   - 담당 팀 전용 채널
   - 설계 리뷰 채널
6. **스레드 따라가기.** 관련 메시지를 찾으면 스레드 전체를 가져온다. 결정은 답글에 있을 때가 많다.

## 여기서 좋은 증거의 모습

- 트레이드오프를 명시적으로 논쟁한 스레드("A를 쓰려고 했는데 B가 더 낫다, 왜냐하면...")
- 코드가 막는 버그를 설명하는 장애 채널 메시지
- 리뷰어의 질문과 작성자나 리드의 권위 있는 답
- 결정이 내려진 회의에 대한 언급
- 고객 요청을 설명하는 프로덕트 매니저나 고객 대응 엔지니어의 메시지

## 흔한 함정

- **채널 발굴의 한계.** 아주 오래된 메시지는 보존 정책 때문에 사라졌을 수 있다. 특정 날짜 이전으로 아무것도 찾을 수 없으면 그 보존 절벽을 기록한다.
- **검색되지 않는 DM.** 많은 결정이 검색할 수 없는 DM에서 이뤄진다. 놓치게 된다. 알려진 한계다.
- **결정으로 착각한 농담.** Slack은 격식이 없다. "ㅋㅋ 그냥 그거 해"는 커밋 직전에 나왔더라도 결정이 아니다. 숙고한 논의를 찾는다.
- **메시지 하나만 볼 때의 맥락 붕괴.** 스레드 없이 보면 메시지 하나가 맥락 속에서와 다르게 읽힐 때가 많다. 스레드는 늘 가져온다.
- **인증 실패.** MCP가 인증되지 않았으면 멈춘다. 결과를 지어내지 않는다. Slack을 검색할 수 없었다고 보고한다.

## 돌려줄 것

관련 스레드마다 다음을 돌려준다.
- 채널 이름
- 고유 링크 또는 스레드 ID
- 참여자
- 논의 날짜 범위
- 핵심 인용(원문 그대로)과 발화자
- 맥락: 어떤 스레드, 장애, 논의의 일부였는지
